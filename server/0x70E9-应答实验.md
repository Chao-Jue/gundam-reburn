# 0x70E9 应答实验（65 张已下完，唯一的交互点）

> 2026-10-20 18:30。
>
> ⚠️ **状态标注（2026-11-01 补）**：本文第 1~3 节是**当时的观测**，第 4/5 节是
> **候选设计与执行预案**，不是实验结论。"必须回应答、界面才会推进"这句当时没有对照实验支撑。
> 真机结果见文末 **§6**（2026-11-01，114 次实收实测）。

## 1. 先钉死一个事实：客户端的清单就是 65 项，而且已经全部给完了

把 `server/fake_auth.log` 里 10 轮登录的 `0xF86A` 请求序列全部拉出来：

- **每一轮都是 65 条**，一条不多一条不少；
- 最后一条恒为 `develop/mechanic_overcustom.csv`；
- 与 `download_list.csv` 的 74 行做差集，**客户端从没要过的 9 张**是：

```
player_navi/player_navi.csv
mission/mission_xwar_banpick_rule.csv
reward/monthly_bonus_reward.csv
item/advanced_option.csv
season_class/season_class_information.csv
season_class/season_class_up_reward.csv
reward/season_rankerbattle_reward.csv
trend/trend_data_weapon.csv
reward/beginner_challenge.csv
```

⇒ **"缺表"这个方向对"能否进大厅"是无关的**。客户端只要 65 张，65 张全给完了。
⇒ 65 张之后客户端不再要第 66 张，不是卡在下载，是**下载阶段已经结束**。

> 注意顺序也不是 CSV 顺序：客户端第 7 条要 `item/bullet.csv`，而 CSV 第 7 行是
> `item/item.csv`。所以客户端用的是自己内嵌的清单，跟我们的 CSV 只是同集合。

## 2. 65 张之后客户端只做一件事：发 `0x70E9`

```
15:51:50  第 65 张 develop/mechanic_overcustom.csv 请求 → 我们回 op_5290
15:51:53  客户端 frame 68（明文 58 字节）
          消息 操作码=70e9 载荷=56 余=05000000000000000000000000
                43 3a 5c 57 49 4e 44 4f 57 53 5c 73 79 73 74 65 6d 33 32 5c
                75 78 74 68 65 6d 65 2e 64 6c 6c 5f 61 30 61 65 32 62 32 62 00
          = 三个整数 (5, 0, 0) + 路径 "C:\WINDOWS\system32\uxtheme.dll_a0ae2b2b"
15:52:38  recv timeout (45s idle)   ← 我们一帧都没回
```

另一轮（14:13）里同一条出现过两次，间隔 36s，第二次是 `MSCTF.dll_36bd5c96`。

**判读**：这是反外挂的**模块完整性上报**——客户端把某个 DLL 连同一个 8 位十六进制
指纹（很可能是它自己算出的哈希）报给服务端，然后**等服务端裁决**。
我们从不回复，所以它就一直等。

## 3. 已加到服务端的能力

`server/fake_auth.py` 新增：

| 项 | 说明 |
|---|---|
| `parse_msg(pt)` | 通用入站解析，返回 `(opcode, 正文)`，不再只认 `0xF86A` |
| `op_block(opcode, body)` | 任意操作码的下行消息构造（自动 16 字节对齐） |
| `body_70e9(rest, mode)` | 四种应答候选 |
| `--seventye9 / --70e9` | `none` / `zero`（默认）/ `ok4` / `mirror` / `echo` |

四种候选的正文：

| mode | 正文 | 理由 |
|---|---|---|
| `none` | 不回 | 现状，用于对照 |
| `zero` | 12 个 0（3 个整数） | 最像"校验通过"的 ack |
| `ok4` | 4 个 0（1 个整数） | 有些协议只要一个 result |
| `mirror` | 回显请求前 12 字节（5,0,0） | 如果客户端把第一个整数当"请求类型"回读 |
| `echo` | 整段回显 | 兜底 |

自测已过（构造/解析/对齐都正确，见 `op_block(0x70E9, 4 个 0)` → `0006e97000000000 0006ffff00000000`）。

## 4. 本轮实验步骤

1. **先手起 fake_auth**（不要让它被 `start_local.cmd` 顶掉，30000 已占用时 start_local 会跳过）：
   ```
   python server/fake_auth.py --sweep --sweep-gap 2 --idle 60 --seventye9 zero
   ```
2. 用 `tools/start_local.cmd`（右键管理员）起客户端，点登录。
3. 观察 `server/fake_auth.log`：
   - 出现 `[70e9] 收到模块校验报告（56 字节）→ 回 op_70e9 12 字节正文（zero，n=..）`
   - **关键判据**：之后客户端有没有新动作
     - 界面推进 / 出现新状态窗口 → **成功，0x70E9 就是最后一道门**
     - 又发来新的 `0x70E9`（另一个 DLL）→ 说明它一批一批地报，继续回就行
     - 还是静默 → 换 `--seventye9 ok4`，再不行 `mirror` / `echo`

## 5. 如果四种都不行

那时说明客户端不是在等"裁决"，而是在等一个**带具体结构**的回复（比如校验通过令牌）。
下一步就去镜像里找 `0x70E9` 的下行处理函数：主代码段是明文，
但**反外挂相关代码很可能在 `.vmp0`（231KB）里** —— 那就得换思路，
比如直接让 65 张之后的那个状态推进（用服务端多发一条 `0xA5DA`/休息室消息试试）。

## 6. 真机结果（2026-11-01 补齐）

### 6.1 它到底什么时候发

`server/fake_auth.log`（2026-11-01 当天，369k 行）里 `0x70E9` 共出现 **114 次**：
`载荷=54` 76 次、`载荷=56` 38 次。每次会话通常 1~2 条，位置固定在
**表下载阶段收尾、登录界面出现之前**，例如：

```
14:14:10  消息 操作码=70e9 载荷=56 余=05000000 00000000 00000000
          433a5c57494e444f57535c73797374656d33325c75787468656d652e646c6c5f613061653262326200
          → = (5, 0, 0) + "C:/WINDOWS/system32/uxtheme.dll_a0ae2b2b"
14:14:10  消息 操作码=70e9 载荷=54 … "C:/WINDOWS/System32/MSCTF.dll_36bd5c96"
22:36:30  消息 操作码=70e9 载荷=54 … "C:/WINDOWS/System32/MSCTF.dll_36bd5c96"
```

还抓到过一条完全不同形态的（不是模块路径，而是地址 + 代码指纹）：

```
361782  载荷=54 余=00000000 00000000 00000000
        41646472 3a343534364330 2c20433a453933464339423532392c204f3a364146463638383825 00
        → "Addr:4546C0, C:E93FC9B529, O:6AFF688825"
```

⇒ 正文 = `(校验类型 u32, 保留 u32, 保留 u32) + NUL 结尾字符串`，
字符串是"被校验的对象"：合法模块给 `路径_hash`，可疑地址给 `Addr:…, C:…, O:…`。
这和客户端日志串 `send_you9_cps_CLientCheck_response` 完全对得上：
**它是 CPS 本地检查结果的上报，方向是 C→S，不是请求**。

### 6.2 回了会怎样

2026-11-01 当天 `--seventye9 zero` 全程生效，**回了 114 次**（每次 12 字节正文）：

```
[70e9] 收到模块校验报告（54 字节）→ 回 op_70e9 12 字节正文（zero，n=243..243）
```

结果：这 114 次里**没有一次引发崩溃、断连或后续步骤异常**。
当天这些会话都能正常走完 登录 → 选区 → 频道 → 机师 → 格纳库 →
（下午起）正式战/出击链路。

⇒ **`snap_11-评估.md` 里"回了必崩"这一条在 5.0.0.33 上不成立。**

### 6.3 不回会怎样

同一份日志里 2026-10-20 的早期会话（还没有 `--seventye9` 选项）是这样的：

```
14:14:10  消息 操作码=70e9 载荷=54 …
14:14:55  recv timeout (45s idle)
14:14:55  closed 127.0.0.1:61507 (存活 97.4s)
```

但那个 45s 静默**不能归因于"没回 0x70E9"**：此刻客户端正停在登录界面等人点「登录」，
服务端本来就不会再收到任何帧。所以它既不能证明"必须回"，也不能证明"不用回"。

⇒ 到 2026-11-01 为止，**`none` 与 `zero` 仍没做过 A/B 对照**。这是本文唯一还欠的实验
（见 `server/答复-三处代码与文档不一致-2026-11-01.md`）。

### 6.4 客户端有没有接收 handler

三条独立线索都指向"没有"：

1. 全镜像搜不到任何 `cmp eax,0x70E9` / `cmp r32,0x70E9` 立即数比较（0 处）；
2. `server/lounge_dispatch_table.json` 的 282 条首级分发表里没有 `70E9`；
3. `server/lounge_recv_handlers.json` 的 93 条接包 handler 里也没有。

⚠️ 但第 1 条不能单独当证据：这套分派里有大量"`cmp` 命中后顺序落下"的分支
（`0x45E4` 就是这么被漏掉的，见 `docs/HANGAR_AND_UNITS.md` §7.1.1），
所以只能说"枚举不到"，不能说"绝对没有"。真正支撑"不需要回执"的是 6.2 的实测。

### 6.5 现在的默认值

`--seventye9` 默认已改为 `none`（`tools/start_local.cmd` 也不再显式传 `zero`）。
理由不是"回了必崩"（已证伪），而是**它不需要回执，少一个变量**：
真出问题时可以先排除"回错内容"这一项。要复现历史行为加 `--seventye9 zero`。
