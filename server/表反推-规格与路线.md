### 3. 调用链（已确认到 C 代码级）

```
0x5290 回复 → FUN_00544F60(name, content, len) → FUN_00544790
   按 wstring 名字在待下载表里精确查找节点（+0x0C = 序号，+0x14 = 名字）
   命中 → 拷正文 → FUN_00A46480（UTF-8 → UTF-16）→ 为 0 时：
        switch(序号) 调各自 Load
        FUN_009AE510 = std::map::erase   ← 删掉节点才会请求下一张
```

节点布局：`+0x00/04/08` 红黑树 left/parent/right、`+0x0C` 序号、
`+0x10` wstring 对象（`+0x14` 缓冲/指针、`+0x24` size、`+0x28` cap）、`+0x2C` 颜色、`+0x2D` isNil。

## 二、运行时已经确认的事实（不必再重复验证）

1. 名字查找**是命中的**：卡住时内存里存在节点（`idx=1`，名字 24 字符完全一致）。
2. `autoexec_sv.cfg` 的节点**被 erase 了**（对照组），我们的表**一直没被 erase**。
3. 表对象的行 map **始终为 0 行** —— `Load` 没有插进任何一行。
4. **内容不是唯一变量**：把真 `autoexec.cfg` 的 10222 字节顶着 `msma_weapon_set.csv`
   的名字发过去，仍然卡住 —— 但那不是一份合法的 CSV，所以**不能据此断定"内容无所谓"**。

---

## 三、已知的坑（别再踩）

- `Load` 的返回值**恒为成功**（迭代器正常出口 `xor eax,eax`，回调恒 0），它不参与推进判断。
- 地区过滤**只跳过 `JAPAN`**，`CHINA`/`ALL`/任意值都会收。
- 报文里的"压缩标记"**不生效**，正文一律按 UTF-8 文本转 UTF-16。
- 调试器（frida / CE）一律被壳做掉；只能走 `OpenProcess + ReadProcessMemory`（需提权）。
- `VirtualQueryEx` 必须 `0x10|0x400`，只给 `VM_READ` 会静默返回 0 块（曾导致一次完全错误的结论）。
- 客户端存活率低，进程号随时会变；**任何内存补丁打完要立刻确认进程还是不是同一个**。

## 四、下一步（体力活，但方向确定）

### 阶段 1：把规格补全（纯静态，不需要客户端）

1. 对 `表规格.json` 里 `ncols_min` 偏小的表，逐个把行解析器**完整反编译**（含子解析器），
   人工核对列号 —— 用寄存器传列号（`push esi`，`esi` 在循环里递增）的地方自动抽取抓不到。
2. 把 `表绑定.md` 里 30 个低分绑定人工核对一遍（尤其是 `chara/*`、`item/*` 这一批）。
3. 产出最终契约：`表 → 文件 → 列数 → 每列类型 → 枚举取值 → 主键列`。

### 阶段 2：按客户端的请求顺序逐张打通

客户端是**串行**的：`autoexec` → `msma_weapon_set` → `msma_weapon_equipcomb` → … → 共 74 条。
所以不需要一次造 74 张，**一次只解一张**：

1. 按规格生成该表的 CSV
2. 跑一次登录，看是否出现**下一张**的 `0xF86A`
3. 通了 → 下一张；不通 → 回到该表的解析器，找"这一行为什么被拒"

`fake_auth` 的 `missing_body()` 已经支持从
`GundamOnline_CHINA_已解密/decrypted/settings/<路径>` 直接读文件，
所以**把生成的 CSV 放进那个目录就会自动被使用**，不用改服务端代码。

### 阶段 3：记录

每张表打通后把「列布局 + 枚举 + 实测通过的样例行」追加进 `表规格.md`，
形成可复现的契约清单 —— 这也是唯一能交给别人的东西。

## 五、老实说的不确定性

- `ncols_min` 是**下界**，真实列数可能更多。
- 枚举只抽到了 3 张表，其余表可能也有枚举列但用的是别的写法（查表 / 位掩码）。
- **一行数据都没插进去**这件事，目前无法区分是"行被拒"还是"`Load` 没跑"。
  阶段 2 的第一张表（`msma_weapon_set`）就是把这件事定性的地方：
  一旦生成出第一份能被接受的表，`rows(weapon_set)` 会立刻从 0 变成非 0，
  后面的表都可以照这个模板推进。
