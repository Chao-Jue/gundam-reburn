## 2. 三处必须纠正的旧结论（都会误导后续排查）

### 2.1 `0x5290` 有分派，而且不是二分树

旧文：*"`0x5290` 全镜像无立即数比较 ⇒ 分派不到"* —— **错**。
`0xAA2D50` 里除了二分树还有**稠密区间开关**：

```
0xAB099A  sub  eax, 0x5281
0xAB099F  cmp  eax, 0x21          ; 0x5281..0x52A2 共 34 个
0xAB09A2  ja   0xAD59A7           ; 越界 = 静默 error
0xAB09A8  movzx eax, byte [eax+0xAD5EF0]    ; 二级字节表
0xAB09AF  jmp  [eax*4 + 0xAD5EDC]           ; 三级 dword 表
```

`0x5290` → idx 15 → **handler `0xAB09B6`**。
整个区间只出现一个字面量 `0x5281`，所以**任何"按 4 字节立即数搜 opcode"的方法都必然漏**。
（顺带：`0xAF6080`（`vt+0x78`，旧文认定的表应答处理器）在这个 build 里**没有任何调用点，是死代码**。）

### 2.2 `0xB70350` 不是"建 `{ptr,end}` 游标"

它只有 4 条指令：

```
0xB70350  mov eax, ecx
0xB70352  mov ecx, [esp+4]
0xB70356  mov [eax], ecx        ; 单 dword setter
0xB70358  ret 4
```

真正的游标在 `on_message` **自己的栈帧**里，入口就设好了：

```
0xAA2D98  lea  eax,[edi+ebx]      ; end = 入参 ptr + len
0xAA2D9C  mov  [esp+0x1C],edi     ; → [esp+0x14] = 载荷起点
0xAA2DA0  mov  [esp+0x20],eax     ; → [esp+0x18] = end
0xAA2DA4  call 0xA5A330           ; 读 u16 opcode，游标 +2
```

而 `0xE13A` 末尾校验判的就是这两个格子（`0xAD007D cmp [esp+0x14],[esp+0x18]`）。
⇒ **客户端眼里的正文长度 = 帧层 `vt[0x54]` 传的 `len-2`，就是我们发的 817，一分不差。**

### 2.3 `FUN_00A956F0` 的失败出口有 28 处，不是 3 处

旧文按 `xor al,al` 统计 ⇒ 只看到 3 个。实际是**内联边界检查后跳同一出口**：

```
0xA95A69  pop edi
0xA95A6A  xor al,al
0xA95A6C  pop esi
0xA95A6D  ret              ← 所有失败共用
...
0xA957AF  je  0xA95A69     ← 逐字段，共 28 处
0xA956FD  ja  0xA95A69
```

⇒ **任何一个字段读越界/不合格，整个记录解析立刻返回 false，静默**。
这条正好解释了"为什么改成什么长度都没用"：失败发生在**读第二条记录的中途**，与总长度无关。

### 2.4 其它纠正

| 旧说法 | 实际 |
|---|---|
| `pump+0x10` bit0 = `CAN_SEND`（可以发下一个） | **恒 0**，连泵高速排空（66→4）时也是 0 ⇒ 不能当"泵卡住"的判据 |
| 表分派 `id 0x26`(38) 缺 case ⇒ 死锁源 | 它跳公共出口 `0x544DD7`，那里照样 `erase` + `or [pump+0x10],1` ⇒ **不是死锁源** |
| `--dl-retry`（重复 0x5290）安全 | **不安全**：实测让泵在第 23 张就停住（重复应答会破坏泵的 map 状态） |

## 4. 已定案的新事实（可直接依赖）

1. **`0xE13A` 正文 = 817，记录 = 398**，两者都对，不必再怀疑。
2. **`real_eff` 变体是错的**：它只填 `pilots_eff`，`pilots_zeon` 是 398 字节全零，
   `avatar_id = 0` ⇒ 解析器在校验第二条记录时 `return false`。
3. **把 zeon 记录也填上合法外观（`real_both`）后，客户端行为改变**：
   从"完全静默"变成 `L0:0` 退役会话、掉回登录界面。
   ⇒ 解析已通过，报文已被接受，`+0x10615` 那条链被真正走到。
4. `L0:0` 是**客户端自绘状态码**，不是协议字段（旧文已记，仍然成立）。

“全零 avatar 让解析器 return false”不成立。真正的数据相关风险在成功回调：
`FUN_004336A0` 会读取每个固定槽的 avatar，并在 `avatar_id > 0` 时查询外观表。

- `vacant_both`：两侧 `pilot_id=0`、名字空，但分别保留 EFF `avatar_id=1` /
  ZEON `avatar_id=17` 的合法默认外观；
- `real_eff_vacant`：EFF 为真实记录，ZEON 使用上述合法空槽。

`start_local.cmd` 默认已改为 `vacant_both`。这次运行的判据是能否离开“取得机师数据”并进入
