## 2. 保护模块的"阶段阶梯"（这是本次最关键的发现）

XDt 日志里的 `.last` 与内部错误码是**逐级递进**的，改好一层它就走下一层。
这让"该伪造什么"变成了可观测的闭环，而不是盲猜：

| 阶段 | 日志特征 | `.last` | 内部码 | 含义 |
|---|---|---|---|---|
| 驱动起不来 | `ERROR: STARTSERVICEERROR sys error = 4294901762`、`DLIB-DLOADER=61698` | `0xFFFF0002` | **49236** (0xC054) | `StartService` 失败 |
| （另一形态） | `DLIB-DLOADER=61697` | `0x00000005` | **49235** (0xC053) | ACCESS_DENIED |
| 伪造 StartService 后 | `DLIB=61699`，`STARTSERVICEERROR` 消失 | `0x00000002` | **49234** (0xC052) | `0x2 = ERROR_FILE_NOT_FOUND`，即打开 `\\.\CPS` 失败 |
| 再伪造设备+IOCTL | `K_DS: routine ok, code = 0`；**无任何 ERROR** | — | — | **初始化成功** |

即：**49236 → 49235 → 49234 是同一个驱动加载链的降级阶梯**，不是"没提权 vs 被防火墙拦"
（印证 `分析与绕过方案.md` §1.1 的判断）。

## 4. 抓到的驱动 `CPS.sys`（`server/CPS_extracted.sys`）

```
md5     = 34b8e3854065367c46ecf46e324a8b49
size    = 125232
Machine = 0x8664 (x64)          Subsystem = 1 (native driver)
TimeDateStamp = 2016-09-05      PDB = D:\CPS\CPS\x64\Win7Release\CPS.pdb
Sections: .text .rdata .data .pdata PAGE INIT .vmp0(0x16028) .reloc
```

导入表说明它是**反作弊自保护驱动**：

- `ObRegisterCallbacks` / `ObUnRegisterCallbacks` → 句柄保护（反杀进程、反读内存）
- `PsSetCreateProcessNotifyRoutine` / `PsSetCreateThreadNotifyRoutine` → 进程/线程监控
- `PsIsProcessBeingDebugged`、`ZwQueryInformationProcess` → 反调试
- `IoCreateSymbolicLink` / `IoCreateFile` / `IoAllocateIrp` / `IofCallDriver` → 建 `\DosDevices\CPS` 并对外发 IRP
- **`KeBugCheckEx`** → 能主动蓝屏

字符串里有 `TdProtectNameCallback` / `TdDeleteProtectNameCallback` /
`TdControlProtectName` —— 对象名保护（保护/过滤特定名字，正是"反卸载、反访问"那一套）。

**判定：路线 A（让它真加载）不可行。** 2016 年的 Win7 x64 驱动 + 自带 `.vmp0`，
在开了 VBS / CI 强制 / 易受攻击驱动阻止列表的 25H2 上加载无望；
而且就算加载成功，它是个带 `ObRegisterCallbacks` + `KeBugCheckEx` 的反作弊，
副作用不可控。**只能走路线 B。**

# 8. 2026-10-14 第三轮：三个关键根因 + 游戏主窗口起来了

本轮把「进程启动后自己退出」这件事彻底查清了，**之前的三条结论有两条是错的**。

## 8.1 根因一：「进程自己退出」其实是 frida 崩的，不是游戏

Windows 事件日志（Application Error）里每轮都有一条：

```
出错应用程序名称： GundamOnline_CHINA.exe
出错模块名称：   frida-agent.dll          <-- 崩的是 frida 自己
异常代码：       0xc0000005
错误偏移：       0x00c0919c
```

原因：`frida-agent.dll` 自己也会调用 `VirtualAlloc` / `VirtualProtect` /
`LoadLibraryA/W` / `GetProcAddress` / `CreateFileW` / `CreateThread` 这些我们 hook
的 API。回调里再去 `Process.findModuleByAddress` / `Thread.backtrace` 就会重入
agent 内部结构 -> 段错误。表现就是「游戏跑十秒左右自己退出」，极易误判成游戏或
保护模块的问题。

**修法**（已实现在 `tools/xgg_hook.js`）：

1. 启动时枚举模块，把名字含 `frida` 的都收进 `AGENT_MODS`；
2. 统一 hook 包装器 `hook()` 里加两道闸：
   - `inAgent(this.returnAddress)`：调用方在 agent 里 -> 直接放行，不记也不改；
   - `__depth > 0`：回调内部再触发的嵌套调用 -> 直接放行（frida 的 JS 回调是串行的，
     全局计数器够用）。

## 8.2 根因二：分辨率弹窗是 DPI 缩放的经典 bug，不是真的分辨率不够

探针在 `GetSystemMetrics` 的 `onEnter` 里读调用点现场（不碰被 Themida 覆盖的主节），
拿到实测值：

```
要求 = 1920 × 1080   （esi=1920, edi=1080，来自配置对象 0xbe24498 的 [+0]/[+4]）
屏幕 = 1536 × 864    （GetSystemMetrics(0/1)）
1536 < 1920  ->  jb 到 0x58f7da  ->  弹「屏幕分辨率小于要求的尺寸」
```

检查逻辑（RVA `0x58f166`，**明文 x86，未命名主节**）：

```asm
RVA 0058f166  a1 58 20 16 01   mov  eax, [0x1162058]     ; 配置对象
RVA 0058f16b  8b 30            mov  esi, [eax]           ; 要求宽度
RVA 0058f16d  8b 78 04         mov  edi, [eax+4]         ; 要求高度
RVA 0058f170  53               push ebx
RVA 0058f171  8b 1d 48 a4 ca 00 mov  ebx, [0xcaa448]     ; GetSystemMetrics
RVA 0058f177  ff d3            call ebx                  ; GetSystemMetrics(0) -> 1536
RVA 0058f179  6a 01            push 1
RVA 0058f17b  89 44 24 3c      mov  [esp+0x3c], eax      ; 存屏幕宽
RVA 0058f17f  ff d3            call ebx                  ; GetSystemMetrics(1) -> 864
RVA 0058f181  39 74 24 38      cmp  [esp+0x38], esi      ; 屏幕宽 < 要求宽 ?
RVA 0058f185  0f 82 4f 06 00 00 jb   0x98f7da               ; -> 弹框
RVA 0058f18b  3b c7            cmp  eax, edi
RVA 0058f18d  0f 82 47 06 00 00 jb   0x98f7da               ; -> 弹框
```

> 栈偏移看着对不上（写 `[esp+0x3c]`、读 `[esp+0x38]`）其实是对的：
> `GetSystemMetrics` 是 **stdcall，被调用方清栈**，`call` 返回后 caller 的 esp 比
> `push 1` 之后高 4 字节，所以 `cmp [esp+0x38]` 读到的正是刚写进去的那个宽度。

那 1920×1080 是哪来的？—— **物理显示模式**。`server/_dpi_probe.py` 实测：

| 项目 | 值 |
|---|---|
| `EnumDisplaySettings(ENUM_CURRENT)` | **1920×1080** @144Hz（游戏的要求来源） |
| `GetSystemMetrics(0/1)`（非 DPI 感知进程） | **1536×864** |
| `GetDeviceCaps(HORZRES/VERTRES)` | 1536×864 |
| 缩放比 | **1.25**（125%） |
| `IsProcessDPIAware()` | 0 |
| `SetProcessDPIAware()` 之后 | 1920×1080 ✓ |

1920/1.25 = 1536、1080/1.25 = 864。**这是老游戏在高 DPI 缩放下的经典 bug**，
和"分辨率不够"毫无关系（弹窗文案里写的 1024×768 也是硬编码的假信息）。

**修法（不需要改系统缩放、不需要改 exe）**：让游戏进程带上 `HIGHDPIAWARE` 兼容层。

```
__COMPAT_LAYER=HIGHDPIAWARE
```

实测加上之后 `GetSystemMetrics(0/1)` 直接变成 1920×1080、`IsProcessDPIAware()=1`，
分辨率检查通过。`tools/run_hooked.py` 已默认在 spawn 时注入这个环境变量
（`--no-dpi-fix` 可关掉做对照）。

## 8.3 根因三：Themida 反虚拟机弹窗 = 壳在扫 API 入口字节，发现被打了跳板

现象：**不带 frida 稳定通过（5/5），带 frida 完整脚本 5/6 触发**，
弹 `Themida / Sorry, this application cannot run under a Virtual Machine`，
调用点 `GundamOnline_CHINA.exe+0xe899c7`（`ohjicybf` 节，用未公开的
`MessageBoxTimeoutA` 弹），然后自杀。

而且触发的那一瞬间，日志里**一条 API 事件都没有**——纯属对内存里代码的扫描。

二分实测（每组 3 次，用 `--skip-dlls` / `--skip-names`）：

| 关掉哪一部分 hook | Themida 触发 |
|---|---|
| 空脚本（不装任何 hook） | **0/3** |
| 完整脚本（45 个 hook） | 5/6 |
| `--full` 基线 | 2/3 |
| `ntdll!KiUserExceptionDispatcher` | **0/3** ← 在检查名单里 |
| `user32!MessageBoxTimeoutA/W` | **0/3** ← 在检查名单里 |
| `ntdll!LdrLoadDll` | 2/3 |

| `gdi32` / `ws2_32` 全部 | 3/3（无影响，也不背锅） |

## 8.5 IOCTL 协议新发现（`0x222055` 的返回值是指针）

实测入参结构像"驱动读写原语"：

```
0x222055  in 20 字节 = { u32 size; u32 op; u32 x; u32 len; u32 addr }
样本: 14000000 03000000 00000000 08000000 44fc1a00
      size=20    op=3      x=0       len=8      addr=0x1afc44
```

另一笔 `op=3, len=6, addr=0x73db005`，读到的字节是
`8b10 8bc8 8b4238 ffe0` = `mov edx,[eax]; mov ecx,eax; mov eax,[edx+38]; jmp eax`
—— 模块在**读代码字节做完整性校验**。

关键：`0x222055` 的 **8 字节输出被模块当作指针解引用**。之前只对 `0x222059`
（模块从来不调）写版本号，`0x222055` 的输出从来没填过，模块拿到未初始化数据
-> 在自映射代码区 `+0x28d9f` 处 `mov dword ptr [ecx+0x18], ebx` 用坏指针写
-> `0xC0000005`。改成回一个合法的用户态零缓冲地址后，崩溃点从 `+0x28d9f` 移到
`+0x28d71`，并有 1/8 的轮次完全活下来。

## 8.6 还没解决：保护模块自映射区里的概率性崩溃

```
出错模块名称： unknown        异常代码： 0xc0000005
错误偏移：  0x07408d71 / 0x07418d71 / 0x07428d9f / ...
            = (该轮 320KB r-x 匿名区基址) + 0x28d71 / 0x28d9f
```

- 崩溃代码在模块**动态分配的一块 320KB `r-x` 匿名区**里（`tools/xgg_hook.js` 的
  `dumpRange()` 会在发现"线程入口不在任何模块里"时整块 dump 下来，
  产物 `server/cps_dump/region_*.bin`）。
- 同一块区里 `+0x2a4b0` 是**正常的 C++ 代码**（`sub esp,8; call ...; mov edx,[eax];
  mov edx,[edx+0x3c]; call edx; cmp eax,1`），说明是模块自映射/解密的代码。
- 崩溃是**概率性的**：8 轮里 1 轮完全活过窗口，其余 5~13 秒挂掉。
  怀疑是模块通过驱动做自校验（上面那笔读代码字节的 IOCTL）后，
  按校验结果走了不同分支；我们用假数据喂它，时序/数据不同就走到坏分支。
- 也可能与 VMProtect 的防篡改有关（崩溃点周围的字节明显是混淆过的）。
