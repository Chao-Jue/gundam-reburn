主要实现为 `server/battle_entities.py`、`server/local_battle.py`、`server/hangar_experiment.py`。均属于本地实验路径，保持普通模式隔离。

3. E650 若包含基地实体 ID，验证己方与合法范围，记录选择；640D 使用基地实体数组表示等待部署的人数关系。
4. 部署期限结束，下发玩家 7621、86B2 成功结果、640D 零秒与 3E23 正式战进度。
5. 战斗脚本 CB97（game_resume_enter）收到空正文 8297（game_resume）应答。

这条链已经过合成客户端加密 TCP 冒烟；真实客户端中“点击基地后发出指定基地 E650”的链路尚未证实。已见日志只有初始无点位和自动 post=0 两次 E650，因此不能根据合成测试宣称出击计数正常。

| Opcode | 当前客户端含义 | 结构要点 |
|---|---|---|
| E650 | 机体/地点选择 | `<IIIBBH>`：机体索引、post、spot、ship ride、msma ride、基地实体 ID；无选择 sentinel 为 FFFFFFFF/FFFF |

| CB97 / 8297 | 恢复游戏请求/应答 | 请求含 initial u32、script_thread u8、至多 64 字节 NUL 终止脚本；应答为空 |

战斗描述读取器 A5E300 为 175B wire / 200B native，不能替换成 299B 格纳库记录。快照 A5EA80 为 39B wire / 44B native，格式 `<4H7H2BH3B2HIH>`；位置按 pos_factor=100 编码。当前速度、姿态及若干战斗状态为零占位，不是完整原版参数。568A 是快照更新，不能作为创建实体包。Opcode 必须由实际分支运算核验，近邻处理函数/不完整枚举脚本曾误判 6D8F、759C。

## 基地图标、颜色、字母、点击是多条条件

- 角色表第 7 列 EX_STRONGHOLD=6 与第 35 列地图分类 STRONGHOLD=22 分别负责角色与标记分类。只改图片分类不创建世界实体。
- 原生创建链 717D → AF47C0 → A554D0 → 4AB220 → 地图挂接 4546C0。基地用实体 100..103、实验 msma=777201、model=601030301；玩家实体 1、msma=777001、model=101010101。不可混用这些 ID。
- actor+C8 为字母序号；0/1 对应各方第一个、第二个基地。actor+35C 指向组件，其 +D2 bit0 为出击许可，来自 appear 的 is_respawn。
- 配色注册函数 9EF6A0 会附加 `wnd_`。必须使用 `wnd_eff_ui_color` 与 `wnd_zeon_ui_color`，四个值为 ARGB。此前未带前缀的配置被忽略，导致灰色。当前蓝红值为实验选择，不声称原版配色。
- 默认配色可读于 UI 对象 +90/+8C；默认值曾为零。满血与阵营并不自动保证颜色有效。
- 点击还受选择阶段剩余时间、机体就绪和阵营限制。早期长时间调试后剩余时间已为零，临时重新开放 120 秒后用户确认可选择。
- 基地不得使用玩家 world/pilot。当前用 0/0 的空归属；44E120 所用成员查找已作原生测试。此前复用玩家身份使姓名落在建筑上。

出击数读取链 885470 → 8852F0：基地控件 +118 保存实体 ID，+11C=0 时匹配 game+24908 每条 8B 选择记录的 +2（stronghold entity）；类型 1/2 分别匹配 +4 post / +6 spot。640D 最后一组基地 ID 数组是相关数据，但当前仍缺真实点击请求闭环证据。

## 位置与镜头：尚未确认的根因

`reference/odessa_home_bases.json` 来源为任务 30110130 的双方 pop 标记，当前场景使用 30110100。四个 pop 是出击锚点，不能直接视为固定建筑中心，更不能宣称恢复 A/B/C-X/Y/Z 完整布局。当前基地不受玩家式落地修正；用锚点放建筑会悬空或埋地。

模型 BAM_0601_0303_01 的静态包围盒约为 X[-680,680]、Y[0,830]、Z[-1130,1130] cm，仅证明模型尺寸。源任务还含 GroupStronghold_ship 的模板触发器，但尚未证明其变换就是当前变体的基地中心。下一步须分离基地中心、玩家出击点及地形高度；不能统一把高度改零。

最新运行探针显示相机 mode=2（CEventViewControl），event_active=0，保存的 previous_mode 也为 2；mode=3 的 TPS 控件存在。这提示镜头生命周期可能未收尾，但还没有证明它是吉姆不可见的唯一原因。模型表实验行仅 32 列，多数值为 1，而 53FA30 还读取更后面的列，战斗模型/镜头/碰撞参数不完整也是待查项。

原始脚本 `default_start.nut`：换地图 → 初始化本地角色 → requestMsList → 开场动画/Cam.startEvent → openMsSelect/等待结束 → Cam.endEvent → initBattle → 等待 isCreateSelf → sendGameEnter。`default_respawn.nut` 也等待实体创建后再 Cam.endEvent。应沿脚本和原生状态核查，不能仅强制切 TPS 掩盖缺失初始化。

最后一次临时 TPS 切换实验没有生成结果文件，之后客户端消失且附近有 0x388C 记录。用户指出很可能已到战场结束时间而返回大厅。时间关系不能证明镜头调用导致退出，也未确认此次一定是崩溃；后续需同时记录战场计时、阶段切换和进程存活。

## 调试经验与接续顺序

1. 先记录 PID、时间和阶段；重启、UAC 等待、回大厅后读取不到演员，不等于战斗创建失败。只读探针保存 PID 和阶段，避免不同进程快照混合推断。
2. 区分内存临时实验与重启后网络落地。手工补字段能点选只说明条件成立，不代表协议生成正确。
3. 先核对真实 E650 发送和选择记录，再改计数显示；不以服务端伪造点击请求通过冒烟替代 UI 请求。
4. 对玩家不可见，先只读核查 self 引用、模型更新状态、相机所有者与脚本阶段，再设计可失败的复现测试；暂不重复未完成的强制镜头切换。
5. 基地位置另按资源变体与地形核验，保留原始 pop 坐标来源。图标正常不证明建筑实体布局正确。
6. 保持本地运行资料与发布源码分离，不上传客户端、解码资产、转储、日志、账号及 saved_*。当前工作树有大量既有和并行改动，不得整体清理或覆盖。
