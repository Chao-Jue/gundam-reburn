## 2. 已确认的格式约定（来自本机反汇编，硬证据）

| 项 | 值 | 证据 |
|---|---|---|
| 记录线长 | **398B**（内存槽 424） | 445 条指令逐项相加 |
| `0xE13A` 正文 | **817B**（bmg 为空） | alloc 1253 精确吻合 |
| `name` | **UTF-8，定长 25B，无 NUL 检查** | 参考文档 §3.3 + 反汇编 |
| `comment` / `clan_name` / `cupteam_name` | 116B / 31B / 31B 定长串 | 同上 |

| **`troops` 线上 0 基** | **0 = 秩序/eff，1 = 抵抗/zeon** | 参考文档 §3.11 规则③ |

## 3. 还缺两块，都需要"客户端内部视角"

| 缺口 | 现状 | 为什么必须观测 |
|---|---|---|
| **空列表流程** | 两记录全零发送后，客户端**不推进也不报错**（无 AV、无 error、无断连） | 无法从服务端区分「解析成功但回调没生效」和「压根没分发到 handler」 |
| **有角色流程** | 只要"id+名字"同时存在，客户端 **0.0 秒断连**，`user/exrep.log` 记录 `0xc0000005`（AV） | 崩在客户端堆上，不知道是哪条指令、需要什么数据 |

### 3.1 最省事的观测方案（不改客户端代码/数据）

**A. frida 只装异常处理器**（VEH）——`Process.setExceptionHandler`，
不写任何代码字节、不改 vtable，崩时取 `ExceptionAddress/CauseAddress` + `Thread.backtrace`。
⇒ 直接拿到 AV 的 EIP，回离线就能定位到具体函数。

**B. 抓客户端自己的解析日志** —— 成功分支 `0xAD009C` 之后有一大段格式化日志
（`')->_proto_lounge_client::recv_pilot_list_get_r( '` / `'result='` / `'pilots_eff={'` …），
最终走全局 logger（对象 `0x108D1D4`，vtable `0xE6364C`，`vt+8 = 0xBD2860`）。
**待查**：这个 logger 的最终出口是不是 `OutputDebugStringW`（镜像里确实 import 了它）。
如果是，用一个 **DBWIN_BUFFER 旁听器**（完全在进程外、零注入）就能白拿客户端眼里每条记录的内容。

## 4. ★ 拿到"完全正确"的最快路径

**新建流程就是标准答案**：一旦空列表能过，客户端会进「新建机师」界面；
用户在里面捏一个机师 → 客户端发 `0xFD3E send_pilot_create`（159B 记录）
→ **那条报文里的 `avatar` 就是客户端自己编码出来的真值**。

⇒ 我们不需要猜 `clothes/hair/voice` 的编码方式，**照抄客户端自己发上来的那份**即可。
这也是 `pilot_form.csv` 之外唯一能确认"编码口径"的证据。

所以顺序必须是：

1. **先让空列表通过** → 进新建界面；
2. 用户捏一个机师 → 抓到 `0xFD3E` → 得到权威的 avatar 编码；
3. 用这份编码 + `pilot_form.csv` 的合法取值，构造"有角色"的列表 → 回灌验证。

## 5. 当前 `start_local.cmd` 的变体

```
--pilot-variants real_eff,real_both,zero --probe-gap 10.0
```

- `real_eff`：联邦侧一条**外观全合法**的记录（avatar 来自真表），zeon 侧空
- `real_both`：两侧都合法（avatar_id 1 和 2）
- `zero`：空列表对照

如果 `real_eff` 不再 AV，说明 **AV 就是外观字段非法值引起的**，那第 3 节的两块缺口一次解决一半。
