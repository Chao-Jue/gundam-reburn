# 网络层定位（2026-10-17）

> 目标：把客户端"发包—收包"这条链在解包镜像里钉死，为后面写服务端做准备。
> 本文所有地址都是**运行时绝对 VA**（模块基址 `0x400000`）。
> ⚠️ 踩过的坑见最后一节，务必先读。

## 0. 一句话结论

登录时客户端走的是**自己写的 socket 类**，不是 WinINet/WS2_32 的高层封装：
`Socket::Send` → 环形缓冲 → `FlushSendBuffer` → `send()`。
16 字节登录包就是从这里出去的。接收侧对称：`Socket::OnRead` → `Socket::Recv` → 上层解析。

## 1. 精确调用链（已逐帧校验为真实 `call` 返回点）

发送（2026-10-17 13:06:21 实测，14 帧）:

```
send()                              来自 0xbfd2f2  call 0x76587630
 └ 0xbfd2e0  send 薄包装（push 0; push len; push buf; push sock; call send; ret）
   └ 0xc03de4  Socket::Send(buf, len, pOut)
     └ 0xbf9453  Socket::FlushSendBuffer()   ← 从环形缓冲取数据
       └ 0xbf9b6e ... Socket 状态机（这里另有一次 len=0 的 send）
```

接收（静态推导，`recv` 包装只有一个调用者）:

```
recv()  来自 0xc03d35   call 0xbfd300（recv 薄包装）
 └ 0xc03d10  Socket::Recv(buf, len)
   └ 0xbf8a54  Socket::OnRead()   ← 先向 [this+0x4c] 申请 0x10000 字节缓冲再 Recv
```

`connect` 链（同为实测，12 帧全部校验通过）:

```
connect()  来自 0xbfcfb1
 └ 0xc03b84 → 0xbf9993 → 0xbfcd22 → 0xbeb477 → 0xb2b713
   → 0xbf5e83 → 0xbf6337 → 0xa4f30f → 0x9a4355 → 0x9e20ef → 0x9837da
```

## 2. Socket 类字段（tc = this）

| 偏移 | 含义 | 依据 |
|---|---|---|
| `+0x48` | `SOCKET` 句柄（int） | `Send`/`Recv` 都 `mov eax,[esi+0x48]` 后 push 给 send/recv；`< 0` 视为无效 |
| `+0x4c` | 收包缓冲提供者（虚表对象，`[obj+0x78]` 是 `Alloc(size)`，调用后把 0x10000 字节指针给它） | `0xbf8a26` 起 |
| `+0x58` | 事件/日志用的 id | `0xbf9b4a` 起 |
| `+0xc0` | 连接状态，`==1` 时 `IsConnected()` 返回 true | `0xbf89f0` |
| `+0x1c8` | 单次 flush 的最大字节数（flush 时与待发量取小） | `0xbf9433` / `0xbf9444` |
| `+0x1f8` | **发送环形缓冲**（见下） | `lea edi,[esi+0x1f8]` |
| `+0x234` / `+0x238` | 收包统计（已收/已处理） | `0xbf8820` 起 |
| `+0x258` | 状态机状态（失败后置 4） | `0xbf9b86` |

发送环形缓冲（`this = Socket+0x1f8`，即 `RingBuffer`）:

| 偏移 | 含义（**推断**，待运行时确认） |
|---|---|
| `+8` | 缓冲区基址 |
| `+0xc` | 读位置 readPos |
| `+0x10` | 写位置 writePos |
| `+0x14` | 上限/容量 limit |
| `+0x1c` | 历史最高水位 |

`FlushSendBuffer` 里 `ebp = [this+0x208] - [this+0x204]` 就是"待发字节数"，
发送指针 = `[ring+0x8] + [ring+0xc]` —— 和上面的读/写位置解释自洽。

## 3. 关键函数表

| VA | 名称（推定） | 说明 |
|---|---|---|
| `0xbfd2e0` | `send` 薄包装 | `push 0; push len; push buf; push sock; call send; ret` |
| `0xbfd300` | `recv` 薄包装 | 同型 |
| `0xbfd320` | `WSARecv` 薄包装 | 供异步路径用 |
| `0xc03dc0` | `Socket::Send(buf,len,pOut)` | `ret 0xc` |
| `0xc03d10` | `Socket::Recv(buf,len)` | `ret 8` |
| `0xbf9410` | `FlushSendBuffer()` | 环形缓冲 → send，返回 bool |
| `0xbf8a00` | `Socket::OnRead()` | 收包泵，含 SEH |
| `0xc034f0` | `RingBuffer::Write(data,len)` | **所有待发字节的唯一入口**；`push len; push src; push dst; call memcpy` |
| `0xc120e0` | `memcpy` | `RingBuffer::Write` 里调用 |
| `0xbf87f0` | `RingBuffer::GetAvailable()` | `[+0x210]-[+0x208]+[+0x204]` 或 `[+0x20c]` 版本 |
| `0xbf87e0` | 取 `RingBuffer` 的 thunk | `add ecx,0x1f8; jmp 0xc034f0` |
| `0xbf1640` / `0xbf1560` | 日志/事件上报 | 错误码 `0x3b` / `0x3c` / `0x9` 从这里出去 |

`RingBuffer::Write` 的调用者集中在 `0xbd3xxx`–`0xbd8xxx` 一大片
（`0xbd31c0 0xbd3450 0xbd3b40 ... 0xbd8xxx`），形态是"按类型逐个 write"的
序列化器族（`WriteU8/WriteU16/WriteBytes` 之类），**下一步从这里往上找登录包构造函数**。

## 4. 16 字节登录包实测样本（全部为 `Socket::Send` 层）

| 时间 | 值 |
|---|---|
| 12:50:59 | `4ffa6e6bdfddb8ed774a044385f4aa0c` **(A)** |
| 12:52:36 | `b3bcbdec6e235574c818aa4cfa314b05` **(B)** |
| 12:53:09 | `739f430e097879b1dba28ecf6266bd06` **(C)** |
| 12:54:53 | `4ffa6e6bdfddb8ed774a044385f4aa0c` **(A)** |
| 12:56:46 | `b3bcbdec6e235574c818aa4cfa314b05` **(B)** |
| 13:02:57 | `3fe696e6b3b452d723136aa81856d60c` **(D)** |
| 13:06:21 | `4ffa6e6bdfddb8ed774a044385f4aa0c` **(A)** |

序列：`A B C A B D A` —— **前 5 个严格周期 3**（第 6 个 D 出现在恰好补录成功后，
可能是输入状态不同）。周期 3 是强线索，说明密文里混入了**只有 3 个取值的量**
（计数器 mod 3 / 轮换密钥下标 / 三次重试的阶段），而不是随机数或时间戳。
**必须做单变量实验确认**（连续 3 次相同账号密码）。

紧邻 16 字节包之前还有一次 `send(len=0)`（栈在 `0xbf9b6e`），
即"先空发包 → 再发 16 字节"，服务端模拟时要接受这个空包。

## 5. ⚠️ 踩过的坑：回溯地址是"模块内偏移"，不是 VA

`Thread.backtrace` + 自定义符号化打出的是 `GundamOnline_CHINA.exe+0x7fd2f7`，
这里 `0x7fd2f7` 是**相对基址的偏移**，真实 VA = `0x400000 + 0x7fd2f7 = 0xbfd2f7`。
我一开始直接拿偏移当 VA 去反汇编，得到一堆"看似合理但全错"的代码，绕了两轮。

**验证方法**（现已脚本化）：对每一帧，检查该地址往前 2–7 字节是否存在一条
`call rel32` 且恰好在此地址结束。14/14 帧全通过才说明回溯可信。
校验脚本见 `tools/xref.py` 的思路 + 会话里的一次性脚本。
