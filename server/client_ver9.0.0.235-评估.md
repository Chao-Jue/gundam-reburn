## 一、先纠正"自己写了个 exe 绕过反作弊"这个说法

`msgo_tools/tools/` 里只有：

```
182脱壳版-GundamOnline_CHINA.exe   14,774,272
235脱壳版-GundamOnline_CHINA.exe   14,870,016
放游戏根目录管理员启动.cmd          ← 只是 start /wait "GundamOnline_CHINA.exe" ./data
日服国服通用解包工具.zip            ← 资源解包（FPMF key 表），与反作弊无关
```

那个 cmd **没有任何注入、hook、patch、驱动卸载**，它就是 `start /wait /d "%~dp0" GundamOnline_CHINA.exe ./data`。

**真正的机制不是"对抗反作弊"，是"让反作弊没机会运行"**：

| 证据 | 数据 |
|---|---|
| 导入表只有 26 个 DLL | advapi32 / comctl32 / dinput8 / dsound / gdi32 / IPHLPAPI / kernel32 / oleaut32 / psapi / shell32 / shlwapi / user32 / winhttp / wininet / winmm / ws2_32 / d3d9 / d3dx9_42 / dbghelp / LIBCURL / libogg / libtheora / libvorbis / ole32 / kernel32 / KernelBase |
| 反作弊 DLL | **一个都没有**（无 ACOPCShell / XIGNCODE / nProtect / GameGuard） |
| `VMProtect` 字符串 212 处 | 全落在 `.vmp0` 死数据里（与 snap_11 的"静态死数据"结论一致），未被任何代码引用 |
| 入口点 | `0x8CC5DD`，在 `.text` 里（不是壳的 `.loader`） |
| 导入目录 | `0x12857D6`，只 0x21C 字节，物理位置在 `.SCY` 段 ⇒ **是重建出来的**，不是原壳的 |

⇒ 做法就是标准脱壳三步：**dump 运行镜像 → 把入口换回真 OEP → 重建只含系统 DLL 的导入表**。
壳（`.vmp0` / `.SCY` / `.loader`）作为死段被原样带着走，不参与执行。

## 二、★ 重要发现：`235脱壳版` 就是 snap_11 分析的那个 build

| 项 | snap_11 的 memraw | 235脱壳版 |
|---|---|---|
| TimeDateStamp | 2022-02-14 | **2022-02-14** |
| SizeOfImage | 0x1298000 | **0x1298000** |
| 节表 | `.text 0x965000 / .rdata 0x2AD000 / .data 0x27F000 / .vmp0 0xE95000 / .imports 0xECE000 / .SCY 0x1285000 / .loader 0x1288000` | **逐项相同** |

两处函数签名独立验证通过：

```
0x8B4580  83 EC 4C  53  8B 5C 24 54  81 FB 80 00 00 00   ← SPN「按密钥长度分 0x80/0xC0/0x100」
0x8B7C10  83 EC 28  56  8B F1                             ← recv_pump（snap_11 replay.md 自检值就是 83ec2856）
```

### 它把 snap_11 的头号阻塞解决了

逐页比对 `.text`（2405 页）：

```
完全一致        2149 页 (89.4%)
脱壳版有 / memraw 全零   249 页   ← 正是 snap_11 报的「249 页空页 / 10.4%」
memraw 有 / 脱壳版全零     0 页
两边都有但内容不同          7 页   （待查，可能是壳打的补丁或运行时改写）
```

⇒ snap_11 反复强调的"代码段 10.4% 空页 ⇒ 所有静态扫描都可能漏命中"，
在这份 exe 上**不存在**。他们卡了多轮的 `0xE12B6C` 引用为零、opcode→slot 映射拿不到，
现在可以直接在这份 exe 上重扫。

⚠️ 但注意：**snap_11 里那些 `0xb3xxxx–0xb6xxxx` 的 case 地址不是这个 build 的**
（235 的 `.text` 只到 0x966000，那些地址落在 `.rdata`）。
他们自己写过"服务端注释里的客户端地址是从另一个版本逆出来的"——就是这件事。
我在我们自己的 5.0.0.33 镜像里也验了：`0xB4F95D` 是乱码，`cmp eax,0x9397` 只出现一次（`0xABC347`）。
⇒ 那批 case 地址属于**第三个 build**，谁都不能直接用。

## 三、对我们的价值（v5.0.0.33）

### 1. 最大启示：这条"脱壳成独立 exe"的路，可行性被证明了

如果 5.0.0.33 也做成脱壳版，当前**三条硬约束同时消失**：

| 现在 | 脱壳后 |
|---|---|
| 启动期概率性崩溃（`c0000005`，崩在 CPS 解压出来的 `r-x` 区） | 没有 CPS 那段代码，崩溃源消失 |
| `0x70E9` 报 `Addr:ACFE76` 代码篡改 ⇒ 禁止 inline hook | 没有检测方，hook 安全 |
| 探针只能只读（`OpenProcess`+`ReadProcessMemory`），**不能直接喂解析器** | 可以随便改内存/打补丁/单步 |

第三条是重点：我们卡在"固定基地标记不创建"这种**纯客户端时序/分支**问题上，
只读探针只能看结果、看不到判定输入。能改内存就能直接把 `DAT_01161F90+0x394` 的控件建出来试。

**成本与前提**：
- 我们的镜像磁盘态是 **94% 明文 + 6% 加密**（`server/img_dump` 在 `0xB4F95D` 处就是乱码），
  所以**不能纯静态重建**，必须先让客户端跑起来、按页 dump 运行镜像、再把加密页换成明文。
- 找回真 OEP：我们现在 EP=`0xEED000` 在壳节 `esllbfpk` 里，脱壳版应该换成 `.text` 内的地址。
- 重建 IAT：snap_11 的 `02_UNPACK_REPORT/scripts/build_imports.py` 是现成方法（505 槽位 / 469 解析）。

### 2. `235脱壳版` 可以当"对照本"

同源代码、不同年份编译（2017 vs 2022），**字节相同的函数可直接移植**。
已验证一例：我们 `0xAB099A` 的 `sub eax,0x5281; cmp eax,0x21` 在 235 里也存在（`0xB601A8`）。
对 `0xA9xxxx`/`0xAAxxxx` 那批解析器尤其有用——235 侧无壳、IDA 直接能读。

**不能照搬**：协议不同（机师列表 845 vs 我们 817；`0x063E` 51725 vs 我们 29514），
派发结构也不同（235 是 route2 跳表，我们是 262 条二分表）。

### 3. 别直接运行这两个 exe

来源不明；需要完整 `data/` 目录与能连的服务端；且不是我们的目标版本。
分析可以，执行没有收益。

## 四、那个 3.4 GB 转储包

`9.0.0.235内存转储(角色创建页面)/snap_createrole/` 是同一批人对 **235 在角色创建页面**做的分析包：
`02_pe/`（118 个模块镜像）、`03_protocol/opcode_table.csv`（2095 行 route2 跳表，**名字全空**）、
`08_structs/`（1836 个 vtable）、`05_crypto/verdict.md`。

`05_crypto/verdict.md` 自己写着：堆区熵中位数 2.14，"**本轮没有拿到可确认的收发帧**"。
⇒ **这一轮比 snap_11 还浅**，没有可用的协议语义。

对我们当前卡点（固定基地图标/点选）**没有直接帮助**——角色创建页面不涉及战术地图标记。

## 五、建议

1. **P0 不变**：固定基地模型/标记（当前唯一阻塞，这批材料帮不上）。
2. **P1（新增，价值最高）**：评估"给 5.0.0.33 做脱壳版"。
   第一步只要验证一件事：**活进程里能否把磁盘那 6% 加密页 dump 成明文**。
   能，则整条 CPS 线可以退役；不能，就继续现状。
3. 235 的 `opcode_table.csv` 与 `snap_11` 的 slot 表**不要拿来推我们的地址**——
   至少三个 build 的地址被混在一起过（235 / 182 / 第三个），这是他们最大的坑。
