### 为什么第一次"点了没反应"

不是回复格式的问题，是**请求根本没进 handler**。`fake_auth` 分发前有一道闸门：

```python
elif args.login_seq and iter_type0(plain) and any(
        op in HALL_OPS or op in HALL_NO_REPLY_OPS for op, _rest in iter_type0(plain)):
```

一帧里只要没有 `HALL_OPS` 的 opcode，**整帧被静默丢弃**，连"未知/未实现"都不打。
修法：把 `0x550A / 0xA28F / 0x34AB` 加进 `HALL_OPS`。

## 十、原地刷新：0x45E4 正文必须是 17 字节（2026-11-01 20:23 定案）

### 结论

```text
0x45E4 msma_weapon_unlock_r 正文 = 17B
  result    i32  4
  uniqid_ms u64  8
  item_id   u32  4
  db_index  s8   1
```

回这 17 字节 → 客户端当场把该武器标成已解锁，**不用重登**。实测 20:23:40 一次点击：

```
[hangar] 武器解锁 新增 item=777107 uniqid=777000000001 db_index=5
[hall]   收到 0x550a，回占位 0x45e4 bodylen=17
```

### 之前 34B 为什么无效

上一版猜的是 `result i32 | id u32 | 0 u64 | uniqid u64 | item_id u32 | db_index u32 | u8 | u8`。
多了一个 `id u32`，于是**整条链错位一格**：客户端把 `item_id` 读成 `uniqid_ms`、
把 `uniqid` 低 32 位读成 `item_id`（→ 3905886721，本地表里没有），
末尾还多 2 字节触发结尾校验，直接静默走 `error(0x110,1)`。

### 推导过程（三个独立来源互相印证）

**① 逐字段对宽度** —— 处理器 `0xAAE0B5` 的读取序列，每条都能对上原语：

| 地址 | 调用 | 宽度 |
|---|---|---|
| `0xAAE0FD` | `0xA5A270 claim_u32` + `0xA5A310 read_u32` | 4 |
| `0xAAE134` | `0xA94620 claim 8` + `0xA5D7C0 read_u64` | 8 |
| `0xAAE174` | `0xA5A270 claim_u32` + `0xA5A310 read_u32` | 4 |
| `0xAAE198` | `0xA5D400 claim 1` + `0xA5A360 read_u8` | 1 |

原语语义（这次逐个反汇编确认，不靠猜）：

| 地址 | 语义 |
|---|---|
| `0xA5A270` | `claim_u32(dst,&p)` thiscall，`*dst=p; p+=4; ret 4` |
| `0xA5A310` | `read_u32(dst,&p)` cdecl，边界检查后 `*dst=*p; p+=4` |
| `0xA94620` | `claim 8(dst,&p)`，`p+=8; ret 4` |
| `0xA5D7C0` | `read_u64(dst,&p)`，写 8 字节 |
| `0xA5D400` | `claim 1(dst,&p)`，`p+=1` |
| `0xA5A360` | `read_u8(dst,&p)` |
| `0xA63160` | 追加**有符号单字节**（`movsx`）⇒ `db_index` 是 s8 |

**② 长度自证** —— `0xAAE0D1` 是 `push 0x11; call session->vt[0x78]`。
这个方法是"申请定长正文"，四个 send 函数用的是同一个槽：
`0x550A/0x34AB/0xA28F` 正文 20B → `push 0x16=22`；`0x2E33` 正文 16B → `push 0x12=18`。
所以 `0x11=17` 就是正文长度，与字段和完全一致。

**③ 结尾校验** —— `0xAAE1BC`：
```
mov eax,[esp+0x14]
cmp eax,[esp+0x18]
jne → [esi] vt[0x64](0x110, 1) → 清理返回
```
游标必须**恰好等于** end。多一字节少一字节都会被静默丢掉，所以长度必须精确到 17。

### 命中回调

读完 4 个字段后 `0xAAE336–0xAAE34B` 组装 5 个参数调 `vt[0x2c4]`：

### 分发表里的一个坑

`server/lounge_dispatch_table.json` 里 `45E4 → 00AD5E25`（默认分支），是**误标**。
真实分派在 `0xAAE07D` 起的二级比较链：

```
cmp eax,0x48A4 ; jg … ; je 0xAAEAF9
cmp eax,0x4632 ; jg … ; je 0xAAE54F
cmp eax,0x44D4 ; je 0xAAE367
cmp eax,0x45E4 ; jne 0xAD59A7
        ↓ 顺序落到
    0xAAE0B5  ← handler
```

`0xAAE0B5` **没有任何 jmp/jcc 指向它**（搜索跳转目标得 0 处），
所以"按跳转目标找 handler"这种办法对这类顺序落下的分支必然漏。
判断某个 opcode 有没有处理器，要看这些 `cmp eax,imm` 链，不能只看首级二分表。
