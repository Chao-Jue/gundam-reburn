# 5.0.0.33 脱壳可行性评估（2026-11-01）

> 触发问题：235 那边能做出「脱壳版 exe」直接跑，我们能不能对自己的 5.0.0.33 做同样的事？
> 本文全部结论来自磁盘文件与 `server/img_dump/main_GundamOnline_CHINA.exe`（运行时镜像）的逐字节比对。

---

## 0. 一句话结论

**脱壳对我们没有意义 —— 这个客户端已经是"脱好的"了。**
唯一没解的两块（`.vmp0` 233 KB、主段里 1 MB 高熵块）在**运行时也一字节没变**，
dump 不到任何新内容；而壳自身的明文我们早就有了。

⚠️ **更正**：上一轮我说"脱壳后启动崩溃 / `0x70E9` 篡改告警 / 禁止 hook 三条约束同时消失"——
**这是错的**。CPS 不在壳里，是游戏明文代码自己 `LoadLibraryW` 起来的（证据见 §2.3）。

**但这次顺手挖到一个比脱壳值钱得多的东西：客户端自带 `cpsoff` 开关，能整个跳过 ACOPCShell**（见 §4）。

---

## 1. 实测：磁盘 vs 运行时镜像

`launcher/.../GundamOnline_CHINA.exe`（15,659,840 B）vs `server/img_dump/main_GundamOnline_CHINA.exe`（15,654,912 B）

| 区段 | 大小 | 差异字节 | 比例 | 判读 |
|---|---|---|---|---|
| 主段 `0x1000–0xB48000` | 11.8 MB | 10,852 | **0.09%** | 磁盘即明文，差异是 IAT/补丁 |
| **`0xB48000–0xC4A000`** | 1.0 MB | **0** | **0.00%** | 熵 7.94，**运行时完全没解** |
| `0xC4A000–0xE0C000` | 1.8 MB | 18,275 | 0.99% | 明文 + 补丁 |
| `ohjicybf`（壳载荷） | 667 KB | **319,914** | **47.92%** | 壳在这自解包 —— **我们已有解密结果** |
| `.vmp0` | 233 KB | **0** | **0.00%** | 熵 7.889，运行时原封不动 |
| `.idata` | 4 KB | 8 | 0.20% | IAT 被填 |
| `esllbfpk`（入口桩） | 4 KB | 1 | 0.02% | 自改 1 字节（`int3`→`0x00`） |

**这张表就是答案**：真正"加密"的两块，运行时与磁盘**逐字节相同** ⇒ 它们不是"等运行时解密"的东西，
dump 内存拿不到任何新东西。反过来，唯一被解密的是壳自己（`ohjicybf`，48% 变化），
而那份解密结果**我们早在 10 月 17 日就落盘了**（`server/img_dump/`）。

## 2. 为什么"做成独立 exe"的额外收益 ≈ 0

### 2.1 没有新东西可读

- 1 MB 高熵块：全镜像只有 **29 处直接 `call`、20 处 `jmp`** 落入其中（对 1 MB 代码来说少得离谱），
  且块内还夹着明文导出名（见 §4），更像**静态加密的数据/VM 字节码**，不是被隐藏的代码。
- `.vmp0`：2026-10-20 的评估已定案（`server/破壳可行性评估.md` §4）——它是虚拟化段不是压缩，
  devirtualize 成功率 < 5%，且里面只有 CPS 驱动的分发逻辑，没有我们要的功能。

### 2.2 我们其实已经完成了 235 派做的那三步

| 235 派的做法 | 我们的状态 |
|---|---|
| dump 运行镜像 | ✅ `server/img_dump/main_GundamOnline_CHINA.exe`（10-17） |
| 让壳自解包后的内容落地 | ✅ `ohjicybf` 已解密（48% 差异在镜像里） |
| 重建导入表 | ⬜ 没做，但我们不需要（见 2.3） |

### 2.3 ★ 关键：CPS 不是壳的一部分

`server/hook_log.txt` 的实测调用栈：

```
{"ev":"LoadLibraryW","path":"./ACOPCShell.dll","realRet":"0x0",
 "bt":["GundamOnline_CHINA.exe+0x583679","GundamOnline_CHINA.exe+0x210064",
       "GundamOnline_CHINA.exe+0x58eb1b", ...]}
```

`+0x583679` 在**主段明文区**（0x58xxxx），不在 `ohjicybf`（0xE4A000+）里。

⇒ **跳过壳不会跳过 CPS**；启动期那次概率性崩溃也发生在 CPS 自己 decompress 出来的匿名 r-x 区，
跟 PE 壳无关。所以"脱壳换写权限"这条路根本不成立。

### 2.4 如果非要做的成本

| 步骤 | 难度 | 说明 |
|---|---|---|
| 取 OEP | **高** | 入口桩 `0xEED005` 是 GetPC 桩：解密 `0x1000` 字节到 `0xE4D000`（xor `0x54E14DD9` / add `0x47AF69B6`）后 `ret` 到 `0xE4D014`。我按这个算法离线解过，解出来是 VM 垃圾填充（`std; cld; shr esp,1` 重复） ⇒ 二级链在 VM 里，静态走不通，只能运行时取 EIP |
| 重建 IAT | 中 | 需要把内存里已解析的 500+ 个指针反查成「模块!导出序号」，再生成 descriptor（snap_11 的 `build_imports.py` 是现成范式） |
| 抗 ASLR | 中 | dump 出的 IAT 是绝对地址，必须重建 descriptor 而不能直接沿用 |
| 收益 | **≈ 0** | 见 §1、§2.3 |

**结论：2~4 天工作量，换不到任何当前需要的能力。不建议做。**

## 4. ★ 意外收获：客户端自带的 `cpsoff` 开关

在 `0x9F657C` 找到 ACOPCShell 的导出名表，唯二引用点都在 `0x5836xx`；
顺着反汇编出整个 CPS 引导函数：

```asm
0058366E  push 0xDF65AC          ; L".\ACOPCShell.dll"
00583674  call LoadLibraryW      ; 返回 0 时（文件不存在）走 0x58374E
0058367E  mov  [0x117B798], eax  ; g_hAcopc
00583695..00583729  GetProcAddress × 9，结果存进：
     0x117B79C InitAcopc
     0x117B7A4 InitSystem
     0x117B7A8 Release
     0x117B7AC IntegrityCheck
     0x117B7B0 UpdateScanEngineHdb
     0x117B7B4 Scan
     0x117B7B8 SetSpeedGearCallBack
     0x117B7BC RegisterApi
     0x117B7C0/0x117B7C4 SecurityCallApi
00583731  mov al,1               ; 返回 true = CPS 就绪
```

而在**加载之前**有一段参数匹配：

```asm
00583605  xor eax,eax
00583607  mov edi,0xDF65D0       ; "cpsoff"
0058360C  mov ecx,7              ; 比 7 字节
00583611  repe cmpsb             ; 逐个 argv 与 "cpsoff" 比较
00583613  sete [esp+0x17]
00583657  cmp [esp+0x17], bl
0058365B  jne 0x583747           ; ★ 命中就走这里
...
00583747  mov byte [0x117B7A0], 1   ; g_cpsoff = 1
0058374E  xor al,al                 ; 返回 false，LoadLibraryW 那整段根本不执行
```

⇒ **只要命令行里有一个以 `cpsoff` 开头的参数**（`cpsoff` / `cpsoff1` / `cpsoff=1` 都行），
客户端就会置 `[0x117B7A0]=1` 并**完全不加载 ACOPCShell.dll**。

### 这个开关可能一次性解决三件事

| 现在 | 用 `cpsoff` 之后（待验证） |
|---|---|
| frida 伪造 7 个 CPS 驱动 IOCTL + `LoadLibraryW`，**必须管理员** | 可能完全不需要 |
| `0x70E9` 上报"代码篡改 `Addr:ACFE76`" | `IntegrityCheck` 指针为 NULL，检测源可能消失 |
| 启动期概率性崩溃（崩在 CPS 的匿名 r-x 区） | CPS 不加载，崩溃源可能消失 |

⚠️ **全部是推断，没有一条经过运行时验证。** 两条必须实测的悬念：
1. 游戏是否还走 `CreateFileW("\\.\CPS")` + `DeviceIoControl`（驱动链可能独立于 DLL）；
2. `0x70E9` 的上报是谁拼的（若在明文游戏代码里，`cpsoff` 也救不了）。

## 5. 建议的下一步（按性价比）

1. **P0（今天就能做）**：给 `tools/run_hooked.py` 加一个"带 `cpsoff` 参数启动、不做任何 frida 伪造"的模式，
   看能否一路走到休息室。**如果能，整条 CPS 线可以退役**，顺带解决管理员依赖与启动崩溃。
2. **P0.5**：若能进休息室，立刻回测 inline hook（例如在 `0xAA2D50` 打一个只读日志桩），
   确认"禁止 hook"是否随之解除——这是解锁全部运行时分析的关键。
3. **P1**：若 `cpsoff` 不通，再回去查 `0x5836xx` 的调用者（`+0x210064`）；那才是"谁要求 CPS"的真正入口。
4. **不建议**：重建独立 exe（§2.4）。
