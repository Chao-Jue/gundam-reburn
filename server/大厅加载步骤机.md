# 大厅加载「步骤机」：`FUN_0043b530`

> 2026-10-22。目的：找出「正在取得数据」到底靠什么条件离开。
> 反编译原文：`server/decomp_check580.txt`、`server/decomp_wait.txt`。

---

## 1. 它是谁

`FUN_0043b530(this)` 是一台**顺序步骤机**，`*(this+4)` 是当前步骤号。
函数指针只出现在 `.rdata` 的 `0x00caba6c` 一处（不是普通 vtable，没有 RTTI）。

游戏对象 `DAT_01161f28`（运行期实测 `0x2063d128`），表下载器挂在它的 **`+0x580`**。

## 2. 关键几步（原文照抄）

```c
case 4:                                     // 创建表下载器
    FUN_00439fb0(0xb, 0);
    uVar2 = FUN_0042efb0();                 // 重建下载器（已知：销毁+新建+FUN_00545210 启动）
    *(int*)(this + 4) += 1;                 // → 5
    return;

case 5:                                     // ★ 等下载器消失
    if (*(int*)(DAT_01161f28 + 0x580) == 0) {
        FUN_00438b30(0xb);
        uVar2 = FUN_0042ef40();
        *(int*)(this + 4) += 1;             // → 6
        return;
    }
    break;                                  // ← 下载器还在，就停在这里

case 6:
    FUN_0045bad0(); FUN_0054fec0(); FUN_0055e5c0(); FUN_00541e70();

case 7:
    FUN_0043a680();
    *(int*)(this + 4) += 1;                 // → 8   （注意：没有 return，会继续落到 case 8）

case 8:
    if (*(char*)(DAT_01161f28 + 0x10615) != 0) {    // ★ 又一道闸，字节标志
        *(int*)(this + 4) += 1;
        return;
    }
    break;

case 9:
    *(char*)(DAT_01161f28 + 0x10611) = 1;
    *(int*)(this + 4) += 1;
```

**两道闸**：`+0x580`（下载器指针）和 `+0x10615`（字节标志）。

## 3. 配套的「重置器」`FUN_0043bf50`

```c
FUN_0043afe0(); FUN_0043ae60()×2; FUN_004352c0(); FUN_00435350(); FUN_00435230();
FUN_0042d880(); FUN_00433360(); FUN_0042b510()×2;
*(int*)(this + 0xC)       = 0;
*(int*)(this + 0x1061c)   = 0;
(**(code**)(*DAT_01161f2c + 0x14))(0x95);   // 逐个释放界面 id：95 b7 d8 f6 b1 ca
... 同样 0xb7 / 0xd8 / 0xf6 / 0xb1 / 0xca ...
*(int*)(this + 0x10620)   = 0;
if (this->tables) { 析构; free; this->tables = 0; }   // ← 也会销毁下载器！
```

⇒ 「下载器被销毁」有两个来源：**tick 的 done 分支**，或者**这个重置器**。
所以外部强改时看到对象消失，不能反推是哪一条路径。

## 4. 实测：把第一道闸强行满足，结果不是推进，是**退回登录**

```
poke [0x2063d6a8] ( = DAT_01161f28+0x580 ) 之前 = 非 0
poke [下载器+0x0C] = 0   →  4 -> 0（写入成功）
3 秒后扫堆：vtable=0xcb9edc 的对象已消失（tick 的 done 分支确实跑了）
再读 [0x2063d6a8] = 0                      ← 闸门条件已满足
再读 [DAT_01161f28+0x10615] = 0            ← 第二道闸仍关着
界面：截图显示**回到了登录界面**（账号/密码/登录框）
```

⇒ **外部满足第一道闸 ≠ 状态推进**。合理解释有二：
1. 步骤机此刻没被调用（不在这条路径上）；
2. 步骤机推进了，但卡在 case 8 的 `+0x10615`，而那是**服务端消息**才会置的字节；
   会话随后被重置（`FUN_0043bf50`）→ 退回登录。

两条都指向同一个结论：**这条链的正解在服务端**，不是客户端。

## 5. 第二道闸 `+0x10615`：只有一个置位点，而它没有调用者

全镜像扫「位移 0x10615」共 8 处：

| 位置 | 指令 | 作用 |
|---|---|---|
| **`0x4392c0`** | `mov byte [ebx+0x10615], 1` | **唯一置 1 点**，位于 `FUN_00439190` 末尾 |
| `0x43a6b5` / `0x43a828` | `mov byte [...], 0` | 清零 |
| `0x43b64f` | `cmp byte [...], 0` | 步骤机 case 8 |
| `0x43c44f` | `mov [esi+0x10615], bl` | `+0x10611..+0x1061a` 一整组标志的批量重置 |
| `0x44c7ac` / `0x9e783f` / `0x9eab61` | `cmp byte [...], 0` | 另外三处读它 |

置位函数末尾：

```c
*(this+0x10619) = (param_7 != 0);
*(this+0x10615) = 1;          // ← 这里
*(this+0x1061a) = 0;
FUN_00438b30(5);
```

调用链：`0xaf618e`(trampoline) → `0xa4fae0`(纯转发) → `0x439190`。
**但 `0xaf618e` 在全镜像里没有任何引用**（VA `0xaf618e`、RVA `0x6f618e` 各 0 次），
既无 `E8/E9` 直接调用，也无 4 字节指针指向。

⇒ 要么这段是**死代码**（本版本永远不会置 1），要么那张「消息→处理函数」表
在运行期被壳重定位（镜像里已有 29132 字节运行期补丁，最密页在 `0xd8xxxx`）。
两种可能都指向同一结论：**这个 5.0.0.33 版本在 case 8 这条通路上是不完整的**。

## 6. 下一步（都很便宜）

1. **1 字节堆写**：卡住时把 `[game+0x10615]` 写成 1，看等待界面是否关闭。
2. 读另外三处 `cmp [..+0x10615]`（`0x44c7ac` / `0x9e783f` / `0x9eab61`）在等什么，
   它们可能揭示同一个标志还控制别的界面。
3. 若 (1) 有效但界面变成另一个卡点，就顺着第二个卡点继续——这条链已经能一步步走。

## 7. 顺带记下的坑

- `server/rtti_classes.txt` 里的地址是 **RVA**，加 `0x400000` 才是 VA。
- 本镜像的 TypeDescriptor 名字在 `TD+0xC`（不是常见的 `TD+8`），按 `+8` 查名会全部落空。
