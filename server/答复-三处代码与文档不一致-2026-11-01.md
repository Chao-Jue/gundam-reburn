## 1. `slot_num` —— 你们是对的，已改

### 改动

```python
# server/fake_auth.py, 0x16AC 分支
struct.pack_into('<H', begin, 4, min(len(units), 0xFFFF))   # 原来是 max(100, len(units))
```

`docs/HANGAR_AND_UNITS.md` §3.1 那句"它是仓库容量"已改成"它 = 本次下发的 A832 条数"。

### 你们没提、但能加固这个结论的三条

1. **字段名的出处是客户端自己的日志串。** 我们给的 handler 是 `0xAAA848`，它的日志前缀是
   `_proto_lounge_client::recv_msma_init_get_r_begin`，字段串依次是
   `sv_time= / slot_num= / sort_tm_sec= / sort_tm_usec= / conf_payload_boost_penalty= /
   conf_payload_boost_bonus= / conf_payload_body_balance_max= / msma_sort_type= / msma_sort_order=`。
   `slot_num` 是客户端给的命名，不是我们起的。
2. **读取顺序与本表一致，长度自证。** 该 handler `push 0x1c`（28）申请正文，和 28B 定长吻合，
   读取序列是 `u32 → u16 → u32 → u32 → u16 → u16 → u16 → u32 → u32`，就是这张表。
3. **handler 内部不拿它循环。** 读完 9 个字段后，`0xAAAC89` 一次性调
   `vt[0x21c](…)`，9 个参数就是这 9 个字段（参数顺序与字段顺序相反，`slot_num` 是其中之一）。
   真正消费它的是那个虚方法，handler 自己不用它控制迭代次数。这也解释了"偏大值为什么不一定崩"
   ——要看那个回调怎么用。

### 你们那条"代码自身不自洽"的批评成立

`if units:` 那行确实是"容量"读法的反证：容量不该因为仓库空就变 0。已按条数写，
并且不再包在 `if` 里（空仓库直接写 0）。

### 关于"两个 build 结论相反"，我要补一个反向线索

`refs/msgo-doc/reverse-login-chain/formats/全链报文总表.md:96` 里，同类报文
`0x947E send_item_init_get → 0x02EE` 的字段叫 `slot_num_main / slot_num_consume /
slot_num_trash / slot_num_plan`（4×u16），那**确实是背包格数，也就是容量**——
因为背包有"扩展"概念，且同一条报文里有独立的 `count + itmlist`。

所以"`slot_num` 家族 = 容量"这个类比是真实存在的，这也是当初写成 100 的由来之一。
但在 `msma_init` 里**没有独立的 count 字段**，终止靠 `0xFCE6`，加上你们 235 的单变量结果，
容量读法站不住。**两个 build 的读取器行为不同**（一边只用它 reserve，一边按它迭代）是我目前
能给出的唯一自洽解释，但这是我们两边的共同开放项，不是已证结论。

### ⚠️ 我这边还没有 50033 的 A/B

我们长期用 100 跑通，**没有"50033 填 n 也能跑"的对照**。所以你们的等价修正请先保留，
等我们跑完一次真机再定：跑得通就确认条数读法；跑不通我会立刻回滚，并在文档里写清
"50033 要求 ≥100 / 235 要求 =n"这个分歧，而不是硬套一个结论。

### 2.3 它到底是什么（正文解出来就知道了）

### 2.4 客户端有没有接收 handler —— 你们问的第 3 件事

三条独立枚举都指向"没有"：

1. 全镜像搜不到任何 `cmp eax,0x70E9` / `cmp r32,0x70E9` 立即数比较（**0 处**）；

**但我要主动提醒这个证据的强度有限**：这套分派里有大量"`cmp eax,imm` 命中后顺序落下"的分支，
`0x45E4` 就是这么被我们漏掉过一次（表里误标成默认分支 `0xAD5E25`，实际 handler 在 `0xAAE0B5`
且**没有任何跳转指令指向它**）。所以正确说法是"**枚举不到**"，不是"绝对没有"。
真正支撑"不需要回执"的是 2.2 的 114 次实测，而不是这三条枚举。

### 2.5 为什么你那边 0 次、我这边 114 次

先说清边界：**"收到"这条日志与 `--sweep` 无关**（`--sweep` 只决定走不走回复分支），
所以你们三轮一次都没见到，说明客户端**根本没发**这条。最可能的原因是 CPS 模块加载与否：

- 它上报的对象是 `uxtheme.dll` / `MSCTF.dll` 的 hash 和代码指纹，这是 ACOPCShell 的扫描产物；
- 我们用 `cpsoff` 启动时 ACOPCShell 完全不加载（见 `server/cpsoff-验证-2026-11-01.md`）。

但这条推论**我还没坐实**：我们 22:36:30 那一次（当天最后一条 0x70E9）很可能就是 cpsoff 会话，
如果 cpsoff 下仍然会发，那"CPS 产出"的解释就不成立。记为待查项，不做结论。

时间位置上可以确定：它固定在**表下载收尾、登录界面出现之前**，每次会话 1~2 条。
