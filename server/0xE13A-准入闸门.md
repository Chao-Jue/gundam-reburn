# `0xE13A` 分支入口的「准入闸门」全解（P0 结果）

> 2026-10-23 17:40。纯离线静态分析（`server/img_dump/main_GundamOnline_CHINA.exe`，base `0x400000`）。
> 反汇编产物：`server/_dis_a93e40.txt`。

---

## 0. 结论先行（重要，且与上一轮的猜测相反）

`0xACFE1F` 处的 `call 0xa93e40` 确实是**每个操作码独立**的准入检查，但：

- **允许标志数组默认全是 1**（构造时逐字节写 1），全镜像里**没有任何一处把它写成 0**；
- **配额/速率字段默认全是 0**，而代码里 `0` 明确表示「不做检查」。

⇒ **在当前「服务端不配置配额」的状态下，这道闸门对 `0xE13A` 一律放行。**
⇒ 我上一轮"闸门静默丢包"的假设**被证伪**，不要再往这个方向找。
⇒ 它仍然值得留一个观测点（成本为零，见 §4），因为一旦服务端下发配额，它就会**静默丢包**
（错误虚函数 `vt[0x64]` 是空 `ret 8`，什么都不打印）。

## 1. 闸门本体 `0xA93E40`（全函数只有 0x75 字节）

```
0xa93e40  push ebx
0xa93e41  mov  ebx,[esp+8]              ; arg1 = code（小整数，不是 opcode！）
0xa93e46  esi = (code*3 + 0x4e) << 4     ; = code*0x30 + 0x4E0
0xa93e4b  edi = ecx                      ; this = 协议对象
0xa93e50  esi += edi                     ; state = this + 0x4E0 + code*0x30
0xa93e52  cmp  byte [ebx+edi+0x29e],0    ; ← 允许标志 flag[this+0x29e+code]
0xa93e5a  jne  0xa93e6e
0xa93e5c      vt[0x64](code, 2)          ; 报错码 2
0xa93e66      al = 0 ; ret 4             ; ← 静默拒绝（错误函数是空的）
0xa93e6e  eax = [esi+0x10] ; or eax,[esi+0x14]
0xa93e74  je   0xa93ead                  ; 周期 == 0 ⇒ 不做检查 ⇒ 放行
0xa93e76  call 0xa5d2d0(esi)             ; 到点就把计数清零（令牌桶/滑动窗口）
0xa93e7d  ecx=[esi+4] ; eax=[esi]
0xa93e80  cmp ecx,[esi+0xc]              ; 64 位比较 hi
0xa93e85  jb  0xa93ea2                   ; count < limit ⇒ 放行
0xa93e87  ja  0xa93e8e                   ; count > limit ⇒ 拒绝
0xa93e89  cmp eax,[esi+8]                ; 64 位比较 lo
0xa93e8c  jbe 0xa93ea2                   ; count <= limit ⇒ 放行
0xa93e8e      vt[0x64](code, 3) ; al=0 ; ret 4    ; 超配额 ⇒ 静默拒绝
0xa93ea2  count64++ ; [esi]=eax ; [esi+4]=ecx     ; 放行时计数 +1
0xa93ead  al = 1 ; ret 4
```

## 2. 两个数据结构（在协议对象里的位置）

### 2.1 允许标志数组：`this + 0x29E`，共 `0x242` 字节

同一块里还有**第二个**长度相同的数组在 `this + 0x5C`，两者成对初始化：

```
0xa998b4  lea  eax,[esi+0x29e]
0xa998ba  mov  ecx,0x242
0xa998c0  loop: mov byte [eax-0x242],1     ; ← 数组 A @ this+0x5C
0xa998c7        mov byte [eax],1           ; ← 数组 B @ this+0x29E（闸门读的就是它）
0xa998ca        inc eax ; dec ecx ; jnz
```

`0x242` = 578，正好等于 `0xAA2D50` 里读 opcode 失败时上报的错误码（`push 0x242`）。
⇒ 这两种数组都是**按 code（0..0x241）索引**的。

> `code` ≠ opcode：`0xE13A` 分支用的是 `push 0xc`，隔壁 `0xE18C` 分支用 `push 0xa7`。
> 所以 code 是"报文通道/类别编号"，每个 handler 各自硬编码一个，**不能靠 opcode 反推**。

### 2.2 每 code 的状态块：`this + 0x4E0 + code*0x30`，48 字节

ctor 在 `0xa99836` 起（先 `mov [esi],0xE09A74` 装基类 vtable），把
`0x4E0 .. 0x713F` 共 `0x242` 个 48 字节块整块清零，然后
`[esi+0x7140]=0 / [esi+0x7144]=0 / memset(esi+0x7148, 0, 0x908) / [esi+0x58]=0`。

| 偏移 | 含义（实测自 `0xa93e40` + `0xa5d2d0`） |
|---|---|
| `+0x00..0x07` | 已收计数（u64） |
| `+0x08..0x0f` | 上限（u64） |
| `+0x10..0x17` | **周期 ms（u64）；== 0 表示"本 code 不做任何检查"** |
| `+0x18..0x1f` | 上次清零时刻（u64，来自 `0xbd28a0` 取时） |

`0xa5d2d0` 就是"到点清零"：`if period==0 or count==0 → ret`；否则
`now - last >= period` 时按 `0xc185a0`（64 位除）算出应清零的倍数、更新计数与时刻。

## 3. 证据：全镜像只有 3 处碰到这两块

搜索 `9e 02 00 00`（disp32 = 0x29E）与 `be fd ff ff`（`[eax-0x242]` 的负位移）：

| 位置 | 作用 |
|---|---|
| `0xa93e55` | 闸门**读** `flag[this+0x29e+code]` |
| `0xa998b6/0xa998c0/0xa998c7` | 构造函数**写 1**（两张表一起） |
| `0x540fc5` | 无关（另一个类里 `mov ax,word[ecx+0x29e]` 的 getter，`ret 8`） |

- **没有任何 `mov byte [...+0x29e+code], 0`**；
- 也没有 `memset(this+0x5c, 0, 0x70E4)` 这种整块清零（搜 `imm32 0x70E4` 只有一处无关命中）。

⇒ 标志永远为 1；状态块永远是全 0 ⇒ 周期 0 ⇒ 检查被跳过。**闸门恒放行**（除非有服务端配额下发，
而写这四组字段的代码在本镜像里同样没找到——大概率在 `.vmp0` 或干脆没实现）。

## 4. 对后续实验的影响

1. **不要再怀疑闸门**。`0xE13A` 被丢掉的原因只剩两种：
   - ① 报文根本没到 `0xAA2D50`（**帧层长度/封装**问题）；
   - ② 到了、也进了分支，但字段读取越界（正文长度不足）。
   两者在 P1 的观测里**一个数就能区分**。
2. P1 的 vtable 探针**顺手记这 6 个数**（全是数据读，零成本）：
   `flag=*(this+0x2AA)`、`count/limit/period/last`（`this+0x720` 起 4 个 u32），
   以后遇到"莫名静默"先看这 6 个数是不是全 0。
3. `0x2AA = 0x29E + 0xC`（`0xE13A` 分支自己的 code）。

## 5. 顺手更正两条旧记录

| 旧说法 | 更正 |
|---|---|
| `0xad5e25` = 成功出口 | ❌ 它是**所有分支的统一收尾**（`[esp+0x2908]=-1` + `call 0xbd2890`）。闸门失败也是跳这里。**不能当判据**。 |
| 错误虚函数 `vt[0x64]` 为空 ⇒ 看不出错误 | ✅ 依然成立，但原因更清楚：`vt[0x64](code, 2/3)` 是**闸门专用**的上报，参数是 `(code, 原因码)`，`2`=标志未放行，`3`=超配额。将来若真要区分，就 hook 这个槽（数据补丁，同 P1 手法）。 |
