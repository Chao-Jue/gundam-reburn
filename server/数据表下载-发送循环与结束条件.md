# 数据表下载：发送循环与"结束"条件（静态全解）

> 2026-10-20。放弃方案 B 后转静态路线（镜像主代码段是明文，**不需要运行客户端**）。
> 本文回答一个问题：**第 66 张之后为什么不再发请求？**
> 结论：**不是"卡住"，是客户端主动判定"下载完成"并销毁了下载器。**

---

## 1. 完整的三个函数（Ghidra 反编译，已核对汇编）

### 1.1 发送器 `FUN_005446e0`（`server/decomp_driver.txt`）

```c
void FUN_005446e0(tables *this) {
    if (this->field_0xC == 0) return;          // ← 唯一的发送闸门
    node = *(node**)this->field_8;             // field_8 = std::map 的哨兵
    name = ((std::string*)*node)->c_str();     // node->[0]->[+0x14]
    tmp  = FUN_00b10f60(name);                 // 临时 std::string
    FUN_00a561e0(tmp.c_str());                 // → 0xad6ac0 send_datafile_download
}
```

汇编对照（`0x544703`）：`mov eax,[ecx+0xc]; test eax,eax; je 0x54475e`。

### 1.2 闸门 + 待发标志 `FUN_00544770`

```c
void FUN_00544770(tables *this) {
    if ((this->flags_0x10 & 1) != 0) {          // 有待发的下一张
        this->flags_0x10 &= ~1;                 // 清位
        FUN_005446e0(this);                     // 发出去
    }
}
```

### 1.3 结束判定 `FUN_00544610`

```c
bool FUN_00544610(tables *this) {
    return this->field_0xC == 0;                // 「下载完成」
}
```

**注意 `0xC` 同时是"还能不能发"和"算不算完成"的同一个字段。**
两者互斥：`0xC != 0` → 发下一张；`0xC == 0` → 判定完成。

### 1.4 每帧 tick（`FUN_0043d270` 尾部，`0x43d7a0`）

```c
ecx = this->tables;                 // [edi+0x580]
if (ecx == 0) goto L;
FUN_00544770(ecx);                  // ① 有 pending 就发下一张
ecx = this->tables;
if (FUN_00544610(ecx)) {            // ② 判定"下载完成"
    esi = this->tables;
    if (esi) {
        (*(vtable[0]))(0);          // ③ 析构
        FUN_00b294d0(esi, ..., 0);  // ④ 释放
        this->tables = 0;           // ⑤ 置空 —— 之后 tick 再也不会碰它
    }
}
L: ...
```

汇编：`0x43d7aa call 0x544770` → `0x43d7b5 call 0x544610` → `test al,al; je` →
`0x43d7dc call 0xb294d0` → `0x43d7e4 mov dword ptr [edi+0x580], 0`。

## 2. 成功路径是原子的（这条纠正了旧假设）

`FUN_00544790` 里，`0xA46480` 返回 0 之后：

```c
switch (node->index) { case 0..0x46: 各自 Load; }   // 71 个分支
FUN_009ebc20(node->index, node->name);
FUN_00b08aa0(0);
FUN_009ae510(&reply, node);                          // 从 map 里 erase
this->flags_0x10 |= 1;                               // 置「有下一张」
```

**erase 和置 pending 位是紧挨着的两条语句，无条件、原子。**
⇒ 不可能出现"erase 了但没置标志"或"置了标志但没 erase"。
⇒ 只要进去过一次成功路径，下一帧就一定会发下一张。

这条很重要：它把"卡住"的候选原因从一大堆收缩到一个 ——
**`field_0xC` 变成了 0**（于是既不发，又被判定完成，还被销毁）。

---

## 3. 由此得到的因果链

```
第 66 张处理成功
   → erase + pending=1
   → 下一帧：FUN_00544770 清 pending、发第 67 张    ← 本应发生
   → 同一帧：FUN_00544610 返回 true（0xC == 0）
   → 析构 + 释放下载器 + [X+0x580] = 0
   → 之后 tick 永远跳过
   → 界面停在「正在取得数据」，且不再有任何 0xF86A 请求
```

**注意顺序**：发送在前、销毁判定在后。所以最后一张其实**发出去了**，
只是紧接着下载器就被销毁，回包回来时已经没有接收者 ——
这与"服务端看到最后一张请求、客户端界面不动"的观察一致。

## 4. `field_0xC` 是什么：构造时是 0，`0` 就等于"完成"

### 4.1 这个下载器只有 20 字节

`FUN_0042efb0`（重建入口）：

```c
if (this->tables) { 析构; free(this->tables); this->tables = 0; }
iVar2 = FUN_00b29490(0x14, ...);                        // 分配 0x14 = 20 字节
this->tables = iVar2 ? FUN_00545340(iVar2) : 0;         // 构造
FUN_00545210();                                          // 启动
```

### 4.2 构造函数 `FUN_00545340`

```c
*this        = &PTR_LAB_00cb9edc;   // +0x00 vtable
this[2]      = FUN_00a45d20();      // +0x08 = std::map 哨兵（isnil=1，三个自指）
this[3]      = 0;                   // +0x0C = 0        ← 关键
*(byte*)(this+4) &= 0xfc;           // +0x10 清低 2 位
```

20 字节刚好装下 vtable / map / `+0x0C` / `+0x10`，**没有地方放"剩余张数"之外的复杂状态**，
所以 `+0x0C` 只能是一个 int 标志。

### 4.3 所以 `+0x0C` 不是"剩余张数"，是"就绪/待发"

推导链：
1. 构造时 `+0x0C = 0`；
2. `done()` 判据就是 `+0x0C == 0` → **刚构造出来的对象立刻算"完成"**；
3. tick 里"先发送、后判完成"，所以只要 `+0x0C` 一直是 0，
   这一帧就会**发不出去 + 立刻被销毁**（`[X+0x580] = 0`）。

⇒ `+0x0C` 必须由**某个异步回调置 1**，否则这个下载器活不过一帧。
**这就是一条静默放弃路径**：置 1 没发生 / 被清回 0 → 下载器被销毁 →
界面永久停在"正在取得数据"，且服务端再也收不到 0xF86A。
**和观察到的现象逐条吻合。**

## 5. 启动函数 `FUN_00545210` —— msma 那条队尾的来历

```c
FUN_0042d5d0(...);
uVar1 = FUN_00b116b0(0xa000005, 2, FUN_005451b0, this, 1, 0);   // 异步读容器里的文件
iVar2 = FUN_00a485c0(uVar1, ...);                                // 逐行/逐块取
if (iVar2 == 0) {                                    // ← 只有"成功"才走进去
    FUN_00402b20(L"msma/msma_overwrite_params.csv", 0x1e);       // 拼文件名
    local_2c[0] = 0x46;                                          // 0x46 = 70
    FUN_00567ca0(local_50, local_2c);                            // 登记 (70, msma…)
    FUN_005446e0();                                              // 立刻发第一张
}
```

回调 `FUN_005451b0` 是**按行**的：

```c
line = FUN_004559c0(0);              // 取一行
if (*line != L'#')                   // 首字符不是 '#'
    FUN_00545000(this);              // 才处理这一行
```

⇒ 这就是"`#` 注释行"为什么关键：**注释行被整行跳过**。

### 结论：`msma/msma_overwrite_params.csv` 是**独立第二阶段**，不是主清单的一项

这解释了那个一直很别扭的现象：
- 它不在我们 `download_list.csv` 的 74 行里；
- 它却出现在客户端队列的**队尾**，序号 `0x46 = 70`；
- 它由 `FUN_0042efb0 → FUN_00545210` 这条**单独的重建+启动**路径入队。

也就是说，**"正在取得数据"至少有两个阶段**：主清单阶段 + msma 阶段，
而 `[X+0x580]` 那个下载器两个阶段共用、用完就销毁、下次重建。

## 6. 还没确定的一件事（必须一次运行期读数才能定）

`+0x0C` 到底由谁置 1、又为什么在 66 张之后变回 0。两条候选：

| 候选 | 含义 | 若成立则 |
|---|---|---|
| **A. 有处把 `+0x0C` 清回 0** | 例如"这一批发完了"或某个错误分支 | 属于**主动放弃**，去镜像里找那条清零点（`mov dword ptr [reg+0xc], 0`） |
| **B. `+0x0C` 从来没被置 1** | 异步读 `FUN_00a485c0` 返回非 0 → 整块 if 被跳过 | 属于**静默失败**，客户端压根没打算发，界面才一直等 |

判据只要 3 个整数（**纯只读，一个字节都不写**）：
```
tables = ReadProcessMemory(DAT_0117d380 + 0x580)   // 4 字节指针
读 tables + 0x08 / + 0x0C / + 0x10
```
- `0x580` 已经是 0 ⇒ 下载器早就被销毁过了（tick 走完 ⑤），落 A/B 都可查
- `0x0C == 0` 且 `0x580 != 0` ⇒ 卡在"刚重建还没置 1"，落 B
- `0x0C != 0` ⇒ 两条都不成立，转查 tick 为什么没被调用

> `DAT_0117d380` 是 `0x7A60` 字节的会话对象（`0xa4f130` 里 `FUN_00b29490(0x7a60, ...)`）；
> `+0x580` 是它的成员。回包分派 `0x42DA60` 也是 `mov ecx,[ecx+0x580]; jmp 0x544F60`。

## 7. 顺带确认 / 需要改的旧结论

- ✅ `0x42DA60 → 0x544F60`：汇编就是 `mov ecx,[ecx+0x580]; jmp 0x544f60`。
- ✅ `0x544620` 名字→序号：查不到时 `mov eax,0x47; ret 4` = 返回 **71**（`0x5446c0`）。
- ✅ 71 个 Load 分支（case 0..0x46）与旧 case 表一致；`case 0x46 → FUN_0054d0a0`。
- ❌ **旧结论「SEH 吞异常导致不 erase」要降级**：erase + 置 pending 是两条相邻语句，
  若 `Load` 抛异常被 SEH（`0xC47580`）吞掉，**已经退出了 `if (rc==0)` 块，
  所以既不 erase 也不置 pending** —— 那种情况下会**永久停在那一张**。
  但实测是"前进了 66 张"，所以不是这条路。
