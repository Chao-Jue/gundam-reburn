# 帧层定案：`0xBD1610` 反汇编 + 我们封装的逐字节验证

> 2026-10-23 17:55。本机镜像离线反汇编 + 用同一套逻辑回读服务端实际发出的字节。
> 结论：**服务端的帧封装与客户端解码器逐字节吻合**，帧层不是卡点。上一轮怀疑的
> "k=1 只读低 8 位"">255 不可用"**全部作废**。

---

## 1. 解码器本体 `0xBD1610`（vtable 里的分帧函数）

```
0xBD1610  sub  esp,0x48
0xBD161F  ebx = arg1                ; 可用字节数
0xBD1623  cmp  ebx,1 ; jae ok       ; 少于 1 字节 → return 0（等更多数据）
0xBD1628  edi = arg2                ; buf
0xBD1647  call 0xBD28A0             ; 取时间戳 → [esi+0x48]/[esi+0x4C]
0xBD1652  eax = buf[0]
0xBD1657  ecx = eax >> 4            ; **type = buf[0] >> 4**
0xBD165A  cmp  ecx,4 ; ja 0xBD1A9A  ; type 0..4 合法，其余报错
0xBD1663  jmp  [ecx*4 + 0xBD1ADC]   ; 5 路跳转表
   ── case 0（数据帧）落点 0xBD166A ──
0xBD166A  eax &= 3                  ; **k = buf[0] & 3**
0xBD166D  ecx = k+2
0xBD1670  cmp  ebx,ecx ; jb wait    ; 头不足 k+2 字节 → return 0
0xBD1678  len  = buf[1]
          if k>=1: len += buf[2]<<8
          if k>=2: len += buf[3]<<16
          if k>=3: len += buf[4]<<24          ; 小端，宽度 = k+1
0xBD16A6  ebp = len + k + 2                    ; **本帧总长**
0xBD16AA  cmp  ebx,ebp ; jb 0xBD1A2D           ; 帧不完整 → return 0（不消费）
0xBD16B2  if ([esi+0x50]) [edx+0x24]=0         ; 每帧一次状态复位
0xBD16BE  edx = [esi] ; edx = [edx+0x54]
0xBD16C3  push len
0xBD16C8  push buf + k + 2                     ; 载荷起点
0xBD16C9  mov  ecx,esi ; call edx              ; → 0xAA2D50 on_message(payload, len)
0xBD16CD  eax = ebp ; return 本帧总长
```

跳转表实测（`0xBD1ADC` 起 5 个 dword）：

| type | 目标 | 
|---|---|
| 0（数据帧） | `0xBD166A` ← 我们唯一用到的 |
| 1 | `0xBD16E4` |
| 2 | `0xBD177A` |
| 3 | `0xBD17FE` |
| 4 | `0xBD1868` |

由此定死三件事：

1. **`type = buf[0] >> 4`，`k = buf[0] & 3`** —— 与 `fake_auth._kind0` 的
   `byte0 = 0x00 | k` 完全一致。
2. **长度字段 = 载荷长度，含 2 字节 opcode**，不含首字节、不含长度字段自身。
3. **本帧总长 = len + k + 2**。`817` 正文 → payload `819` → k=1 → 线上 `822` 字节，
   首 5 字节 `01 33 03 3a e1`。

⇒ `0xAA2D50` 就是 `vt+0x54`（vtable `0xE14D04`+0x54），它收到的 `len` 就是长度字段原值。

## 2. 闭环验证（`server/_verify_frames.py`）

把 `0xBD1610` 的字面逻辑用 Python 重写，然后回读 `fake_auth.op_block()` 的真实输出：

```
PASS  0xE13A 正文 817       发 832B = 0133033ae100…
      首帧 total=822 k=1 len=819 payload=3ae10000…
      对齐填充：1 个 dummy 帧共 10B，opcode 0xFFFF
      解码器消化 832B，剩余 0B
PASS  0xE13A 正文 252       发 256B = 00fe3ae1…    首帧 total=256 k=0 len=254   剩余 0B
PASS  0xE13A 正文 254       发 272B = 0100013ae1…  首帧 total=259 k=1 len=256   剩余 0B
PASS  0x5290 占位 2431      发 2448B = 01810990 52… 首帧 total=2436 k=1 len=2433 剩余 0B
```

- 每一帧的 `payload` 都严格等于 `opcode + 正文`；
- 16 字节对齐用的 dummy 帧（`opcode 0xFFFF`）被**整帧吃掉、零剩余**，不会造成错位
  （这一点很关键：`_align_message` 补的是**合法帧**，不是零填充）；
- 2431 字节的表占位也走 k=1 正确解码。

## 3. 连带结论

| 旧说法 | 现状 |
|---|---|
| "k=1 的 2 字节长度只取低 8 位" | ❌ 作废。代码明写 `len = buf[1] \| buf[2]<<8`（k≥1）。 |
| ">255 需要另一种封装" | ❌ 作废。k=1/k=2 都合法，2431 与 819 都能解码。 |
| "`clientBody=49` 说明客户端只认 1 字节长度" | ❌ 那 49 是 hook 读错栈（`[esp+0x1c]/[esp+0x20]` 在分支内部不是 {cur,end}）。真值应是 **819**。 |
| "帧层未定，要重新观测" | ✅ 已定，见 §1；不用再观测帧层。 |

## 4. 于是 `0xE13A` 失败的原因只剩两条

1. **解析器拿到的 `len` 不是 819**（那就说明发出去的字节在到达解码器前已经变了/错位）；
2. **`len` 是 819，但字段读取仍然失败**（那就只剩"内容语义"问题，因为线长 398/正文 817
   已经用两种独立方法核对过：alloc 1253 与 296 条指令的逐项相加，见
   `server/0xE13A-准入闸门.md` §4 与 `server/_dis_rec.txt`）。

这两条**只需要一个数**就能分开：`0xAA2D50` 收到的 `len`。
→ 用 `tools/vt_probe.py`（vtable 数据补丁）一次运行即可拿到，见
`server/下一步-2026-10-23-复盘与计划.md` P1。
