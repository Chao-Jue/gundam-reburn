# 破壳可行性评估：我们到底还差多少

> 2026-10-20。触发问题：「破壳成功的概率有多少？」
> 本文用**磁盘文件 vs 内存镜像**的逐字节比对来回答，不靠印象。

---

## 0. 一句话结论

**「破壳」在我们这个项目里已经完成了 —— 而且比预想的容易得多，
因为主代码段在磁盘上本来就是明文。真正没破的只剩 `.vmp0`（231 KB，占镜像 1.5%），
而它不在我们要走的那条路上。**

## 1. 实测数据（磁盘 vs 内存导出）

工具：`pefile` 读节表 + 逐字节比对
`launcher/.../GundamOnline_CHINA.exe`（磁盘，15,659,840 B）
vs `server/img_dump/main_GundamOnline_CHINA.exe`（内存镜像，15,654,912 B）

| 节 | RVA | 大小 | 磁盘熵 | 内存熵 | 磁盘 vs 内存 | 判读 |
|---|---|---|---|---|---|---|

| `.rsrc` | `0xE0D000` | `0x2A94` | 5.82 | 5.82 | 完全相同 | 资源，未加密 |

## 2. 关键发现：主代码段「磁盘即明文」

这条把旧结论推翻了。之前 `壳与环境分析.md` 记的是
「双层壳 Themida(外) + VMProtect(内)，`.text` RawSize=0，磁盘静态不可 patch」。

实测：

- 主代码段 `SizeOfRawData = 0xE0C000`，**不是 0**，且**有内容、熵 6.35**；
- 与内存镜像只差 **0.20%**（29,132 / 14,680,064 字节），且是散布的单点差异
  ——典型的 **IAT 修复 + 少量运行时补丁**，不是「解压后完全不同」。

**所以 Themida 保护的从来不是游戏代码，只是它自己那段壳逻辑（`ohjicybf`）。
游戏逻辑从磁盘上就能反汇编。**

这也解释了为什么 `tools/dis_img.py` 离线反汇编一直很顺、
为什么 RTTI 2850 个类名能在磁盘明文里翻出来 —— 因为它本来就是明文。

> 附带一条更正：`D:\...\MEMORY.md` 里「`.text` RawSize=0」应删掉。

## 3. 概率分解（分目标，不给单一数字）

「破壳成功概率」是个含糊的问题，得拆成四个子目标。下面的数字是**工程判断**，
依据是上面的实测数据 + VMProtect 的公开攻防现状，不是测量值。

| # | 子目标 | 概率 | 依据 |
|---|---|---|---|
| 1 | 拿到可反汇编的**游戏逻辑代码** | **100%（已完成）** | 磁盘即明文，实物 `server/img_dump/main_GundamOnline_CHINA.exe`；协议链路 `0xAD6AC0 / 0xAF6080 / 0x544790` 已全部读通 |
| 2 | 拿到 **Themida 壳自身**的明文代码 | **~90%** | 内存镜像里 `ohjicybf` 已解密（熵 7.50→6.53，48% 字节改变），**已落盘**，可直接反汇编。剩下 10% 是不确定「解包后是否还有二次加密的 handler 段」 |
| 3 | **devirtualize `.vmp0`**（还原成 x86） | **< 5%** | 见第 4 节 |
| 4 | **我们要做的功能**（大厅流程 / 表加载 / 协议 / 战斗模型） | **不依赖 .vmp0** | 见第 5 节 |

## 4. 为什么 `.vmp0` 几乎是死路

三条硬理由，任何一条单独成立就够劝退：

**① 它根本没被解密。** 磁盘和内存 0 字节差异、熵恒为 7.89
→ 运行时它就是一个**原封不动的 blob**。VMProtect 的做法是把这个段当**数据**读，
在**另外的匿名内存**里解密出自己的 VM 解释器和字节码（我们已 dump 了 128 段匿名 r-x，
共约 60 MB）。所以「dump 内存就能拿到明文」这条路对 `.vmp0` 天然无效
—— 那里的字节码本来就不是 x86。

**② 它是虚拟化，不是压缩。** 被保护函数的原生指令在编译期就被翻译成了
VM 字节码（每条原指令 → 若干条 handler 指令 + 一张随机化的 handler 表）。
即使你把 blob 完整解密，拿到的也是**字节码**，不是可反汇编的代码。
要还原必须做 **devirtualization**（符号执行 / 把 handler 语义一条条对回去）。

**③ VMProtect 3.x 没有可用的公开 devirtualizer。**
- VMProtect **2.x** 的简单 handler 有社区工具能处理（VTIL / NoVmp 等），成功率也就中等；
- **3.x** 引入了 handler 随机化、多套 VM、变异传播，公开工具基本全部失效；
- 真正能做的是**人工逐 handler 语义还原**——对 231 KB 的虚拟化段，
  这是**人数月级**的工作量，而且每换一个版本要重做。

**结论：这不是「努力就有回报」的方向，是「投入产出比接近 0」的方向。**

## 5. 好消息：`.vmp0` 里没有我们要的东西

`.vmp0` 里唯一被坐实的功能是 **CPS 反外挂驱动的分发/校验逻辑**
（`CPS_extracted.sys` 的驱动侧代码也在 `.vmp0` 段 → 所以「路线 A：直接跑驱动」不可行）。

但这条链我们**早就绕过去了**：

- 驱动链用 frida 伪造打通（`StartServiceW→1`、`CreateFileW("\\.\CPS")→假句柄`、
  `DeviceIoControl→1`），已能稳定进到休息室；
- `ACOPCShell.dll` 缺失那关用伪造 `LoadLibraryW` 成功兜住。

而真正卡住我们的「正在取得数据」在**主代码段明文**里：
`0xAF6080`（回复分发）→ `0xA4FAC0` → `0x42DA60` → `0x544F60` → `0x544790`（表匹配）
→ `0xA46480`（校验）→ switch Load → `0x9AE510`（erase）。
这些**全部已反编译、已逐个 case 读完**，没有一个字节需要破壳。

**所以：破壳不构成阻塞。当前的阻塞是「表加载器按表强类型校验，缺表占位恒被吞」，
这是数据问题，不是壳问题。**

## 6. 如果非要做，路径与预期

按性价比排序：

| 路径 | 预期 | 风险 |
|---|---|---|
| **不碰 `.vmp0`**（推荐） | 100% 够用 | 无 |
| 只读 `ohjicybf`（已解密的部分）确认反外挂手法的全貌 | 高 | 无（纯静态） |
| dump 那 128 段匿名 r-x，找出 VM 解释器做特征分析 | 中（能看清 VM 结构，但还原语义仍难） | 低 |
| 用 VTIL / 自研 devirtualizer 打 VMProtect 3.x | **极低** | 极高，数月无产出 |
| 找别人已经 devirtualize 过的同版本产物 | 需要圈子人脉，本项目无渠道 | —— |

## 7. 一句话回答

> **破壳概率 ≈ 100%，因为它已经破了**（游戏代码磁盘即明文，实物已在 `server/img_dump/`）。
> **剩下的 1.5% 是 VMProtect 虚拟化段，成功率 < 5%，而且里面没有我们要的东西 ——
