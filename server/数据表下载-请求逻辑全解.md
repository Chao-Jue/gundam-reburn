# 数据表下载：请求全链路逻辑（反编译 + 运行期实证）

> 2026-10-20。本文回答一个具体问题：**客户端到底怎么发这个请求、怎么处理回复、  
> 卡在哪一行**。所有结论都有地址或运行期数据支撑，不含猜测。



---

## 0. 一句话

客户端对 74 个表**串行**下载：发 `0xF86A(路径, hash)` → 收 `0x5290` →  
按**文件名查一张硬编码表**得到序号 → **解包** → 按序号 `switch` 调对应表的 `Load` →  
`erase` 队列节点 → 发下一条。**全流程只有一个判决点**：解包函数 `0xA46480` 的返回值。

---

## 1. 请求侧：`0xF86A` 是怎么发出来的

`_proto_lounge_client::send_datafile_download` @ **`0xAD6AC0`**（Ghidra 原样）：

```c
if (this->[0x19] && this->[3]) {
    buf = alloc(0x106);                    // 262 字节
    *(u16*)buf = 0xF86A;                   // 操作码（小端 = 6A F8）
    FUN_00a5a100(path, &pos, 0x100);       // 路径字符串 + NUL，上限 256
    *pos = hashval; pos += 4;              // 紧跟一个 u32（u32 hashval 由调用方给）
    send(buf, pos - buf);                  // vtable[0x58]
    this->[0x1A2]++;                       // 发送计数（低 32 位）
    this->->[0x1A3] += carry;              // 高 32 位
    return 1;
}
return 0;
```

**要点**

- 请求体 = `u16 0xF86A` + `路径\0` + `u32 hash`，**没有数量上限，也不遍历任何容器**。  
  它只负责"发一条"。
- 唯一调用它的薄壳是 `0xA561E0`（`hash` 固定传 **0**）。
- `0xA561E0` 的唯一调用者是 **`0x544742`**，位于 `0x5446E0`：

```c
void 0x5446E0(this) {
    if (!this->[0xC]) return;
    node = *this->[8];                              // 当前节点
    s = (node->cap < 8) ? node+0x14 : *(node+0x14); // std::string，SSO 阈值 8
    w = 0xB10F60(s);                                // string → wstring
    p = (w->cap < 0x10) ? w+4 : *(w+4);             // std::wstring，SSO 阈值 16
    0xA561E0(p);                                    // → send_datafile_download(path, 0)
}
```

⇒ **"当前要下哪一张"由 `this->[8]` 这个游标决定**，游标指向下载队列的 map 节点。

## 2. 文件名 → 序号：一张 70 项的硬编码表

`FUN_0054620` @ **`0x544620`**：

```c
undefined4 FUN_00544620(wstring* 文件名) {
    i = 0;
    name = PTR_u_AUTOEXEC;                     // 0xCB9494
    while (name) {
        if (长度相等 && 逐宽字符相等) return *(u32*)(0xCB9490 + i*8);   // 序号
        i++;
        name = *(u32*)(0xCB9494 + i*8);        // 下一项的名字指针
    }
    return 0x47;                               // 查不到 → 71
}
```

表在 **`0xCB9490`**，每项 8 字节：`[+0]=序号, [+4]=宽字符串指针`。  
**共 70 项，序号 0..69**，第 71 项是终止哨兵（seq=71, ptr=0）。

完整表（已导出，见下表）。

## 3. 回复处理：`0x544790` 是唯一入口

`0x544790` 的完整伪代码（Ghidra，已核对汇编）：

```c
void FUN_00544790(this, reply, ptr, len) {
    head = this->[8];
    node = *head;
    if (node == head) return;                       // 队列空

    遍历 map（按 名字 宽字符 + 长度 精确比较）：
        命中 ↓
        0xB08B60(ptr, len);                          // 正文拷进临时结构
        0x42D5D0();
        rc = FUN_00A46480(&src, &dst, 1);            // ★ 唯一判决点
        if (rc == 0) {
            switch (node->[3]) { ... }               // 序号 → 各表 Load
            0x9EBC20(node->[3], node+4);
            0x9AE510(&reply, node);                  // erase 节点
            this->[0x10] |= 1;                       // 置"已推进"标志
        }
        // rc != 0 → 直接 return：节点不删、标志不置、下一张不发
}
```

**序号跳转**（汇编 `0x5448FA`）：

```asm
mov  eax,[esi+0xC]        ; 序号
cmp  eax,0x46             ; 70
ja   0x544DD7             ; >70 → 直接去"推进"段（= 跳过加载但仍然推进！）
jmp  [eax*4+0x544E3C]     ; 71 项跳转表
```

⇒ **名字查不到（序号 71）的表，反而会直接通过**，因为它跳过了加载。  
这解释了为什么 `player_navi` / `season_*` 那些客户端从不请求或查不到的表不报错。

## 4. 唯一的判决点：`0xA46480`

```c
int FUN_00A46480(void *src, int dst, int packed /* = 1 */) {
    rc = FUN_00A463C0(src->[4], src->[8], &out, &outlen, packed);
    if (rc != 0) { free(out); return rc; }        // ← 失败 1
    rc = FUN_00B08AC0(outlen);
    if (rc != 0) { free(out); return 0x80100000; } // ← 失败 2
    memcpy(dst->[4], out, outlen);
    free(out);
    return 0;                                      // 成功
}
```

`0xA463C0`（`packed == 0` 走 memcpy，`packed != 0` 走 UTF-8 转 UTF-16）：

```c
if (packed == 0) {
    outlen = len - 2;
    out = malloc(len - 2);          // len < 2 → malloc(0xFFFFFFFE) → 必失败
    memcpy(out, src + 2, len - 2);
    return 0;
}
n = MultiByteToWideChar(CP_UTF8 /*65001*/, 0, src, len, NULL, 0);
if (n == 0) return 0x80100000;      // 非法 UTF-8 或 len<=0 → 失败
outlen = n * 2;
out = malloc(outlen); memset(out, 0, outlen);
m = MultiByteToWideChar(CP_UTF8, 0, src, len, out, n);
return (m >= 0) ? 0 : m;
```

**`0x544790` 传的 `packed` 是常量 `1`**，所以**所有表都走 UTF-8 → UTF-16 转换**。

       0x9BEAF0(row, this):
           if (首字符 != '#') {
               if (第0列长度 != 0) {
                   k = (**(code**)(*this+0x14))(row);     // 槽5 = 0x9DEE20 = GetInt(row,0)
                   (**(code**)*this)(row, k, local_30);   // 槽0 = 0x548980 = 行解析

- `0x9BAEF0` 是标准 RB-tree insert，比较只用 key 的第一个 dword
- `0x9B9CF0`（clear）是"释放树 + 重置哨兵"，和 msma 那张一模一样

## 9. 现在剩下的唯一可疑点

链路、对象、序号、名字、块号全部排除之后，`0x544790` 里能拦住推进的只剩一行：

```c
rc = FUN_00A46480(&src, &dst, 1);
```

它失败的两个条件：

1. `MultiByteToWideChar(CP_UTF8, 0, src, len, NULL, 0)` 返回 0  
   —— 需要 `len <= 0`，或 `src` 里有**非法 UTF-8 字节**
2. `0xB08AC0(outlen)` 返回非 0 —— 缓冲准备失败

**而 `len` 来自 `0x544F60` 对 `0x5290` 帧的解析，不是我们自己算的。**

⇒ 下一步应当反编译 `0x544F60`，核对它从帧里取的 `len` 是哪个字段、  
和我们 `datafile_block()` 写的字段是否一一对应。  
**如果 `len` 含有头字节或符号问题，#65 就会因为"长度不对"而转码失败 —— 而这与表内容完全无关。**

## 11. 补证：帧格式逐字段核对（2026-10-20 16:40）

`FUN_00af6080` @ **`0xAF6080`** 就是 `recv_datafile_download_r`：

```c
void FUN_00af6080(int result, name, hash, size_t raw_len,
                  size_t packed /* 低16位当标记 */, ptr, int body_len)
{
    if (result < 0) return;                     // 结果码为负 → 直接丢弃
    if ((short)packed == 0) {
        FUN_00a4fac0(name, ptr, body_len);      // 不压缩：正文直传
    } else if ((short)packed == 1) {
        pv = calloc(raw_len, 1);
        FUN_00bd2ab0(ptr, body_len, pv, &packed);   // 解压
        FUN_00a4fac0(name, pv, packed);
        free(pv);
    }
}
```

对照 `fake_auth.datafile_block()`：

| 帧字段 | 我们写的 | 客户端取用 | 结论 |
|---|---|---|---|
| `u32 结果` | `0` | `if (result < 0) return` | ✓ 0 合法 |
| `文件名\0` | 31 字节 | `param_2` → wstring | ✓ 与队列节点一致 |
| `u32 hash` | `0` | `param_3` | ✓ 未参与判断 |
| `u32 原始长度` | `len(data)` | `param_4`（仅 packed==1 用） | ✓ |
| `u16 压缩标记` | `0` | `(short)param_5` | ✓ 走直传分支 |
| `u32 正文字节数` | `len(data)` | `param_7` → `0xA46480` 的 len | ✓ |
| 正文 | `X\n`（2B） | `param_6` | ✓ |

⇒ **帧格式完全正确，前面 66 张的成功也证明了这一点。**
**排查方向必须从"帧"上移走。**

⇒ 下一步只有两条路：
- **(a) 用一个"能改变 `0xA46480` 结果"的对照实验**，从客户端行为反推它是否失败
  （例如把某一张已知能过的表的正文换成一串**非法 UTF-8 字节**：若它立刻失败、而正常正文通过，
  就证明该函数确实是判决点；再据此定位第 65 张的输入差异）
- **(b) 直接观测**：给 `0x5448F4` 下一次性断点读 `eax`——但客户端对调试器附加敏感，会退出。

**(a) 是唯一不杀客户端、又能定性的一枪。**

## 14. 最后一轮排除（2026-10-20 16:40~17:15）

### 14.1 对照实验：非法 UTF-8 不影响判决

把 `msma/msma_settings.csv`（第 5 张，case 4，与 case 67 同走槽 1）写成
**4 字节非法 UTF-8 `ff fe ff fe`**，其余不动。结果：**第 5 张照样通过**，队列仍走到第 65 张才停。

⇒ `0xA46480` 的失败分支**从来不会触发**。原因：`0xA463C0` 调用
`MultiByteToWideChar(CP_UTF8, dwFlags=0, ...)`，`flags=0` 时非法字节会被
**替换成 U+FFFD 而不是失败**（要失败必须传 `MB_ERR_INVALID_CHARS`）。
⇒ **`0xA46480` 不可能是判决点，之前的定位作废。**

### 14.2 逐函数排除（全部反编译过）

| 函数 | 实际行为 | 能否失败 |
|---|---|---|
| `0x9EBC20`（switch 之后） | **空函数**，`return;` | 不能 |
| `0x9AE510`（erase） | 标准 RB-tree erase；只检查 `node+0x2D`（哨兵位），有效节点不抛 | 不能 |
| `0xB08AC0`（缓冲准备） | `malloc(size)`，返回 `0x80100000` 仅当分配失败 | 2 字节不可能失败 |
| `0xA46480`（解包） | UTF-8→UTF-16 + memcpy | 见 14.1，不会失败 |
| `0x9BEC20`（Load） | clear + `0xB08960` 迭代 | 与 case 18 同一份代码，case 18 成功 |

### 14.3 case 18 与 case 67 的差异只有一格

```
case 18  CMsmaMaterialTable        槽0=0x558D10  ← 成功
case 67  CMechanicOverCustomTable  槽0=0x548980  ← 卡住
槽1/2/3/4/5 两者完全相同：0x9BEC20 / 0x9BAFB0 / 0x9BAFE0 / 0x9B9CF0 / 0x9DEE20
```

`0x548980` 只有 7 次 `GetInt`，`ret 0xc`；且槽0 的输出缓冲与槽3 的输入缓冲是
**同一个栈地址 `esp+0x54`**（Ghidra 误显示成两个变量），数据流是通的。

### 14.4 客户端自己记录了错误

XDt 解码日志（`16:43:20`，即最近一次登录之后）：

```
WARNING:  UTILITY: OPG warning: chunk ID = , code = 1
ERROR:    DLIB-DLOADER , code = 61697
```

**`DLIB-DLOADER` ERROR 61697 证明加载确实执行了并失败了**（不是"没被调用"）。
但 `DLIB` 这个标签属于保护层（XDt）的日志分类：`DLIB` / `DLOADER` 字符串在
主模块、`libmbs.dll`、`libcset.dll`、`Ng.dll` 里**全部 0 命中**，只在 `.vmp0` 里，
**静态读不到**。`61697 = 0xF101` 也不是硬编码常量（搜到的 `0xF101xx` 全是 RTTI 的 TypeDescriptor 区域）。

### 14.5 由此推出的唯一自洽解释

`0x544790` 链上**没有任何可失败的代码**（14.2），却一次都没走到 erase（节点还在）。
两条路都通向同一个结论：

- 要么 `0x544790` **没被调用**（协议层没把这条回复交给它）
- 要么 map 遍历**没匹配上**（但队首就是它、名字 31 字节逐字一致，已实测排除）

而 `0xAF6080` 是**虚函数**，占 vtable 里 `0xE14D7C` 这一格，由协议层按 opcode 选槽调用。
⇒ **下一个要读的地方是协议层的 recv 分发**（opcode → 虚函数槽），
这是整条链上唯一还没反编译过的一层。

**注意**：这也解释了为什么"改内容、改大小、改列数、改枚举"全都无效——
那些改动都作用在 `0x544790` **之后**，而问题在它**之前**。

## 15. 协议层定位（2026-10-20 16:45~17:05）

### 15.1 `recv_datafile_download_r` 的真实身份

`0xAF6080` 是 **`CGVOProtoLounge`** 的一个虚函数，**槽 30**：

```
vtable 0xE14D04 = CGVOProtoLounge
  槽27 = 0xAF6010   记录 +0x7A58 标志
  槽28 = 0xAF6030
  槽29 = 0xAF6050   7 参数薄壳 → 0xA4FA90
  槽30 = 0xAF6080   ★ recv_datafile_download_r
  ...（槽 31+ 是别的协议消息）
vtable 只被引用 2 次：0xAF8D8C（构造函数写 vtable）、0xAF8DC5（析构 0xAF8DC0）
```

### 15.2 `0xAF6080` 完整的参数布局（开头已验证）

```asm
0xAF60A5  cmp dword [esp+0x24], 0     ; param1 = result（栈帧 0x20 之后第一个参数）
0xAF60AA  jl  0xAF615B                ; result < 0 → 直接返回
0xAF60B0  movsx eax, word [esp+0x34]  ; param5 = packed 的低 16 位
0xAF60B8  je  0xAF6144                ; == 0 → 直传
...
0xAF6144: name=[esp+0x28]  ptr=[esp+0x38]  len=[esp+0x3C] → call 0xA4FAC0
```

**逐项核对我们的帧：`result=0` 不返回、`packed=0` 走直传、`name/ptr/len` 全部指向正确字段。
⇒ 调用链 `0xAF6080 → 0xA4FAC0 → 0x42DA60 → 0x544F60 → 0x544790` 是通的，不存在"没被调用"。**

### 15.3 协议对象上的状态标志

`CGVOProtoLounge` 在 `+0x7A54 / +0x7A55 / +0x7A58` 存三个标志字节
