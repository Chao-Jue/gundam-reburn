# 数据表下载：现象与结论总表

> 2026-10-20 汇总。只写**观察到的事实**和**由此得出的结论**，
> 推测一律标注为"推测"。此前的 `数据表下载-65张通过.md` 是过程稿，以本文为准。

## 一、现象（可复现的观察）

### 现象 1：客户端请求表的顺序是固定的

在 `0xF86A` 请求里读出文件名，得到固定的顺序（每次登录都一样）：

```
autoexec_sv.cfg
msma/msma_weapon_set.csv
msma/msma_weapon_equipcomb.csv
msma/msma_color_set.csv
msma/msma_settings.csv
msma/msma_model.csv
item/bullet.csv
item/equip_parts.csv
item/use_item.csv
...
```

**注意：这个顺序和 `download_list.csv` 的行序不一样**
（清单里 `item/item.csv`、`item/use_item.csv` 排在 `item/bullet.csv` 前面，
但客户端先要 bullet，item.csv 直到第 60 位才要）。
⇒ **不能再用"清单行号 - 2 = 分派序号"这种推法。**

### 现象 2：失败后会重试，且重试发生在**同一条 TCP 连接内**

一次点击登录，日志里出现 17~19 轮"从 `autoexec_sv.cfg` 开始"的序列，
但 `accept` 只出现 **2 次**。

⇒ 客户端**不重建连接**，而是在同一条连接里把整个下载序列从头再跑一遍。
⇒ 统计进度必须**按 `autoexec_sv.cfg` 切分轮次**，不能按 `accept` 计数。

### 现象 3：前若干轮都只走 2 张，某一轮突然走很远

典型的一轮（不分段发送）：

```
第 1..17 轮：每轮 2 张，停在 msma/msma_weapon_set.csv
第 18 轮   ：一遍走完 65 张，停在 develop/mechanic_overcustom.csv
```

分段发送（`--pace 64 --pace-gap 2`）时：

```
第 1..16 轮：每轮 2 张
第 17 轮   ：41 张，停在 quest/quest.csv
```

### 现象 4：能走多远，取决于前面回了多少字节

| 实验 | 回的正文 | 停在第几张 |
|---|---|---|
| A | `autoexec` 用真 `autoexec.cfg`（10222B） | **#2** |
| B | `autoexec` 用 29B 垃圾 | **#5** |
| C | 前 5 张都 2B | **#8** |
| D | 前 22 张都 2B | **#25** |
| E | **全部 74 张都 2B** | **#65** |
| F | 全部 2B + 分段慢发 | 41（另一次同配置是 65） |

⇒ **正文越小，走得越远；但结果不是确定的。**

> ⚠️ **这组数据是在旧的"连续重试"机制下测的**（一轮会被下一轮截断），
> 所以"停在第几张"这个数字混了两种原因，**不能直接当因果用**。
> 要在新机制（第二次见到 autoexec 就断开 → 干净单轮）下重测才有效。

### 现象 8：关掉重试之后，单轮仍然停在第 65 张

2026-10-20 14:56。`fake_auth.py` 已改成：同一条连接上第二次见到 `autoexec_sv.cfg` 就关掉，不再接着回。
这次登录没有出现第二次 `autoexec`，日志里只有一轮（「本轮第 N 张」）。

- 连续回了 **65 张**，最后一张是 `develop/mechanic_overcustom.csv`。
- 这一张磁盘上是 **2431 字节**（前面多张是 2 字节）。回复发出后没有第 66 张，也没有重下。
- 45 秒空闲后服务端关掉连接（14:57:15，共收 2892 字节）。界面是 `L 2:0`。

⇒ 停在第 65 张不是「前十几轮失败之后碰巧对齐」的产物。干净的一轮也停在这里。

### 现象 9：这一张改成注释行之后，队列继续走了

2026-10-20 15:12。只把 `develop/mechanic_overcustom.csv` 改成 2 字节 `X\n`，其余不动。
干净单轮仍停在第 65 张（n=239..242），没有第 66 张。和 14:56 回 2431 字节是同一个点。消息大小排除。

15:51 再把这一张改成一行注释 `#`。

- 15:51:50 回了第 65 张，正文仍是 2 字节，n 仍是 239..242。
- 客户端没有要第 66 张 `mission/mission_xwar_banpick_rule.csv`。
- 15:51:53 发来操作码 `0x70E9`。正文前三个整数是 `5, 0, 0`，后面是路径
  `C:\WINDOWS\system32\uxtheme.dll_a0ae2b2b`。
- 服务端没有这条的回复。

⇒ 同一长度、同一块号，`X` 停住、`#` 通过。卡点在这张表对非注释行的插入，不在分帧计数。
界面停在「正在取得数据」是因为 `game+0x580` 的下载对象还在；`0x544610` 只在待下载表个数为 0 时才把它释放。

### 现象 10：把**所有**表都变成注释行，反而又卡回第 65 张

2026-10-20 16:05。74 张全部写成 `#\n`（谁都不插行）→ 第 15 轮仍然停在
`develop/mechanic_overcustom.csv`，之后没有 `0x70E9`。

对比 15:51 那次（**只有这一张**是 `#`，其余是 `X`）→ 过了第 65 张并发出了 `0x70E9`。

```
15:51  #1..64 = X（各插 1 行）  #65 = #      → 过 #65 → 0x70E9 ✓
16:05  #1..65 全 = #（都不插行）            → 卡在 #65 ✗
```

⇒ **前面那些表有没有真的插入行，会影响第 65 张能否被接受。**
"全都不插行"不是更好的配置，是更差的配置。
（推测：第 65 张的插入要拿前面表里的数据做校验，前面是空表就查不到。）

**有效配置 = 73 张 `X\n` + `develop/mechanic_overcustom.csv` = `#\n`。**

### 现象 5：正文内容本身不影响通过

- 2 字节的 `X\n` 能过（65 张都过了）
- 2431 字节的"40 列 × 24 行"占位表能过
- 369 字节、**完全符合反编译规格**的 `msma_weapon_set` 能过
- 把真 `autoexec.cfg` 的 10222 字节顶着 `msma_weapon_set.csv` 的名字发过去也能过

⇒ 客户端**不校验表内容**。

### 现象 6：`Load` 的返回值不影响是否推进

对 `CMSMAWeaponSetTable` 完整反编译后确认：

- `0xB08960` 迭代器正常出口 `xor eax,eax`（返回 0），失败出口才返回 1
- 行回调 `0x9DC7F0` 恒返回 0
- 行解析 `0x551BC0` 没有任何范围校验（越界列返回 0 / 空串，枚举查不到返回兜底值）

⇒ **`Load` 恒返回成功**。它不参与"要不要发下一张"的判断。

### 现象 7：推进与否由"删节点"决定

`FUN_00544790`（0x5290 回复处理）的逻辑：

```
按 wstring 名字在待下载表(std::map)里精确查找节点
命中 → 拷正文 → FUN_00A46480（UTF-8 → UTF-16）
      返回 0 时：switch(序号) 调各自 Load → FUN_009AE510 = std::map::erase → 置标志
      返回非 0：直接 return（节点不删，也就不会要下一张）
```

运行时实测（卡住时读内存）：
- `msma/msma_weapon_set.csv` 的节点**在**（`+0x0C` 序号 = 1，名字 24 字符完全一致）
- `autoexec_sv.cfg` 的节点**已被 erase**（对照组）
⇒ 名字查找是命中的，卡点在「查找到 erase 之间」。

## 二、已排除的假设（都做过实验）

| 假设 | 排除依据 |
|---|---|
| 表内容/列数/枚举值不对 | 2 字节 `X\n` 通过率最高；完全符合规格的表反而不行 |
| 地区标签过滤 | 反编译直读：只有 `JAPAN` 行被跳过，其它任意值都收 |
| `Load` 返回失败 | 迭代器正常出口恒返回 0；回调恒返回 0 |
| 行解析抛异常 | `0x551BC0` 无校验、无跨表查找、无可抛点 |
| 名字查找失败 | 运行时读到节点在、序号对、名字一致 |
| TCP 拆包导致客户端错位 | 加 `--pace 64 --pace-gap 2` 分段慢发后**更差**（41 vs 65） |
| `--sweep` 异步发帧污染计数器 | `args.login_seq = bool(args.sweep and not args.sweep_list)`，login_seq 为真时 sweep 线程不启动 |
| `autoexec.cfg` 里有影响下载的配置键 | 全文只有 `wnd_*` / `camera_*` / `misc_client_bogo_version`，无表/下载/版本相关键 |

## 三、结论

1. **卡点不在"表数据的字段值"，但"有没有数据行"是决定性的。**
   ~~客户端对表内容零校验~~ **【15:58 修正：说法过强】**
   准确的表述是：**字段值不参与任何校验**（列数、枚举、地区、数值都能随便填），
   但**"这一行要不要真的插进表"会决定成败**——
   一行注释（以 `#` 开头）会被行回调跳过，不插入、不抛异常；一行真数据会走插入路径，
   插入途中抛异常就被 `0x544790` 的 SEH（`0xC47580`）吞掉，于是不删节点、不置标志、不推进。

   ⇒ 正确的一句话：**失败发生在"插行"，不在"读字段"。**

2. ~~**能不能推进，取决于这次连接里此前回了多少数据**，存在状态残留/累计效应。~~
   **【2026-10-20 15:02 修正：此条撤回】**
   依据：见现象 8。用"同一条连接上第二次见到 `autoexec` 就断开"做成**干净单轮**后，
   一轮仍然稳定停在 #65。⇒ 停在哪一张**不是**重试累积的产物。
   A~E 那组"越少字节走得越远"的数字是在**旧的连续重试机制**下测的，
   每轮被前几轮的残留污染，**不能作为因果证据**；要用干净单轮重测才有效。

3. ~~**"前十几轮只走 2 张、某一轮突然走很远"是同一个连接内的连续重试，
   前几次失败会在连接内留下状态，直到某次"对齐"。**~~
   **【修正】现象成立（重试确实在同一条连接内），但它不是 #65 的原因。**
   它只是让**旧日志里的"停在第几张"这个数字不可信**——因为一轮的结束可能只是
   被下一轮的开始截断，而不是真的卡住。

3'. **【15:51 再修正】#65 卡在非注释行的插入，不卡在消息大小。**
   `X\n`（2 字节）和 2431 字节都停在这一张，块号都是 n=239..242。
   改成一行 `#` 之后，同样的块号被消费，客户端接着发 `0x70E9`，不再要第 66 张表。
   `0x544790` 有异常处理（`0xC47580`）：`Load` 途中抛异常就直接返回，不删节点、不置标志。
   注释行不插入，所以能删节点。

4. **反编译"客户端行为"这条路基本走不通。**
   - 主模块导入表只有 `kernel32.dll` / `comctl32.dll`，网络 API 全是壳运行时动态解析
     （镜像里连 `ws2_32` 字符串都是 0 命中）
   - 按 MSVC COL 布局反查 RTTI 的 vtable：0 命中（三种写法都试过）
   - 唯一能拿到的是明文 RTTI 类名，能看出**架构**但定位不到函数：
     `iCryptSession<TcpStream, CamelliaCrypter>` / `iTcpStream` / `iSocket` /
     `rymPacketBuffer` / `rymStream` / `rymSocket`

5. **当前进度**：第 65 张用注释行可以过去。客户端下一步是 `0x70E9`
   （模块路径 `uxtheme.dll` 加 8 位十六进制后缀），不是下一张 CSV。
   服务端还没有这条的回复。

## 七、下一个卡点：`0x70E9`（模块完整性校验）

第 65 张通过之后，客户端不再要第 66 张 CSV，而是发 `0x70E9`。抓到两条：

```
u32 5 | u32 0 | u32 0 | "C:/WINDOWS/system32/uxtheme.dll_a0ae2b2b/0"     (54 字节)
u32 5 | u32 0 | u32 0 | "C:/WINDOWS/System32/MSCTF.dll_36bd5c96/0"       (52 字节)
```

- 三段 u32 固定是 `5, 0, 0`
- 后面是 **ASCIIZ 路径**，末尾 `_` + 8 位十六进制（像 CRC32）
- `uxtheme.dll` / `MSCTF.dll` 都是典型的 **COM 劫持/注入目标**
⇒ 这是**反外挂的模块完整性校验**：客户端把被检查模块的路径和摘要报给服务端，等服务端裁决。

**现状**：服务端没有这条的回复，客户端等 45 秒超时断开。

**找代码的进展**：`uxtheme` / `MSCTF` 这两个字符串在主模块里 **0 命中**，
只在 `server/img_dump/anon_0x*` 这些**已加载的系统 DLL 段**里出现
⇒ 被检查的模块清单不是明文写死在游戏主模块里的（运行时枚举或另有加密来源），
所以不能靠搜字符串直接定位发送函数。

**回复格式待定**。可选思路：
1. 先从 `0x70E9` 的分发找到处理函数（难点：操作码不是 16 位立即数比较，288 个 2 字节命中全是噪声）
2. 经验试错：回一个「同样的 opcode + u32 0」或复用现成的 ok 块结构，看客户端是否继续
3. 若客户端对「不回复」也能继续（只是等超时），可以考虑不回

### 现象 11：同样的文件配置，15:51 能到 `0x70E9`，16:08 又卡回第 65 张

两次的磁盘配置完全一致（73 张 `X\n` + `develop/mechanic_overcustom.csv` = `#\n`）。

| 时间 | 轮次结构 | 结果 |
|---|---|---|
| 15:51 | **只有 1 轮**，65 张 | 过 #65 → 发出 `0x70E9` ✓ |
| 16:08 | **14 轮各 2 张**，然后第 15 轮 65 张 | 卡在 #65 ✗ |

⇒ 差别不在文件内容，而在**"这一轮之前有没有发生过失败的重试"**。
15:51 是客户端**刚启动后的第一次尝试**，一次到底；
16:08 是客户端**已经在跑**、前面失败了 14 次之后才走远。

**目前最可信的猜测**：客户端在一次"失败重下"之后会进入某种脏状态，
导致后面即使跑到 #65 也无法接受那一张。
⇒ **做这类实验前应当把客户端整个重启**，让第一次尝试就是干净的。

（注意：`accept` 只有 2 次却出现 15 轮，说明"轮"是同一连接内被服务端主动断开后重连的产物，
这一点仍与现象 2 一致。）
