## 1. 新增的硬事实（离线静态，可直接依赖）

### 1.1 `0xAA2D50` 的真实身份 = `CGVOProtoLounge::on_message(buf, len)`

```
vtable @ 0xE14D04  ← RTTI 已解析：.?AVCGVOProtoLounge@@
  +0x54 (0xE14D58) = 0xAA2D50        ← 单条报文处理器
  +0x80 (0xE14D84) = 0xAF6170        ← 上一轮说的"成功回调 thunk"→ FUN_00439190
```

`0xAA2D50` 函数体（`0xAA2D50..0xAA2DA4`）：

```
mov edi,[ebp+8]      ; buf
mov ebx,[ebp+0xc]    ; len
lea eax,[edi+ebx]    ; end = buf + len
mov [esp+0x1c],edi   ; reader.cur = buf
mov [esp+0x20],eax   ; reader.end = end
call 0xa5a330        ; 读 u16 = opcode
→ 一长串 cmp/sub 的二分比较链（0xacfb0c 起），eax==0xE13A 时 jmp 0xACFE1F
```

⇒ 进到 `0xE13A` 分支时，`(buf,len)` **已经由上层分帧决定**，`len` 含 2 字节 opcode。
⇒ 想验证"帧层 >255 到底怎么封装"，**看这一层就够**，不需要再猜 `clientBody`。

### 1.2 ★ `0xE13A` 分支入口的准入闸门（**本轮最关键的新发现**）

```
0xACFE1F  push 0xc
0xACFE21  mov  ecx, esi          ; esi = 协议对象(this)
0xACFE23  call 0xa93e40          ; ← 闸门
0xACFE28  test al, al
0xACFE2A  je   0xad5e25          ; 不过 → 直接 ret 8，什么也不做
0xACFE30  ...                    ; 过了才分配 1253 字节、开始读字段
```

`0xa93e40(this, code)` 内部：

```
cmp byte [edi+ebx+0x29e], 0      ; flag[this + 0x29e + code]
jne ok
  vt[0x64](code, 2)              ; 报错码 2 → 返回 false
ok:
  esi = this + ((code*3 + 0x4e) << 4)   ; 每个 code 一块 0x30 字节的状态块
  if ([esi+0x10] | [esi+0x14]) == 0  → 跳过检查
  else 比较 [esi],[esi+4] 与 [esi+8],[esi+0xc] 两个 64 位序号
       越界 → vt[0x64](code, 3) → 返回 false
```

⇒ **每个操作码都有"当前允不允许"的标志位 + 一块 48 字节的配额/速率状态**
（`{已收计数 u64, 上限 u64, 周期 ms u64, 上次清零时刻 u64}`，`0xa5d2d0` 到点清零）。
⇒ `code = 0xc`（`0xE13A` 分支自己的通道号，不是 opcode），`flag` 在 `this+0x29e+0xc`。
⇒ ⚠️ **P0 已做完，结论见 `server/0xE13A-准入闸门.md`：闸门默认恒放行（标志默认全 1、
没有任何写入 0 的代码；周期默认 0 = 不检查）⇒ 它不是本次卡点，这条假设已自我否证。**

### 1.3 顺带修正两条旧说法

- `0xad5e15` 不是"成功"，它是**所有分支的统一收尾**（写 `-1` + `call 0xbd2890`），
  闸门失败直接落到 `0xad5e25`（同一段收尾）。**别再拿"跳到 0xad5e25"当成功判据**。
- `FUN_00439190` 开头有 **6 组**"遍历监听者数组 → `vt[0x5c](result)`"，
  分别取 `game+0x10638/0x10660/0x10648/0x10670/0x10688/0x10698`。
  ⇒ 关掉那个模态窗的**很可能就是这 6 个监听者之一**，不是 `+0x10615`。这与
  "poke 10615 能切界面但窗不关"完全一致。

## 3. 计划（进度：P0 已完成 ✅ / 帧层已定案 ✅ / 只剩 P1 需要开客户端）

### P0 ✅ 已完成（2026-10-23 17:40）

产出两份：`server/0xE13A-准入闸门.md`、`server/帧层-定案-0xbd1610.md`。

| 问题 | 结论 |
|---|---|
| 闸门会不会拦 `0xE13A`？ | **不会**。标志数组默认全 1 且全镜像无写入 0；配额块默认全 0 ⇒ 跳过检查。所以它**不是**本次卡点。 |
| `k=1` 的 2 字节长度能不能用？ | **能**。解码器 `0xBD1610` 明写 `len = buf[1] \| buf[2]<<8`（k≥1），k=0..3 都合法。 |
| 长度字段算不算 opcode？ | **算**。`len` = 载荷长度 = `opcode(2) + 正文`，本帧总长 = `len + k + 2`。 |
| 我们的封装对不对？ | **逐字节吻合**。按反汇编重写解码器回读 `op_block()` 输出：817/252/254/2431 四种全部 `PASS`，剩余 0 字节，16 字节对齐的 dummy 帧（`opcode 0xFFFF`）被整帧吃掉。 |
| 记录线长 398 / 正文 817 对不对？ | **独立复核为 398 / 817**（296 条指令逐项相加：38×u32 + 3×u16 + 6×u8 + 116+31+31 循环 + 25 名字 + 13 内联 + avatar 18 = 398）。 |

⇒ 三条"为什么 0xE13A 失败"的候选（帧层 / 闸门 / 线长）**全部被排除**，
只剩：解析器拿到的 `len` 不是 819（线上字节变了），或者拿到 819 但内容语义不满足。
**这两条只差一个数**，就是 P1。

### P1 一次开客户端：用 **vtable 数据补丁**做无侵入观测（替代被禁的 inline hook）

上一轮的铁律是"不许在 `0xAA2D50` / `0xAA2DA4` 挂 hook，CPS 校验代码字节"。
但 **0xAA2D50 的地址同时存在于数据段 `0xE14D58`**，所以可以只改**数据**：

```
Memory.protect(0xE14D58, 4, 'rw-')
写入手工 stub（放在我们自己 Memory.alloc 的页里，不在客户端模块内）：
   pushad
   push [esp+0x28]      ; len
   push [esp+0x28]      ; buf
   mov  eax, <logfun>   ; NativeCallback，cdecl 2 参
   call eax
   add  esp, 8
   popad
   push <0xAA2D50>
   ret                  ; 尾调原函数，ecx=this 未被破坏
```

- 客户端代码段**一个字节都不改** → CPS 的字节比对看不到。
- 记录内容：`len`、`opcode`、`buf` 前 16 字节、时间戳。
- **一次运行就能同时回答三件事**：
  1. 我们发的 `01 33 03 3a e1 ...`（817 正文）到这一层 `len` 到底是 819 还是 49/510
     → 帧层 >255 语义定案（这是全链路的根问题，`0x063E` 51KB 也靠它）；
  2. `0xE13A` 有没有真的进到分支（配合 P0 的闸门结论）；
  3. 后面每一条入站消息的真实长度，等于白送一张全链路的"报文长度表"。
- 验收：`server/vtable_probe.log` 里出现 `op=0xe13a len=819` 这类行。
  若 `len` ≠ 819，则**帧层就是根因**，先去修 `_kind0`；若 `len=819`，
  则根因在闸门/内容，走 P2。
