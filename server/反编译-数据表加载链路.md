> 来源：Ghidra 11.4.3 对 `server/img_dump/main_GundamOnline_CHINA.exe`（解包镜像，基址 0x400000）
> 的反编译结果，已与 `tools/dis_img.py` 的汇编逐条交叉核对。
> 原始伪代码：`server/decomp_caller.txt`（0x544790）、`server/decomp_tbl.txt`（Load/行解析）、
> `server/decomp_csv.txt`（迭代器/文本解析）、`server/decomp_unpack.txt`（解包）、
> `server/decomp_idx.txt`（case 1 的额外排序）、`server/decomp_body.txt`（容器/map erase）。

## 一、整个流程（C 代码级）

```
0x5290 回复报文
  → FUN_00544F60( name_utf8, content_ptr, content_len )
      → FUN_00B110C0   name 由 UTF-8 C 串转成 std::wstring（CP_UTF8 = 0xfde9）
      → FUN_00544790( this, name, content_ptr, content_len )
```

`FUN_00544790` 是核心，逻辑如下（简化后）：

```c
node = 待下载表.first();
if (node == end) return;                      // 表空
while (node->name != name) node = next(node); // 按名字精确匹配（wstring 逐字符）
if (没找到) return;                            // ← 静默返回，什么都不做

assign(&src, content_ptr, content_len);        // 拷正文
ok = FUN_00A46480(&src, &dst, 1);              // 解包 / 转码
if (ok == 0) {
    switch (node->index) {                     // +0x0C
        case 0:  FUN_009EEEF0(&dst); break;                    // autoexec
        case 1:  ((void(*)(void*))*(void**)DAT_01169A48)(&dst); // CMSMAWeaponSetTable::Load
                 FUN_005517C0(DAT_01169A48);  break;           // 额外：给每个桶排序
        ...  case 0..0x46 共 71 个
    }
    FUN_009AE510(&name, node);                 // std::map::erase —— 删掉节点
    *(this + 0x10) |= 1;                       // 置"已处理"标志
}
// 只有删了节点，下载管理器才会发下一条请求
```

**关键**：`FUN_009AE510` 是 `std::map::erase`。节点不删 → 永远不会请求下一张表 → 界面停在
"正在取得数据" → `--idle 45` 把连接掐掉。这就是我们看到的全部现象。

## 二、节点（待下载表项）的内存布局

| 偏移 | 含义 |
|---|---|
| `+0x00 / +0x04 / +0x08` | 红黑树 left / parent / right |
| `+0x0C` | **文件序号**（switch 的 key，0..0x46） |
| `+0x14 …` | 文件名（std::wstring，24 字节） |
| `+0x2D` | isNil 标志 |

哨兵在 `[表对象 + 8]`。这解释了"为什么按名字找节点时全内存没有指针指向那些字符串"——
名字是内联在树节点里的，节点本身早就被 erase / 或者当时还没建。

## 三、Load 与行解析（`CMSMAWeaponSetTable`）

```c
bool CMSMAWeaponSetTable::Load(text) {          // 0x9DC930
    clear();                                     // 0x9DC860
    return FUN_00B08960(text, 2, 0x9DC7F0, this, PTR_DAT_01089148, 3) == 0;
}
```

`0xB08960` 通用 CSV 迭代器：

```
0xB08DC0(文本, 跳过前 2 行, ...)   切行准备
loop:
    if (0xB08CD0() == 0) break;    // 取下一行（内部 _wcstok(text, L"\n")）
    if (回调(行) != 0) { 失败出口 → 返回 1 }
返回 0
```

汇编核对：**正常出口 `xor eax,eax`（0），失败出口 `mov eax,1`**。

行回调 `0x9DC7F0`：取第 0 列首个 wchar，`!= '#'` 就 `0xB081E0(row,0)` + `0x551BC0(row)`，
**末尾恒 `xor eax,eax; ret`（返回 0）**。

⇒ **`Load` 永远返回成功**。它的返回值不参与"是否推进"的判断。

行解析 `0x551BC0` 的反编译已拿到（`server/decomp_tbl.txt`），确认：

- 读列 `0,2`（整数）、`4,5`（枚举串）、`6,7`（整数）、`8..19`（3 组循环）、`22`、
  `24,25,26,27`（整数）、`28`（地区串）
- 地区判断：**只有 `"JAPAN"` 的行被跳过**，`CHINA` / `ALL` / 其他任意值都会收
  （`bVar11 = true` 在 else 分支里是无条件赋值）
- 收行路径：`FUN_00557FB0`（红黑树 find）→ 查不到就走新建 → `FUN_0064ABC0`
  （`std::vector::push_back`，元素 **0x58 = 88 字节**）→ `FUN_00551670`（vector 拷贝构造）
  → `FUN_00551B00`（map 插入）

## 四、case 1 独有的那一步（`FUN_005517C0`）

```c
void FUN_005517C0(this) {                  // 0x5517C0
    for (每个桶 in this->map)
        FUN_00551520(bucket.begin, bucket.end, count, &LAB_005506E0);  // 排序
}
// 比较器 0x5506E0: return a[0x18] < b[0x18];   ← 只比整数，不查表、不抛
```

**这是 case 0（autoexec）没有的**，是唯一的结构性差异。但它不会抛异常，所以不是卡点。

## 五、解包 / 转码（`FUN_00A46480` → `FUN_00A463C0`）

```c
int FUN_00A463C0(ptr, len, &out, &size, flag) {
    if (flag == 0) {                    // 不转码：**丢掉正文前 2 字节**，其余照拷
        *size = len - 2; malloc; memcpy(out, ptr + 2, *size); return 0;
    }
    n = MultiByteToWideChar(CP_UTF8, 0, ptr, len, NULL, 0);   // 0xfde9 = 65001
    if (n == 0) return -0x7ff00000;                           // ← 唯一的内容相关失败
    out = malloc(n * 2); memset(out, 0, n * 2);
    MultiByteToWideChar(CP_UTF8, 0, ptr, len, out, n);
    return 0;                                                  // 恒 0
}
```

调用方恒定传 `flag = 1`，所以：

- 正文被当作 **UTF-8 文本**转成 UTF-16
- 报文里的"压缩标记"实际不起作用（那条 `flag==0` 的分支走不到）
- 唯一的失败条件是**正文 0 字节**（`MultiByteToWideChar` 返回 0）

## 六、因此，卡点的候选只剩两条
