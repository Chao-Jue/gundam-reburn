# 壳与环境闸：Themida 反虚拟机（当前的主阻塞）

> 2026-10-14 第二轮。前置：`server/分析与绕过方案.md`（驱动链那关）、
> `server/绕过实现与验证.md`（frida 伪造驱动链）。
>
> 一句话结论：**保护模块那关已经能稳定骗过；但现在卡在更外层的一道
> Themida 反虚拟机检查上，而它是被"本机暴露了 hypervisor"触发的 —— 这是环境问题，
> 不是软件问题。**

---

## 1. 发现：exe 是 Themida + VMProtect 双层壳

`GundamOnline_CHINA.exe`：ImageBase `0x400000`，15,659,840 字节，6 节：

| 节名 | RVA | 虚拟大小 | 熵 | 判读 |
|---|---|---|---|---|
| `'   \0    '` | `0x001000` | `0xE0C000` | 6.35 | 主体代码 |
| `.rsrc` | `0xE0D000` | `0x002A94` | 5.82 | 资源 |
| **`.vmp0`** | `0xE10000` | `0x0389C3` | **7.89** | **VMProtect** |
| `.idata` | `0xE49000` | `0x001000` | 0.22 | 导入表 |
| **`ohjicybf`** | `0xE4A000` | `0x0A3000` | **7.50** | **Themida**（随机节名） |
| **`esllbfpk`** | `0xEED000` | `0x001000` | 0.61 | **Themida** |

直接字符串搜索能在 exe 里搜到 `Themida`。

所以之前"只有 VMProtect"的判断需要修正：**外层是 Themida，内层（保护模块）才是 VMProtect。**
这也解释了为什么改被保护模块的机器码没用 —— 外面还有一层在做完整性/环境检查。

---

## 2. 决定性证据：谁弹的、从哪弹的

之前一直抓不到那两个弹窗，因为：

- 它们**不走 `MessageBoxW/A`**；
- 它们是**未公开 API `MessageBoxTimeoutA/W`** —— 这正是各种壳用来躲常规 hook 的手段。

补上 hook 后立刻抓到：

```
MessageBoxTimeoutA   caller = USER32.dll+0xaa11b
  bt = [ USER32.dll+0xaa11b,
         GundamOnline_CHINA.exe+0xE899C7,   <-- 落在 ohjicybf(Themida) 节内
         KERNEL32.DLL+0x15d49, ... ]

窗口: title = "Themida"
      text  = "Sorry, this application cannot run under a Virtual Machine"
```

结论：**是 Themida 自己的代码弹的**，跟游戏逻辑、跟保护模块都无关。

`_run12.out` 里的时序（很干净）：

```
17:38:20  31 个保护模块工作线程 (start = exe+0xE4B20F) 全部起来
17:38:21  Themida 弹反虚拟机窗口            <-- 距启动约 1.2s
          ...保护模块的驱动链（CreateFileW CPS.sys / SCM / IOCTL）根本没机会跑
```

## 3. 根因：本机对用户态暴露了 hypervisor

Themida 的反虚拟机判断读的就是 CPUID。本机的实测值（`tools/cpuid_probe.py`）：

```
CPU vendor          : 'GenuineIntel'
CPUID max leaf      : 0x00000020
CPUID.1:ECX bit31   : 1      <-- 1 = 存在 hypervisor
```

旁证：

| 项 | 值 |
|---|---|
| `Win32_ComputerSystem.HypervisorPresent` | **True** |
| `bcdedit` `hypervisorlaunchtype` | **Auto** |
| Windows 可选功能 `VirtualMachinePlatform` | **Enabled** |
| `Win32_DeviceGuard.VirtualizationBasedSecurityStatus` | **2（在跑）** |

也就是说：**Windows 自己就跑在 Hyper-V 的根分区里**。
只要启用了 Hyper-V / 虚拟机平台 / VBS 中任意一项，CPUID 的 hypervisor 位就会亮，
一个 2017 年、带反虚拟机检查的客户端就会拒绝启动。

> 附带说明：这也解释了为什么老驱动 `CPS.sys` 加载不了 —— 同一套虚拟化/CI 强制策略。

---

## 4. 修法：把 hypervisor 从环境里拿掉（需要重启）

### 最小改动（推荐）

```bat
:: 管理员 CMD
bcdedit /set hypervisorlaunchtype off
:: 重启
```

回滚：

```bat
bcdedit /set hypervisorlaunchtype auto
```

这条只让**虚拟机监控程序不再随系统启动**，功能本身仍装着；
重启后 `HypervisorPresent` 应为 `False`，`CPUID.1:ECX bit31` 应为 `0`。

### 更彻底（可选，二选一即可）

```powershell
# 管理员 PowerShell：关掉"虚拟机平台"功能（WSL2/Sandbox 会一起失效）
Disable-WindowsOptionalFeature -Online -FeatureName VirtualMachinePlatform -NoRestart
```

### 副作用（必须知情）

关了 hypervisor 之后，这些暂时不可用，**回滚 + 重启即可恢复**：

- WSL2 / WSLg（本机 `Microsoft-Windows-Subsystem-Linux` 本来就是 Disabled）
- Windows Sandbox、Windows Subsystem for Android
- Docker Desktop（WSL2 后端）
- VBS / 内存完整性 / Credential Guard
- 少数依赖 VBS 的游戏反作弊（如 Vanguard 的新模式）

### 重启后怎么验证（按顺序）

```bat
:: 1) 确认 hypervisor 没了
python tools/cpuid_probe.py            :: 应该输出 CPUID.1:ECX bit31 = 0
:: 2) 纯净启动，看是否还弹 49236 那个"OS 不支持"框
python tools/plain_launch.py --seconds 40
:: 3) 如果 2) 还是失败，再上 frida 伪造
python tools/run_hooked.py --no-elevate --seconds 60
```

**乐观预期**：hypervisor 关掉后，老驱动 `CPS.sys` 有可能**真的能加载**
（虚拟化强制的那部分 CI 失效了），那样第 2 步就直接过 —— 连 frida 都不需要。
如果驱动仍被"易受攻击驱动阻止列表"挡住，就继续用第 3 步的伪造。

## 5. 为什么不在软件层硬碰 Themida

- 反虚拟机判断用的是 **`CPUID` 指令**，不是某个 API。ring 3 无法拦截指令。
- 真要在进程里改，只能去 patch Themida 虚拟化过的代码
  （调用点 `exe+0xE899C7` 在 `ohjicybf` 节）—— 既打不准，又会撞上 Themida 的自校验。
- 兜底手法（hook `MessageBoxTimeoutA` 让窗口秒关）**没用**：
  按壳的常规写法是"弹窗 → 终止进程"，关掉窗口只会让它更快结束。

## 6. 其它新事实（顺手记下）

- **错误码/文案是"张冠李戴"的**：
  - `49236 (0xC054)` + `0xFFFF0002` → 文案「抱歉，游戏暂不支持您现在所使用的操作系统…」，
    实测来自**驱动加载失败**，不是 OS 判断、更不是"没提权"。
  - `49234 (0xC052)` + `0x2` (`ERROR_FILE_NOT_FOUND`) → 开 `\\.\CPS` 失败那条。
  - run11 那句「屏幕分辨率小于要求的尺寸…必须大于 1024×768」很可能同样是错位文案：
    本会话 `SM_CXSCREEN=1536 / SM_CYSCREEN=864`，是满足条件的。
- **兼容性垫片已挂**：`HKCU\...\AppCompatFlags\Layers` 里
  `GundamOnline_CHINA.exe => ~ WIN7RTM`（运行时因此加载 `AcLayers.DLL`）。
  也就是说"骗过 OS 版本检查"这步前人已经做了。
- **`ACOPCShell.dll` 不总是被请求**：run11 全程没有它的加载记录。
  它要提供的导出名已从内嵌模块字符串表拿到：
  `InitAcopc / InitSystem / RegisterApi / IntegrityCheck / Release / Scan /
   SecurityCallApi / SetSpeedGearCallBack / UpdateScanEngineHdb / ZESecurityCallApi`
  （内嵌模块自身还导入 `cps.dll / imagehlp.dll / zlib1.dll / mscoree.dll`）。
- **`CPS` 残留清理必须走 SCM**：只删注册表键的话，SCM 内存里还留着这条服务，
  下一轮客户端会走 `OpenService` 分支、日志出现 `Last Error Before Open = 1073`。
  `tools/clean_cps.py` 已改成先调 `DeleteService`。

## 7. 本轮新增/修改的工具

| 文件 | 说明 |
|---|---|
