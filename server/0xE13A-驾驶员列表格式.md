# 0xE13A = `recv_pilot_list_get_r`：驾驶员列表回复的完整格式

> 2026-10-22。这一关是「正在取得机师数据」的唯一出口。

---

## 1. 操作码是 `0xE13A`

`FUN_00aa2d50` 是 `CGVOProtoLounge` 的**总分派器**（不是某个解析器）：
它先读正文第一个 u16，然后一个巨大的嵌套 `if (uVar3 == 0xNNNN)` 树。

从里面提取到 **172 个 opcode 及其名字**（每个 case 结尾都有
`_proto_lounge_client::recv_xxx` 的调试串）。驾驶员列表那条是：

```
0xe13a  recv_pilot_list_get_r
```

> 顺带确认：这个 opcode **不在**我们之前 46 个候选里（`0x1000..0xA000 step 0x400`
> + `0x60CE..0x60D6`），所以那一轮一个都没命中——界面从「正在取得数据」
> 变成「正在取得机师数据」，纯粹是 **poke 把状态机从 case 5 推到 case 7** 的结果，
> 而 case 8 就在等这条回复。

## 2. 回复正文的字段（顺序来自 `uVar3 == 0xe13a` 分支）

```c
result                    u32
pilots_eff                u32 count，然后 count × 212 字节
pilots_zeon               u32 count，然后 count × 212 字节
del_remain_sec_eff        u32
del_remain_sec_zeon       u32
charge_point              u32
bmgpack_list              u32 count（≤ 0x10，超了直接走错误 0xc,1），然后 count × 12 字节
is_tutorial_end           尾部标志
```

末尾还有一道校验：**游标必须正好走到正文末尾**，否则 `(*(*this+100))(0xc,1)` 报错。

## 4. 三个序列化原语（都在 `server/decomp_serial.txt`）

| 函数 | 行为 |
|---|---|
| `FUN_00a5a310(dst, &cur)` | **读 4 字节**（有越界检查），失败返回 0 |
| `FUN_00a5a270(&p, &cur)` | **读 4 字节**（**无**越界检查），一般是"数组起点" |
| `FUN_00a5a360(&p, &cur)` | 读尾部标志（`is_tutorial_end`） |

## 5. 下一步：先用「全 0 的合法骨架」试

所有 count 取 0 时，正文骨架只要：

```
u32 result=0
u32 n_eff=0
u32 n_zeon=0
u32 del_eff=0
u32 del_zeon=0
u32 charge_point=0
u32 n_bmg=0
+ is_tutorial_end 那几个字节
```

也就是 **28 字节 + 尾部标志**。先发 32 字节全零试：

- 若客户端接受 → `+0x10615` 被置 → 界面进到"选机师/新建机师"
  （**0 个机师时应该出现"新建机师"入口**，这正是用户提出的合理预期）
- 若解析失败 → 会走 `(0xc,1)` 错误分支，不会崩（每个字段都有越界检查）
