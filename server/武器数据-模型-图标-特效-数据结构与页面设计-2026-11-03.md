# 武器数据 · 模型 · 图标 · 特效：数据结构与复核页面设计（2026-11-03）

这一轮不改代码，先把「一条武器数据要同时确定模型、两套图标、两组特效」这件事的结构定下来。
文中的数字都是本机实测，不是估计；只有工作量估算是估计，已单独标注。

## 1. 为什么必须先定结构

现在的三个工具各管一段：`weapon_icon_match` 管 Wiki 图标→客户端格纳库图标，
`weapon_threeway` 管模型→两套图标，`weapon_effect_match` 管特效库→武器模型。
它们之间没有共同主键，所以「同一个模型有 5 条武器数据、每条数据特效不同」这件事表达不出来——
而这正是你说的问题。

## 2. 实测数据规模（决定页面怎么排）

| 实体 | 数量 | 来源 |
|---|---|---|
| Wiki 武器行（武器数据） | **5855** | `server/reference/wiki/units.json`，751 个机体 |
| 其中写了「图片名称」的行 | 2558 | 其余行没有图标信息，只能靠同组继承或人工补 |
| 不同「图片名称」 | **1028** | 复用极高：`头炮1` 被 149 行共用、`联邦手雷1` 50 行 |
| 客户端武器外观（模型） | **2427** | `item/**/EM_*.dxg`，2296 个能解析出网格 |
| 格纳库图标 | **5192** | `interface/icon/item/s/*.dds` |
| 战场内图标 | **1023** | `interface/icon/battle/b/*.dds` |
| 可播放特效 | **5257** | `fx/**` 去掉 `attr/PZ_*` 后的 VRA |

**图标不能从模型号推出来**：按 `s`/`b` + 8 位资源号直接对，模型只有 1227 个命中格纳库图标、
**76 个命中战场图标**，两者都有的只有 62 个。所以图标必须是独立的一层决策，
不能挂在模型上顺带得到——这一点和你的箭头（数据→仓图标→战图标）一致。

另：751 个机体里有 **389 个武器表是空的**（模板未覆盖），这 389 个机体不进复核队列，
但要在页面上显示成「未采集」，否则会以为是做完了。

## 3. 关系怎么落

```
            ┌──────────────┐
   1028 ───▶│  icon_pair   │  仓图标 ↔ 战图标（1:1，成对存在或都不存在）
   （图标名）└──────┬───────┘
                    │ 1:1
   ┌──────────┐     │        ┌──────────┐
   │  model   │◀────┼────────│weapon_   │   ← 5855 行，复核主键
   │ 2427 个  │ n:1 │  data    │
   └──────────┘     │        └────┬─────┘
                    │             │ 1:0..2
                    │        ┌────▼─────────┐
                    │        │ effect_group │  mode=normal / alt（F 切换）
                    │        │ 5 个槽位      │
                    └────────┴──────────────┘
```

三条必须写进校验的规则：

1. **一条数据最多两组特效，mode 不能重复**。alt 只在「该武器确实有 F 切换」时出现，
   没有就是 1 组，不允许用空组占位。
2. **icon_pair 要么两套都有，要么都没有**。只填仓图标不填战图标 = 半成品，页面上要标黄。
3. **人工确认过的边不得被自动覆盖**。批量套用只作用于 `unknown`/`candidate`，遇到 `confirmed` 停下并列出冲突。

`schema/weapon_review.schema.json` 是可直接校验的版本，四条主线各自成表、用 id 互指，
每条边都带 `status` / `evidence`（source、score、来源引用）/ `updated_at`，另有追加式 `review_log`。
**不把模型名、图标路径、特效路径塞进同一行**——它们会被分别修正、分别重跑候选，塞在一起每次都要整体重写，
也没法表达「149 行共用同一个图标决策」。

## 4. 复核的三个层级（这是效率的关键）

| 层 | 决策 | 规模 | 一次决策影响 | 候选来源 |
|---|---|---|---|---|
| L1 图标 | Wiki 图标名 → 客户端仓图标（战图标按名配同号） | 1028 | 平均 5.7 行，最高 149 行 | 图像相似 top-N（现成算法）+ 名称前缀 + 同机体已确认行的近邻 |
| L2 模型 | 图标组/武器族 → 客户端模型 | ≤2427 | 该模型下所有数据行 | 由 L1 的图标 stem 反推资源号，或 `weapon_threeway` 的几何-轮廓匹配 |
| L3 特效 | 每条数据 → A 组（+ 可选 B 组）× 5 槽 | 5855 行 | 本行 | 特效库分类浏览 + 同族模板 + 同模型其他行 |

估算（**不是实测**）：L1 约 1000 次判断、L2 大部分由 L1 自动得出（真正要人看的是图标→模型不唯一的那些），
L3 是主要工作量，靠「模板 + 只审差分」压到百来次判断，剩下的按行抽查。

**L3 的高效前提是模板**：同一族武器（如「联邦光束步枪」）的枪口/弹体/命中通常一致。
所以数据结构里 `effect_group` 是独立实体、可被多行引用——先建 100 来个模板组，
行默认引用模板，个别不同的行再单独建组。这样 5855 行不是 5855 次决策。

## 5. 页面怎么排

三个视图共用一个“当前选中”概念，随时切换不丢上下文：

**A. 图标组视图（L1，1028 组）**
```
┌ Wiki图标名(149行) │ 客户端候选（按相似度）           │ 将影响的 149 行
│ [wiki 96×48]      │ [s02010601][s02010401][s02106..] │ 高达OL扎古Ⅱ 头炮
│ 头炮1             │  distance 0.031 / 0.052 / ...    │ 高达OL扎古Ⅱ 头炮(改)
│ 同机体其他组 ▸    │  选中即预览 仓+战 两图并排        │ …（折叠，可展开）
└───────────────────┴──────────────────────────────────┴──────────────
```
一眼看到「这个选择影响多少行」，避免只为一个变体选了个不合适的图标。

**B. 模型组视图（L2 + L3 主体）**
```
┌ 模型 02010601 散弹枪  [3D 预览] [仓] [战]  ← 12 条数据共享
│ ├ 散弹枪(单发散射)   A:粉闪+弹体  B:—      ✓已确认
│ ├ 散弹枪 全自动      A:黄闪+弹体  B:—      ← 继承模板，绿
│ ├ 散弹枪(改)         A:粉闪+弹体  B:紫闪    ← 已覆盖，橙
│ └ …（默认只显示与组默认不同的行，其余折叠）
└ 右侧：特效候选（沿用现有分类浏览 + 组合预览）  键盘：1-5 槽位 / Tab A·B
```

**C. 清单与冲突视图（验收）**
表格式全量，筛选 `未完成 / 半成品图标 / 同模型不同图标 / 缺特效 / 两组同 mode`，
支持多选批量套模板、导出，以及每个层级的完成度条。

**键盘（效率的落点）**：`j/k` 或 `↑↓` 换组，`Enter` 采纳首选候选，`Shift+Enter` 采纳并确认，
`1–5` 选槽位，`Tab` 切 A/B 组，`x` 排除候选，`u` 撤销上一步，`/` 聚焦搜索。
鼠标只用于“看”，不用来回点。

**减少判断量的四个机制**：
1. 候选按「同名前缀 → 图像相似 → 同机体近邻」三档来源排序，并显示来源理由。
2. 组内差分显示：默认只列与本组默认不同的行，绝大多数行不用逐条看。
3. 影响面预演：改动前显示会波及多少行、其中多少行已确认（会先停下来确认）。
4. 断点续做：每步立刻落盘，刷新/重启不丢，进度按层统计。

## 6. 落地顺序建议

1. **先做数据装配**：把 5855 行 + 1028 图标组 + 2427 模型的骨架生成为 `weapon_review.json`（全 `unknown`），
   页面能读、能统计、能显示缺口。这一步不改判定逻辑，风险最低。
2. **再做 A 视图（L1 图标）**：复用现有图像相似算法，产出候选并支持一次决策影响 N 行。
3. **接 B 视图（L2 模型 + L3 特效）**：模型由图标反推，特效沿用 `weapon_effect_match` 的库与组合预览。
4. **最后做 C 视图与批量模板**。

## 7. 需要你定的两件事

1. **L3 特效的模板要不要自动套用**？我倾向：自动生成「模板建议」但状态记为 `candidate`，
   必须人看一眼组内代表行再升级为 `confirmed`；否则 5855 行会伪装成已完成。
2. **模型层允许 1:N 的反向吗**？也就是一个客户端模型能否同时属于多个武器族
   （素材复用，例如同模型被两把不同名字的武器借用）。允许的话模型键要独立于族，
   不允许就可以把族直接挂在模型上。这会影响 `models` 表要不要存 `family`。

## 9. L1 图标注解层落地（2026-11-04）

新增 `tools/weapon_icon_layer.py` 与 `--icons` 命令，复核台接上采纳写回。

**先纠正一个设计假设**：战图标不是仓图标的同号文件。仓图标 5192 张、战图标仅 1023 张，
战图标按武器类型编号（b01 408 个 / b02 259 / b03 303），按同号配对只能命中 **83/5192**。
所以 schema 里 `icon_pairs` 取消了「两图必须成对」的约束，改成 `hangar` 必填、
`battle` 可空，并单独给一组 `battle_candidates`（按 wiki 图标描述子排序）。这条如果不纠正，
后续每一行都会因为「缺战图标」卡住。

**采纳语义**：选一个仓图标 → 写 `icon_pair.hangar/battle` + `confirmed` →
从文件名反推模型（`s02010601 → 02010601`，需存在于 `models`）→ 传播给该组所有行，
行状态由 unknown 变 candidate。实测一组平均覆盖 5.7 行、最高 149 行。

**抓图被限流**：`wiki.biligame.com` 在批量拉图后整站返回 HTTP 567（换 UA 无效，图片 CDN 仍可用）。
首轮拿到 240 张、240 组有候选，其余 788 组待补。`--icons` 是幂等的：
只对没下过的图查 URL，已下过的直接跳过；`confirmed` 的组不会被覆盖。

测试：`tools/test_weapon_review.py` 13 项通过（含战图标命名、模型号反推、
离线候选拼装、采纳传播、无模型时不硬填）。

## 10. 国服武器对照表导入（2026-11-05）

用户提供了一份 `国服武器对照_对照表.csv`（GBK，13814 行）。列：
`国服页名 / 国服机体名 / 势力 / 类型 / model_id / 行序 / 武装名 / 客户端号 / 状态`。

**连接结果**：以 `(国服页名, 行序)` 为键（行序从 1 开始），对上我们数据集 **5848 行**，
且 **武装名 5848/5848 完全一致**——说明两边同源于同一份 Wiki 表，行序没有错位。

**客户端号到底是什么**：不是模型号。1395 个去重号里
1132 个能在 `interface/icon/item/s/` 找到同名文件（`s<号>.dds`），
761 个同时是模型号（`item/.. EM_..<号>.dxg`），759 个两者都是，842 个两者都不是
（多为 9/10/12 位号，可能是新客户端资源或本端缺资源）。所以它主要索引**图标**，
约一半能顺带确定模型，但不能反过来当模型号用。

**导入结果**（`--import-csv`）：
- 5809 行写入 `client_id`（其余 39 行是「待定」无号）
- 3439 行同时确定 `model`
- 1024 个图标组里 **747 组组内号唯一** → 直接写 `hangar/battle` 并置 `confirmed`；
  **0 组冲突**（组内出现多个号的情况没有发生）
- 未匹配 7966 行，来自 249 个我们数据集里没有的页名

**这 249 个页名里 240 个正好是「空武器表」的机体**（Wiki 模板未覆盖）。
它们带着 7966 行武器名 + 客户端号，但**没有 Wiki 属性**（威力/弹数/射击模式）。
是否把它们物化成 `weapon_data`（来源标 `csv_only`、与 Wiki 行分开统计）需要单独决定——
导入会让复核队列从 5855 行涨到 13821 行，但其中一半没有数值依据。

另外 9 个页名在两边都不完全一致（含 `?` 的乱码标题），需要人工核对标题写法。

测试：`tools/test_weapon_review.py` 15 项通过，其中 2 项覆盖导入器
（组内唯一 → 写图标并确认；组内多号 → 记 conflict 且不写；名字不一致/无号 → 跳过）。
