## 一、先说结论（三句话）

1. **报文内容已经是对的**，别再调 817 字节里的字段了。我用三条独立路径互证：
   服务端代码、`vt[0x78](0x4E5)`=1253 的分解、handler 逐条读取指令求和，全都落在
   `817 = 4 + 398 + 398 + 16 + 23n + 1`。
2. **卡点在"送不到"，不在"填不对"。** `FUN_00439190`（= `0x4392BD`）的**第一条指令**就是
   `mov byte [ebx+0x10615], 1`，无条件置位。所以只要它被调用过，步骤机 step 8 必过。
   既然一直不过 ⇒ **这个函数从来没被调用过** ⇒ `0xE13A` 的 handler 从来没走到
   `0xAD0322` 的 `call [eax+0x80]`。
3. 而从 `0xACFE1F` 到 `0xAD0322` 之间**只有两类会静默中止**的关卡（见 §3），
   它们都以"字节流被正确消费"为前提。⇒ 问题在**投递/分发层**，不在正文层。

## 二、这次新拿到的硬证据

### 2.1 `on_message` 的 opcode 分发表已完整枚举（新增资产）

`0xAA2D50` 开头 `movzx eax, word [esp+0x30]` 后是一棵二分查找树：

| 项 | 值 |
|---|---|
| 首级表条目 | **262 个**，覆盖 `0x0021` … `0xFF8B` |
| 解析器 | `server/_enum_dispatch.py` → `server/lounge_dispatch_table.json` |
| 尾部线性链 | 编译器会把最后几个候选降级成 `sub eax, imm; je`，**不是 `cmp`** |

⚠️ 踩坑记录：只按 `cmp eax, imm32` 解析会漏掉线性尾段，一开始误判"0xE13A 不在表里"。
实际 `0xACFB50` 是 `sub eax,0xE13A; je 0xACFE1F` —— **0xE13A 确认是合法 opcode，
handler = `0xACFE1F`**。

附带价值：这 262 条 handler 地址是后面写所有 lounge 报文的地图，不必再猜。

### 2.3 28 字节差异已解释清楚（参考文档 845B vs 本机 817B）

参考文档（另一版本）`845 = 4+398+398+20+4+1+20`，本机 `817 = 4+398+398+16+4+1`。
差 28 = 中段少 2 个 u32（8B，`pilot_rename_remaintime_*`）+ 尾部整块没有（5 个 u32 = 20B，改名功能）。
alloc 也跟着差 28（1281 → 1253）。**两个版本各自自洽，817 是错的这个可能性已经排除。**

成功路径 `0xAD009C..0xAD02F1` 会拼这些串（镜像里都在）：

## 三、失败点全集（从 handler 入口到回调，只有 4 个）

| # | 位置 | 条件 | 后果 |
|---|---|---|---|
| 0 | 更上游 | 报文没被投递到 `0xAA2D50` | **完全静默** |
| 1 | `0xACFE28` | 闸门 `byte[this+0x29e+0xC] == 0` | 调 error(2) = 空 `ret 8`，静默 return false，**不消费正文** |
| 2 | 各 read | 游标越界（`ptr+n > end`） | error(1,0xC) 空转，`jmp 0xAD5E15` 中止 |
| 3 | `0xAD0079` | `cursor.ptr != cursor.end`（多出字节） | 同上，静默中止 |

第 2/3 条都以"正文长度/顺序错"为前提，已被 §2.3 排除。
第 1 条需要一个**目前没有任何代码写 0** 的标志位（`机师关卡` 文档已查过，全镜像无写 0 的指令，
大概率 ctor 里 memset 成 1）。⇒ **剩下最可能的就是第 0 条：报文压根没进这个对象。**

### 为什么"没进去"是最可能的

- `CGVOProtoLounge`（vt `0xE14D04`）的 `+0x54` = `0xAA2D50`（真分发器），`+0x64` = `0x4B31A0` = **空 `ret 8`**；
- `_proto_lounge`（vt `0xE09A74`）的 `+0x54` = `0xA93EC0` = **只会报 error(0x242) 就返回**，
  `+0x64` = `0xAA29C0` = **会打印并关闭连接**。
- 我们观察到的现象是"不报错、不断连" ⇒ 与 `CGVOProtoLounge` 的"哑"特征吻合 ⇒ 对象大概率是对的，
  **但它可能根本没被注册成 session 的 listener**，或者注册了却不是接收这条流的那一个。

`机师关卡` 文档 §五.1 把"确认运行时实例化的是哪个类"列为待办，**这一条至今没做**，
而它恰恰是现在唯一能解释现象的分支。

## 四、这次复查出来的方法论疏漏（比技术卡点更值钱）

### S1 ★ 一条连接上连发多个候选报文 —— 结论全部作废风险

`--pilot-variants` / `--pilot-len-sweep` 都是**在同一条 TCP 连接上隔 3~10 秒连发**。
后果：

- 补零型变体（长度 > 817）会让 handler 在 `0xAD0079` 中止并**留下残余字节**，
  残余字节被当成新帧解析 → 流错位 → 之后所有变体的结果都不可信；
- 实测 `id+name` 变体会让客户端 **0.0 秒断连 + AV**，那之后的变体等于没测。

**正确做法：一个候选 = 一次全新启动 + 一条报文。**

### S2 ★ 813~905 长度扫描是在被 hook 劫持的路径上做的

`机师关卡` §三自己写了："`start_local.cmd` 一直带 `--pilot-hook`… 今天大部分机师实验
都是在被劫持的路径上做的"。而 §2 里"步长 4 扫 813-905 全部无反应"正是那次。
⇒ **这条负结论必须重做**（现在参数已移除，环境是干净的）。
另外步长 4 从 813 起会顺带命中 817，但因为 S1 的连发污染，仍不能算数。

### S3 把参考文档当同版本用

参考文档说"845B + 两条全零记录 ⇒ 客户端接受、可以进去了"；
本机是"全零记录 ⇒ 静默 / 带 id+name ⇒ AV"。
**两个 build 行为不同**，字段语义、`troops` 基址（0/1 vs 1/2）之类只能以本机反汇编为准。
`机师数据-准确填入规格.md` 里 19:35 那次"按 §3.3 改成 1/2"就是这么踩的。

### S4 65 张表全是 2 字节 `X`

`机师关卡` §五 自己列为第 4 条待办，一直没做。成本极低（`decrypted/settings/` 里有同名的真 CSV），
而且如果机师路径要查 `pilot_form` / `badge_config` / `clan_emblem`，这是唯一还能动的变量。

### S5 没有离线仿真验证

所有读取原语（8 个）语义现在都读全了，完全可以写一个纯 Python 的 `0xE13A` 读取链复现器，
对我们生成的 817 字节跑一遍、逐字段打印 `claim/read` 与最终游标位置。
**不依赖客户端就能回答"这 817 字节会不会被恰好消费完"**。这一步从来没做，
导致"长度对不对"这件事一直靠 `vt[0x78]` 的一次除法在撑。

### S6 成功回调被当成"大概是这样"

现在坐实：`0xAF6170`（vt`+0x80`）= 重排参数 thunk，
`FUN_00439190` 真实入口是 **`0x4392BD`**，第一条就是 `mov byte [ebx+0x10615], 1`。
⇒ 回调一旦发生，step 8 必然通过。这条可以用来做**反向判据**：
"UI 没动" ⟺ "回调没发生" ⟺ "handler 没走到 `0xAD0322`"。

### P0 装一个"眼睛"：DBWIN_BUFFER 旁听器 ✅ 已实现并接入启动脚本
