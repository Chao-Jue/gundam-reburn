# 强化券面板与物品图标-数据链接破译-2026-11-03

研究环境：5.0.0.33 中国客户端 + 本地假认证服务端。本文记录「强化券面板全 0、券名空白、图标占位、强化结果 +0」问题的完整因果链，以及服务端侧的修复规则。全部结论经静态反汇编与运行时内存双向验证。

## 一、问题总览与因果链

客户端在格纳库机体强化页打开「选择强化券」面板时，四行全部显示「0个」、券名空白；点确认强化后上行 0x9883 的 ticket_id 恒为 0；物品栏券图标全部显示占位图。

完整因果链（每一环都有实证）：

```
0x9883 ticket_id
  ← 0x75D110（确认按钮处理）：[面板+0x160] 数据提供者 → vt[0x364](usenum) → vt[0x368] → 返回选中条目+0x128
  ← 条目+0x128（item_id）由 0x856650 从数据源 *(0x1161F80)+0x50（0x9EE0A0 类，0x68B）填充
  ← 数据源 +0x00/+0x04/+0x08/+0x0C = 强化页四行的券 item_id；客户端 510 处引用、0 个写者，结构恒全 0
  ⇒ 条目+0x128 = 0 ⇒ vt[0x368] 返回 0 ⇒ 0x9883 携带 ticket_id=0
```

数量与概率是面板拿到 item_id 后自动解析的（数量 ← 物品持有列表；概率 ← mechanic_ticket.csv 行），不需要另行下发。

服务端修复 = 0x02EE 物品栏下发 11 张券（让持有列表有券）+ 运行时向数据源写 4 个券 id（数据源无客户端写者，本仓库服务端无法通过表解决；见第四节）。

## 二、0x02EE 物品数组容量 = 100/栏（重要协议约束）

0x02EE（item_init_get_r）单栏物品数**上限 100**。第 101 个元素会使客户端数组溢出，覆写相邻内存，客户端立即白屏卡死。

二分实证（同一数据集，仅改变注入条数）：

| 每栏元素数 | 包体（both 双栏 / consume 单栏） | 结果 |
|---|---|---|
| 30 | 1396B | 正常 |
| 60 | 2704B | 正常 |
| 90 | 4020B | 正常 |
| **100** | 4460B | **正常** |
| 101 | 4504B | **白屏卡死** |
| 101（单栏） | 2286B | **白屏卡死** |

结论：白屏与包体大小无关（2286B 也炸），与单栏元素数严格相关，临界点 100/101。`slot_num` 等头部字段不影响。

服务端护栏：注入函数内做 `MSGO_ITEM_MAX`（默认 100）截断。任何把全部物品塞进一栏的做法都必须遵守此上限；超量需求应分栏（main/consume）或分页下发。

## 三、物品图标查询链（服务端表数据的修复规则）

客户端不给物品图标下发任何资源号——图标名是**运行期构造**的：

```
图标路径 = str_table 模板 + item.csv 的 sort_group 列

str_table（settings/str_table.txt，UTF-16）：
  键 10,10,51 → ./interface/icon/item/d/di%08d.dds   （详细图，详情页）
  键 10,10,52 → ./interface/icon/item/s/si%08d.dds   （简易图，面板/物品栏）
```

- **sort_group 列就是图标参数**。修复规则：`sort_group = item_id`（券的图标 si80100001 恰好以 item_id 命名，资源在 `data/interface/icon.hed` 包内全部存在：11 张券中 10 张有专属图）。
- 修复前 sort_group=0 → 客户端查询 `si00000000`（包内不存在）→ 回退 `s%08d % 1` = `s00000001` 占位图。运行时证据：客户端请求驻留池中出现 `./interface/icon/item/s/si00000000.dds`（正斜杠=真实请求；反斜杠路径是 icon.hed 加载时自动建立的哈希索引节点，二者可据此区分）。
- `icon_variant` 列（u16）与图标查询**无关**（实测写入客户端 ITEM 结构生效但查询名不变），保持 0 即可。
- 81100001（整备师强化券）在 icon.hed 内无图（黑块）——5.0.0.33 客户端官方未制作，预期表现。
- 图标名数字段支持 8~10 位（si690208010 为 9 位自然溢出 %08d），sort_group 用 item_id 原值即可。

## 四、0x9883 与数据源（运行时填充说明）

服务端把券下发到 0x02EE 后，物品栏/券页签可正常显示券名与持有数，但**强化面板的数据源仍为全 0**（客户端无写者）。纯服务端解决路径（待研究）：追客户端 0xF86A/表下发层，找到官方应由哪个包触发数据源填充。

当前可用的运行时方案（本地工具，不入库）：注入代理在客户端 UI 全局就绪后向 `*(0x1161F80)+0x50` 写入 4 个券 id（80100001/80200001/80300001/80400001），面板四行立即复活（券名/持有数/概率/按钮），确认强化上行 `0x9883 ticket_id=80100001`，服务端正常结算。

0x9883 包体（32B 总帧）：`uniqid u64 | ticket_id u32 | usenum u32`。

## 五、验证记录

- 静态反汇编：0x75D110/0x856650/0x757010/0x773040/0x9EE0A0/0xAE2B10（5.0.0.33 主模块，非 ASLR，VA=文件偏移+0x400000）。
- 运行时内存：数据源 75 次轮询恒全 0；WriteProcessMemory 填充后面板复活；0x9883 抓包 ticket_id 由 0 变 80100001。
- 图标：四向占位探针（d00000000/d00000001/d0000000000/s00000001 指向四张不同券图）一次登录判明查询名；修复后请求池出现 `si80100001`/`si80200001` 正斜杠完整路径。
- 容量：二分 + 双模式（both/consume）交叉验证，100/101 临界点两轮复现。
- 全部验证在本仓库作者的本地假认证环境完成（runtime_integration + native_client_e2e 层）。
