> §5 的"核心矛盾"** 全部有误。本文用本机镜像（`server/img_dump/main_GundamOnline_CHINA.exe`）
> 的离线反汇编 + `refs/msgo-doc` 逐字段表交叉核对，给出确定值。

## 1. 定案：本客户端 `0xE13A` 正文（全部零填 = **817 字节**）

```
off    类型   字段
0      u32    result
4      398B   pilots_eff        ← 固定 1 条，**没有 count 前缀**
402    398B   pilots_zeon       ← 固定 1 条，没有 count 前缀
800    u32    del_remain_sec_eff
804    u32    del_remain_sec_zeon
808    u32    charge_point
812    u32    bmgpack_count     (<= 0x10，超了走 error(0xc,1))
816    u8     is_tutorial_end
       ----  读完必须「游标 == 正文末尾」
```

`bmgpack_count = n` 时总长 = **817 + 23n**（元素线长 23 / 内存槽 24）。

### 证据 A：alloc 逐项精确相等（最硬的一条）

分支入口 `0xACFE1F`，第二条指令就是 `push 0x4E5` → `vt[0x78]` 分配 **1253** 字节。

```
1253 = 4(result) + 424(record 内存) + 424 + 4*3(三个 u32) + 4(bmg count)
       + 0x10*24(bmg 数组上限) + 1(is_tutorial_end)      ← 精确相等
```
- 记录内存步长 `0x1A8 = 424`（`0xACFEB6/0xACFEF9` 的 `add ebx,0x1a8` + `0xA93F50` 的 `add [ecx],0x1a8`）。
- **没有第二个 count 的位置**：若真像旧文那样有 `count_eff/count_zeon` 两个 u32，alloc 会差 8。
- **没有尾部 5 个 u32 的位置**：若按 msgo-doc 的 v15 布局（845B），alloc 会差 28。

### 证据 B：控制流顺序（`0xACFE1F..0xAD0083`）

```
0xACFE76  a5a310        -> result                        (1 次)
0xACFEB6  a956f0        -> record 1   `cmp edi,1; jb`    (硬编码 1 次)
0xACFEF9  a956f0        -> record 2   `cmp edi,1; jb`    (硬编码 1 次)
0xACFF3C  a5a310        -> del_remain_sec_eff   (循环也判 1 次)
0xACFF7C  a5a310        -> del_remain_sec_zeon
0xACFFBA  a5a310        -> charge_point
0xACFFD4  a5a310        -> bmgpack_count, `cmp ebx,0x10; ja` -> error
0xAD002A  a982a0        -> bmgpack 元素，dest 步进 0x18
0xAD0069  a5a360        -> is_tutorial_end (1 字节)
0xAD007D  cmp ecx,[esp+0x18] ; je 0xAD009C        ← 唯一成功判据：cur == end
```

### 证据 C：hook 顺序反过来证明了"没有 count"

旧 hook 在 body=77 时抓到的序列是
`u32(result) → rec → rec`（**只有一个 u32 就打记录**）。
若有 count 前缀，序列必然是 `u32 → u32(count) → rec → u32(count) → rec`。
实测只有一个 u32 ⇒ 结构就是本文 §1。

### 证据 D：一条机师记录 = **398 字节**（不是 411 / 396 / 212）

把 `FUN_00a956f0`（`0xA956F0..0xA95C33`）的读取序列逐项相加：

```
4(id) + 25(name) + 4 + 1+1+1 + 2 + 18(avatar)          = 56
+ 4 + 2+2+2                                            = 66
+ 28×4                                                 = 178
+ 116                                                  = 294
+ 4 + 31 + 1+1+1                                        = 332
+ 4 + 4 + 31 + 1+1                                      = 373
+ 4 + 4 + 4 + 4 + 4 + 1 + 4                             = 398
```
- 单项尺寸来源：`a5a310`=4B、`a5a330`=2B、`a5a360`=1B、`a5de30`(avatar)=4+1+1+1+2+4+1+1+1+2=**18B**。
- `a5a270`/`a93f50`/`a94330`/`a5d400` **只动"结果缓冲区指针"，不吃报文流**（已逐条反汇编确认），
  所以它们不贡献线长——旧文把它们当成"数组头"是根本性误读。
- 398 的**字段线偏移与 `refs/msgo-doc/.../07-机师列表创建选择.md §3.3` 的 58 字段表逐行吻合**
  （0/4/29/33/34/35/36/38/56/60/62/64/66/178/294/298/329/332/336/340/371/372/373/377/381/385/389/393/394）。
  ⇒ 那份 398B 记录表对本客户端**直接可用**。

## 3. §5「唯一未解的核心矛盾」是误判，可以整段删掉

原文：*"hook 在发 845 字节正文时读到 remain=0x4D(77) ⇒ 客户端认为这条消息只有 77 字节
⇒ 长度字段只被读到 1 字节 ⇒ (a) 或 (b)"*。三条硬证据反驳：

1. **算术错**：845 = 0x34D，低字节是 **0x4D**，不是 0x4F。原文自己写的
   "0x4F = 79 = 2(opcode)+77" 恰好说明**那次的正文就是 77 字节**。
2. **日志实锤**：`server/fake_auth.log` 里有一条
   `14:48:42  [probe 8] op=0xe13a bodylen=77`（同一轮是 `70..82` 共 13 个长度，`--probe-gap 0.8`）。
   hook 抓到的就是这一条——`_kind0` 对它写 `[0x00][0x4F]`，客户端读 79，正文 77，**完全自洽**。
3. **>255 字节的帧本来就被接受**：数据表阶段多张"缺表占位 2431B"的 `0x5290`
   走的就是 k=1（2 字节长度），65 张全跑完；`autoexec.cfg` 10272B 走 k=2。
   ⇒ `_kind0`/`build_inbound_frames` 的封装**没有任何问题**。
   推论 (a)/(b) 与"打印前 16 字节对照"这条待办都可以删除。

## 5. 下一步：四个探针（全是冷地址，读一次/条消息）

**先说一个工具 bug**：`tools/pilot_hook.js` 的过滤窗是 `LO=0xacf000, HI=0xad0000`，
而尾部三个关键位置在 `>= 0xad0000`：`0xAD0069`(读 is_tutorial_end)、`0xAD007D`(cur==end)、
`0xAD009C`(成功分支)。**所以旧 hook 从物理上就看不到"长度校验过没过"**，
只能看到 bmg 之前。这解释了为什么它永远只能给出"读了两条记录就没了"。

| 探针 | 位置 | 读什么 | 说明 |
|---|---|---|---|
| P1 报文起点 | `0xACFE76`（onEnter） | `[esp+0x18] - [esp+0x14]` | **客户端眼里的正文长度**。这一个数就能定死 k≥1 的长度语义，不用再猜。 |
| P2 长度校验 | `0xAD007D`（onEnter） | `[esp+0x14]`(cur) / `[esp+0x18]`(end) | 相等 = 字段总和刚好；不等 = 差几字节，直接可见。 |
| P3 成功分支 | `0xAD009C` | 命中一次 = 解析被接受 | 真正的 oracle（比 `+0x10615` 更早、更可靠）。 |
| P4 拒绝出口 | `0xACFE82`（error(0xc,1) 的公共路径） | 计数 | 区分"字段读炸"和"尾部长度不符"（后者只会在 P2 后落到 `0xAD0085`）。 |

注意 `0xAD0085` 是"长度不符"专用出口，`0xACFE82` 是"某个字段读失败"出口，**两者不同**，
这就是判断"到底卡在内容还是长度"的判据。

### 运行顺序（一次登录内完成，不用重开客户端）

1. `bodylen=817` 全零 → 看 P1 的数：若不是 817，说明 k=1 语义有偏移（按 P1 的实际差值补）。
2. 若 P1=817 且 P2 相等、P3 命中 → 界面应该动了；若界面不动，问题已不在 `0xE13A`（去查 case8/`0x10615`）。
3. 若 P2 不等 → 按 `end-cur` 的差值微调 `--probe-body-len`（一次一个）。
4. 通过后再上 `--pilot-body`（`server/fake_auth.py` 已按 398/817 改好，见下）。
