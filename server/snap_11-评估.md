# snap_11 第三方交付包评估（2026-11-01）

对象：`snap_11/snap_11/`（27 轮迭代，594 MB，1019 文件，作者外部）
结论一句话：**"绕过 CPS" 是误传；地址全部不可用；协议语义表和几条实现级约束值得吸收，另有一条高价值线索（gosrv）。**
⚠️ **优先级请直接看第六节**——机师部分已突破，当前可用的是"实体/出生族"，不是机师列表。

---

## 一、先说最要紧的：他们的客户端不是我们这一个 build

| 项 | 我们（v5.0.0.33） | 他们（自称 CN 9.0.0.182） |
|---|---|---|
| PE TimeDateStamp | 2017-04-12 | **2022-02-14** |
| SizeOfImage | `0xEEE000`（15.6 MB） | `0x1298000`（19.5 MB） |
| 节表 | 无名大节 `0xE0C000` / `.rsrc` / `.vmp0` / `.idata` / `ohjicybf` / `esllbfpk` | `.text 0x965000` / `.rdata` / `.data` / `.rsrc` / `.vmp0` / `.imports` / `.SCY` / `.loader` |
| EntryPoint | `0xEED000`（在最后一个壳节里） | `0x8CC5DD`（在 .text 里，已还原） |
| 保护 | CPS 驱动 7 IOCTL + `ACOPCShell.dll` | 无 CPS 痕迹，只有 `.vmp0` / `.SCY` / `.loader` |

⇒ **他们文档里所有地址（`0xe12b6c` slot 表、`0xcb4580` SPN、`0xcb7c10` recv_pump、`0xaf7xxx` handler 区）
对我们的镜像一律无效。** 他们自己也承认：服务端注释里那批"客户端函数地址"是**从另一个版本**逆出来的。

### "绕过 CPS" 究竟是怎么回事

两件事，都不是技术性绕过：

1. **采集**走**硬件 DMA 采集卡**（`D:\Origin\{vmm,采集接口库}.dll`，`-device capture`）——
   进程外的物理/地址空间读取，CPS 根本看不到"有人在读我"。这是钱和设备，不是技术。
2. **能跑到战斗**是因为目标机上跑着**一份现成的第三方 Python 私服 `gosrv`**
   （227 条 opcode 定义 / 98 个 handler / 93 个 CSV 数据表 / `session_schedules_cn.json`）。
   客户端连的是它，不是官方服，也不是我们这种"自己边逆边喂"的 fake_auth。

⇒ 对我们的 CPS 关卡（`0x70E9` / `Addr:ACFE76`）**零帮助**。我们的 frida 伪造方案仍是唯一路径。

## 二、可以直接吸收的四块（按性价比）

### A. opcode 语义主表 —— 能给我们的分发表打 65 个标签 ★最实用

已生成 `server/opcode_names_from_snap11.csv`：

- 我们分发表 282 条 vs 他们主表 239 条，**交集 65 条，其中 65 条有名字**（64 条有中文语义）
- 每行带我们的 handler VA + 他们的名字 / 方向 / 实测 body 长度 / 中文语义

⚠️ 用法：**只信"名字"和"大概语义"，不要信 body 长度**——长度随版本变（见下一节 0x063E 三个变体）。

### B. 0xE13A 的交叉验证 —— 偏移没错，别再怀疑布局

他们抓到的一帧（845 B，`count=1 / ARR2_count=0`）的头 48 字节：

```
00: 01 00 00 00            count = 1
04: 09 00 00 00            pilot[0].id = 9
08: 31 31 34 35 31 34      name = "114514"（25 字节内联）
20: 00 00 01 00            u32 @ +0x20
24: 00 00 00               u8/u8/u8 @ +0x24/+0x25/+0x26
28: 00 00 01 0b            ...
```

与 `server/0xE13A-驾驶员列表格式.md §3` 的字段偏移**逐项吻合**（id@+0、name[25]@+4、u32@+0x20）。
⇒ **解析布局是对的，失败一定在"取值"上。** 这与 2026-10-28 的定案一致，不必回头重扫字段顺序。

`845 - 817 = 28`，正好等于 refs 里"我们少了改名功能"的差额 ⇒ 他们这份也是**带改名**的变体。
另注意：**他们的 0x063E 是 51725 B，我们的实测是 29514 B，他们文档里还记着"老客户端 46189 B"——同一个包里有三个值，
说明 body 长度逐版本变，任何"照抄长度"的做法都会错。**

⚠️ 一个重要的降权理由：这帧的 `id=9 / name='114514'` 与 `refs/msgo-doc` 的测试机师**一模一样**。
说明他们的"真实流量"是**对着自家测试服发的测试数据**，不是官方服地面真值。
所以"他们的 845 能过"推不出"我们的 817 也能过"。

### C. 几条实现级约束（可以直接抄进 fake_auth / 未来实现）

| 项 | 内容 | 对我们 |
|---|---|---|
| `0x70E9 file_integrity_get` | ~~永不应答，回了必崩~~ → **已证伪（2026-11-01）**：5.0.0.33 上回了 114 次 `zero`，零崩溃；客户端根本没有这条的下行 handler，属于单向上报 | 默认已改成 `--seventye9 none`，理由是"不需要回执、少一个变量"，不是"回去会崩"。见 `0x70E9-应答实验.md` §6 |
| `session.frame_chunk = 12000` | 超过 12000 B 的 record 切成多个 transport unit，每 unit 带同一 record 的一段 | 将来发 29514 / 46189 / 51725 这类大包时必须按字节流切，否则流错位 |
| `0xF11C channel_list_r` | `user_max = 0` ⇒ 频道进不去 | 机师之后下一关的坑 |
| `0x063E pilot_select_r` | "决定进不进频道" | 我们已知 |
| `0xB080 mission_info_update_vs` | 主菜单 step 2 的**唯一出口** | 后续关卡 |
| `0x090C pilot_money_update` | 客户端只读余额字段**低 16 位** | 若将来填余额 |
| counter 漂移 | 计数器算错时**只有 opcode 高半字节错**，marker/len 不变，`header+size==unit_len` 照样通过；实测 39 个 opcode 里 30 个是伪影 | 若我们自己抓包解码，必须有"同 opcode 低字节匹配 + 跨轮 counter 单调"两条判据 |

### D. 战斗期协议样本（我们还没走到，但提前知道要什么）

`03_PROTOCOL/frames/frames_all.json` —— 1104 帧**明文**（`frame_hex` + `body_hex`）+ counter：

| opcode | 方向 | 帧数 | body | 说明 |
|---|---|---|---|---|
| `0x421b battle_pos_move` | 上行 | 510（47B）+ 14（126B） | 9 字段 observed：`<Ihhhhh` + `<hhh` + u32 + u16；157 帧验证、94 个不同位置 | 移动/朝向，进入战场后的基础包 |

## 三、明确不要拿的东西

| 东西 | 为什么 |
|---|---|
| 全部地址 | 不同 build（见第一节） |
| 594 MB `01_MEMORY_DUMP` | 是他们那个 build 的进程镜像；地址空间快照同理 |
| `.vmp0` / SPN 反汇编结论 | 只对他们的 build 成立；且他们自己承认"lookup 表与参考实现逐值不匹配" |
| "无代码虚拟化 / 无运行时解密" | 他们的三条否定证据只覆盖他们那个 build。且**内部自相矛盾**：一边说"无运行时解密"，一边用"磁盘上是加密态、运行时才解密"解释 10.4% 的空代码页 |
| `0xe12b6c` 378 项 slot 表 = 分发表 | 结构上与我们 282 条二分表是**两套不同分发层**，不能互推 |
| "opcode → slot 映射" | 他们自己也没拿到（只 20/239，来源是别人的注释） |

⚠️ 方法论警告（对我们自己同样成立）：他们的静态扫描结论大面积受**代码段 10.4% 空页**污染
（采集时未被 demand-page 触发）。我们手上的 15.6 MB 镜像是**磁盘文件**（94% 明文），
同样不能保证"扫不到 = 不存在"。

## 四、最大的一条线索：gosrv

这个包不含它，但它确实存在，而且是把客户端从登录喂到战场的那一方：

```
gosrv/protocol/opcodes.py        227 条定义
gosrv/channels/handlers.py       98 个 @handler(0xXXXX)
gosrv/wire/framing.py            帧格式（已原文摘录）
gosrv/crypto/session.py          外层 wire unit（已原文摘录）
gosrv/crypto/spn.py              SPN 实现
config/session_schedules_cn.json 固定的 SPN 密钥调度（5.4 KB）
data_files/                      93 个 CSV（item/msma/mission/buff/clan/npc/quest/reward…）
var/gosrv.db                     SQLite 116 KB
config/server.json               战斗/掉落/房间参数，152 KB
tools/probe_battle.py            战斗链路无客户端回归测试
```

**对我们的价值远大于这份快照**：
- 我们卡在机师列表；它已经把整条 登录→机师→频道→战场 跑通（哪怕是对着 845 build）
- `data_files/` 的 93 个 CSV ≈ 我们要填的 65 张表
- `session_schedules_cn.json` 若真是固定调度，说明 SPN 参数是**静态的**

建议：向对方（或转发这条的人）**直接要 gosrv 源码**，这比继续啃 `snap_11` 划算。

### 两条可以立刻做的 A/B（都在现成代码里）

1. **`0x9951` 首字段**：我们发 `struct.pack('<II', 0, 1)`（`spawn1st_post=0`）；
   他们跑通的会话是 `4294967295 / 1`（= `-1`，未指定首个出击点）。
   我们现在 D1B3 已经能刷出 14 个 type31 标记，改成 `0xFFFFFFFF` 后再看标记样式是否变化——**成本极低**。
2. **`0x640D` 体长**：我们空选择时 20 B / 带选择 18 B；他们 27 B（`u32=600/1/257/33554176`）。
   差值说明我们**至少少建模了一组字段**。他们的值不可信（自家测试），但"27 B 这个量级"提示我们
   四组计数数组的头部可能还有我们没解析的字段。

这一块是他们完全没碰的领域，一个字都没有。当前的 P0 还是要自己啃。
