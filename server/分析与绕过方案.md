# 敢达OL 客户端启动失败：根因定位与绕过方案

> 结论先行：**问题不在提权、也不在防火墙，而在「保护模块要安装并启动一个内核驱动服务 `CPS`，在这台 Windows 11 25H2 (10.0.26200) 上起不来」**。
> 提权/放行防火墙之所以无效，是因为它们跟真正的失败点没有任何关系。要往下走，要么让这个驱动真能加载，要么在 **Win32 API 边界**上把它"骗过去"——**不要**再去改保护模块内部的机器码。

---

`STARTSERVICEERROR` 这个符号本身就说明了一切：模块在做 **StartService**。

`GundamOnline_CHINA.exe` 的节表：

**主 exe 是 VMProtect 加壳的。** 导入表里有 `CreateServiceW / OpenServiceW / StartServiceW / ControlService / DeleteService / DeviceIoControl` —— 服务这一套是 exe 自己干的。

用 PE 头校验从 exe 体内抠出 **6 个内嵌 PE**（成品在 `server/extracted/`）：

| 文件 | 架构 | 子系统 | SizeOfImage | 时间戳 | 判定 |
|---|---|---|---|---|---|
| `emb_00000000_x86.bin` | x86 | GUI | 0xeee000 | 2017-04-12 | 主 exe 本体 |
| `emb_00b46a60_x86.bin` | x86 | GUI | **0x2ee000** | 2016-09-06 | **保护模块 DLL**（VMProtect，导入 StartServiceW/DeviceIoControl） |
| `emb_00c91340_x86.bin` | x86 | GUI | 0x66000 | 2015-08-14 | 小助手 DLL |
| `emb_00ca1800_x86.bin` | x86 | GUI | 0x53000 | 2015-08-14 | 小助手 DLL |
| `emb_00cf3b28_x64.bin` | **x64** | GUI | 0x72000 | 2015-08-14 | 64 位组件（给 WOW64 用的） |
| `emb_00d06ec8_x64.bin` | **x64** | GUI | 0x5b000 | 2015-08-14 | 64 位组件 |

注意 `emb_00b46a60_x86.bin` 的 `SizeOfImage = 0x2ee000`，**和上一轮内存扫描到的"未打包模块"区域 `0x2ee000` 完全一致** → 就是那个在 `0x6840000` 之类随机基址上跑的保护模块。

而这个模块的节表是：

```
.text  VA=0x001000 VSz=0x04f169 Raw=0x000000 RSz=0x000000   <- 磁盘上根本没有内容
.rdata VA=0x051000 ...
.data  VA=0x065000 ...
.vmp0  VA=0x0d8000 ...
.vmp1  VA=0x1b3000 Raw=0x001000 RSz=0x139000                <- 只有这里有原始数据
```

**`.text` 的 RawSize 是 0**：上一轮定位到的那个 `cmp eax,0x804`（RVA `0x8a66`）落在 `.text` 里，**磁盘文件中根本不存在**，只在运行时解出来。而驱动本体（`CPS.sys`）没有以明文 PE 形式内嵌，是被加密存放、运行时才写到磁盘的。

## 2. 为什么那三件"官方条件"到不了游戏画面

| 官方说法 | 实际对应 | 为什么没用 |
|---|---|---|
| 用管理员身份启动（49236） | `XGGLIB.last = 0xFFFF0002` | 提权只影响 `CreateService` 能否成功（它成功了，事件 7045 为证）。失败发生在 **StartService**，那是内核加载驱动，跟你的令牌是不是管理员无关。 |
| 防火墙放行入站/出站（49235，系统码 0x5） | `XGGLIB.last = 0x00000005` | 0x5 是 `ACCESS_DENIED`，但**不是被墙挡的**，是启动驱动被拒绝。放行防火墙规则永远不会让一个内核驱动加载成功。 |
| 工作目录 + `./data/` 参数 | 只是让 exe 找得到资源 | 完全无关：进程在保护模块初始化阶段就退出了，根本还没走到读 data 的地方。 |

**根因：驱动 `CPS` 装不上/起不来。** 环境侧的高度可疑项（本机实测）：

- `HKLM\SYSTEM\CurrentControlSet\Control\CI\Config\VulnerableDriverBlocklistEnable = 1`
  → **微软"易受攻击驱动阻止列表"已启用**，会拦掉一批旧驱动。
- `Win32_DeviceGuard.VirtualizationBasedSecurityStatus = 2` → **VBS 正在运行**（`SecurityServicesRunning = {0}`，即内存完整性 HVCI 未跑，但 hypervisor 层已起）。
- `CodeIntegrityPolicyEnforcementStatus = 2` → **CI 策略处于强制状态**。
- 系统版本 `10.0.26200`（Windows 11 25H2），比这批 2015 年的驱动（时间戳 2015-08-14）新了十年。

也就是说：一个 2015 年的内核驱动，要在一个开着 VBS + CI 强制 + 易受攻击驱动阻止列表的 25H2 上加载。**大概率被拒**。

## 3. 为什么上一轮"改字节"没有用

`start_game.py` 的 `patch_xgg_startup()` 做的事：在标记 `c784243008000012000000`（即 `mov dword ptr [esp+0x830], 0x12`，RVA `0x8b14`）前 0xAE 字节处，把

```asm
0x8a66  3d 04 08 00 00     cmp eax, 0x804
```

改成

```asm
0x8a66  b8 04 08 00 00     mov eax, 0x804
```

`launch_result.txt` 显示 `patched=105155174`（= `0x6448A66`，即模块基址 `0x6400000` + RVA `0x8a66`），补丁**确实写进去了**，但进程依然 `return=4294967295`（-1）。原因有两个，都很要命：

1. **打错了地方。** 从逻辑看，RVA `0x8a66` 是个 **"状态码 → 弹窗文案"的分发器**：它把 `eax` 跟 `0x404 / 0x804 / 0xC04 / 0x411` 比较，分别跳去拼不同文案，认不出就落到默认分支报错。它决定的是 **"弹哪句提示"**，不是"要不要退出"。真正的闸门是它上游那句 `StartService` 的结果。把 `eax` 强行改成 `0x804`，最多是让你走另一条文案分支。

2. **它改的是 VMProtect 运行时解出来的代码。** 模块的 `.text` 在磁盘上是空的，代码是运行时解密到可执行内存里的。改这种代码很容易：① 被 VMP 的完整性校验发现；② 改到的副本不是真正在执行的那份。这类壳下"改内存字节"是下策。

> 顺带一提：`server/startup_error.txt` 里那条 `module 'subprocess' has no attribute 'CREATE_SUSPENDED'` —— `subprocess` 没有这个常量，得自己传 `creationflags=0x4`（配合 `ntdll!NtResumeProcess` 之类）。这个坑先修掉，后面挂起注入要用。

## 4. 保护模块的结构（按证据还原）

```
GundamOnline_CHINA.exe  (x86, VMProtect 壳)
│
├─ 启动早期，从自身解出并手动映射 →
│     emb_00b46a60_x86.bin   保护模块 (SizeOfImage 0x2ee000, 又是 VMProtect)
│       ├─ XGGLib    顶层调度 / 版本协商
│       ├─ DLIB-DLOADER   驱动加载器  <-- STARTSERVICEERROR 就出在这里
│       ├─ K_DS       内核驱动服务（CreateService/StartService/ControlService）
│       └─ 日志 → XDt/*.log（混淆，见 §6）
│
├─ 驱动本体：加密内嵌，运行时写到 %windir%\SysWOW64\CPS.sys
│     （32 位进程取 SystemDirectory 被 WOW64 重定向到 SysWOW64；
│       服务 ImagePath 记为 \??\C:\WINDOWS\SysWOW64\\CPS.sys）
│
└─ 初始化流程：XGGLib → DLIB 加载驱动 → StartService
     成功 → 走 0x404/0x804/0xC04/0x411 之一（疑似"驱动/保护版本等级"白名单）
     失败 → XGGLIB.last = 0xFFFF0002 或 0x5
             → 弹 "发现错误 / 内部错误码 4923x" → ExitProcess(-1)  ← 你看到的现象
```

## 5. 该怎么继续：三条路线

### 路线 A —— 让驱动真的能加载（最"干净"，但可能走不通）

目标：让 `StartService` 成功。按这个顺序试，每步做完重跑一次客户端：

1. **先把驱动本体搞到手**（这是所有后续工作的前提，见 §5.1）。
2. 关掉三个"现代 Windows 保护开关"（都改注册表/BCD，**注意会影响其它游戏的反作弊，比如本机装着 ACE / EasyAntiCheat / EAAntiCheat**）：
   ```bat
   :: 关微软"易受攻击驱动阻止列表"
   reg add "HKLM\SYSTEM\CurrentControlSet\Control\CI\Config" /v VulnerableDriverBlocklistEnable /t REG_DWORD /d 0 /f
   :: 测试签名（需要先关 Secure Boot 才能生效）
   bcdedit /set testsigning on
   :: 若仍有问题，关 VBS/hypervisor（影响内存完整性、WSA、部分反作弊）
   bcdedit /set hypervisorlaunchtype off
   ```
   → 重启后重试。
3. 若 CI 仍拦：查 `Microsoft-Windows-CodeIntegrity/Operational`，按时间过滤到客户端启动的那一秒，看 3033 / 3077 / 3082 事件里点名的是不是 `CPS.sys`，以及拒绝理由（签名等级 / 哈希不在策略里）。
4. 用 `sc start CPS`（把驱动放好、服务建好之后）单测：返回码能区分"文件找不到(2)"和"加载被拒(577/1275/1058…)"和"驱动自己初始化失败(1053/特定 NTSTATUS)"。

**优点**：不改客户端，行为最接近官方。
**缺点**：如果驱动本身是针对旧内核编译、在 26200 上 `DriverEntry` 直接失败，这条路就是死的。

### 路线 B —— 在 Win32 API 边界上把它骗过去（推荐）

**核心思路：不要去碰被 VMP 保护的模块代码，而是让模块"看到"驱动加载成功。**

保护模块导入表里明明白白有这几个：`CreateServiceW / OpenServiceW / StartServiceW / ControlService / DeleteService / DeviceIoControl`。所以只要在它调用这些 API 时返回"成功"，它就会继续往下走。

实现要点：

1. 用 `CREATE_SUSPENDED`（`creationflags=0x4`）起进程 → 稍等它解包/映射完保护模块 → **恢复**。
2. **Inline hook `advapi32!StartServiceW`**（而不是改模块自身的导入表——VMP 的 IAT 是运行时重建的，而且改那边容易触发完整性校验）。让它在真调用失败时也返回 `TRUE`，并顺手伪造 `QueryServiceStatus` → `SERVICE_RUNNING`。
3. 模块随后会 `DeviceIoControl` 跟驱动握手 → 一起 hook，返回"看起来正常"的响应。握手包长什么样，取决于驱动协议：**可以先只 hook `StartServiceW` 试一次**，看日志/弹窗是否往后走了一步（比如从 `STARTSERVICEERROR` 变成别的 code），这样就摸清了协议需要伪造哪些字段。
4. 更省事的等价做法：写一个独立的注入 DLL（`AppInit_DLLs` / `CreateRemoteThread` / 调试器注入），在里面统一做 hook，然后用最朴素的方式启动 exe。

**优点**：绕开 VMP 完整性校验，不用逆壳；失败时能通过日志一步步逼近。
**缺点**：需要 hook 的 API/协议字段可能要试几轮。

### 路线 C —— 换环境兜底

在 **较老的 OS** 上跑：Win7 x64、或 Win10（1809 以前的构建）、或直接 32 位 Windows；或在 25H2 上关掉 VBS + blocklist 再试。
很多私服/汉化项目就是这么过这类检查的——**先把画面跑起来，再回头做精细绕过**。

### 5.1 所有路线的第一步：把 `CPS.sys` 抓出来

现在这个文件被模块失败后删掉了，必须先截获。三种办法，任选：

```powershell
# 办法 1：轮询拷贝（最简单）——先在另一个窗口跑，再启动客户端
while ($true) {
  $p = 'C:\Windows\SysWOW64\CPS.sys'
  if (Test-Path $p) { Copy-Item $p "D:\project\gundam-reburn\server\CPS_dump.sys" -Force; Write-Host "got it"; break }
  Start-Sleep -Milliseconds 20
}

# 办法 2：Procmon，过滤 Operation = CreateFile / WriteFile，Path end with .sys，Process = GundamOnline_CHINA.exe
# 办法 3：windbg 在 advapi32!StartServiceW 下断，断下后去 SysWOW64 目录直接把文件顺走
```

拿到 `CPS_dump.sys` 之后再看：`Machine`(必须 x64)、时间戳、签名状态、`DriverEntry` 里干了什么——这决定路线 A 是否可行，也决定路线 B 需要伪造哪些 IOCTL。

## 6. 附：XDt 日志解码算法

`XDt/*.log` 是 UTF-16LE，两层朴素变换，互为逆运算：

```
解码 = 取每个 16 位字的低字节
       → 按索引奇偶分别异或 0xFD / 0xCD
       → 相邻两字符互换
（高字节固定是 0x70 / 0xFE 的标记，无信息）

编码 = 明文 → 相邻字符互换 → 按索引奇偶异或 0xFD/0xCD → 每个字节补成 16 位字
```

现成脚本：`tools/decode_xdt.py`（不带参数就解码整个 `XDt/`，产物写到 `server/xdt_decoded/`）。
