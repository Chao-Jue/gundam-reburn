# 接收链路与状态机分析（2026-10-18）

> 本文记录到 2026-10-18 17:00 为止，对《机动战士敢达Online》客户端
> 网络接收链路、连接状态机、消息工厂的全部确认结论。
> 所有结论都来自**活内存反汇编**（CE 硬件断点 / frida 只读 dump），不是推测。

## 一、工具与前提

### frida 与 CE 不能同时用
CE 附加并调试进程时，frida 注入必定失败：

```
frida.TransportError: unexpected error allocating memory in target process
(VirtualAllocEx returned 0x00000005)
```

**调试期间一律用 CE**；CE 关掉后才回到 frida（`tools/dump_code.py` / `tools/scan_ref.py`）。

### CE Lua 的可用 API（实测）
| 用途 | 可用写法 |
|---|---|
| 读寄存器 | `_G.EIP` / `_G.ESP` / `_G.EAX` / `_G.EBX` / `_G.ECX` / `_G.EDX` / `_G.ESI` / `_G.EDI` |
| `getReg` / `getRegisters` | **不存在**，调用会 `attempt to call a nil value` |
| 读内存 | `readInteger(addr)` —— **失败返回 nil**，不能直接进 `%d` |
| 写内存 | `writeInteger(addr, value)` |
| 读字节写文件 | `readBytes(addr, 1, true)` 逐字节 |
| AOB 扫描 | ⚠️ `AOBScan` **扫不到壳解包的匿名 rwx 区**，基本没用 |

⚠️ **硬件数据断点（bptRead/bptWrite）在 WOW64 下报告的 EIP 不可靠**；
**执行断点（bptExecute）的 EIP 才可信**。数据断点请用"扫栈找模块地址"代替。

## 二、接收链路（完整）

```
recv → socket+0x230（密文缓冲）
     → 0xBD4FB0 外层帧解析：u32 密文长度 | 密文
     → 0xBD5080 循环（每 16 字节一块）：
          0xBD508C  call 0xC00BD0     ← cB 解密（Camellia-128）
          0xBD5091  add dword[esi], 1  ← 每次解密后计数器 +1
          0xBD50A0  call 0xC034F0     ← RingWrite(ring, 明文块, 16)
     → 0xBD50F6 call 0xBF8850（推进 head） / 0xBD5102 call 0xBF8820（取剩余长度）
```

### 缓冲区管理函数
- `0xBF8820(socket, *out)`：`*out = tail - head`，返回 `buf + head`
- `0xBF8850(socket, n)`：`head += n`，到顶则 head=tail=0

### 解密队列 ring 的布局
`ring` 由 `0xBD504A` 的 `lea ebx,[edi+0x4E0]` 得出，即 **`ring = socket + 0x4E0`**。

| 偏移 | 含义 | 实测 |
|---|---|---|
| `+08` | buf 基址 | `0x2CDB51D8` 之类 |
| `+0C` | **readPos** | |
| `+10` | writePos | 每块 +16 |
| `+14` | cap | 24576 |
| `+18` | 上限 | 16MB |
| `+1C` | 水位 | |

⚠️ **`RingWrite` 空间不足时会压缩缓冲**（`sub [+0x10], readPos; mov [+0x0C], 0`），
所以"readPos 变了"**不代表有消费者** —— 早期曾据此误判过，已更正。

## 三、连接状态机（`socket + 0x280`）

### 全部状态写入点
| 地址 | 设为 | 备注 |
|---|---|---|
| `0xBEFAFE` | 2 | |
| `0xBEB45A` / `0xBEB6DA` | **3** | 发送请求之后立刻置 3，并开始 30 秒计时 |
| `0xBEB310` / `0xBEB590` | **4** | 条件：`状态==1 && [socket+0x9C]!=0` |
| `0xBEFC5A` / `0xBEFE0A` | 5 | |
| `0xBEFCA1` / `0xBEFE51` | 6 | 握手完成后 |

### 各状态的行为
**状态 3（握手）——`0xBEFC6B` 分支**
```
0xBEFC84  取可用字节；要求 >= 2 ×（位长/8）= 32 字节
0xBEFC9C  call 0xBEDC70
0xBEFCA1  mov [socket+0x280], 6
```

**`0xBEDC70` 的真身：用下发的 32 字节初始化 Camellia 会话**
```
0xBEDD97  lea eax,[esi+0x3A0]   ; sess = 下行会话对象
0xBEDDA4  call 0xC00680         ; 初始化下行加密
0xBEDDBB  call 0xBEC480         ; 再取 16 字节
0xBEDE90  add esi,0x290         ; sess = 上行会话对象
0xBEDE9D  call 0xC00680         ; 初始化上行加密
```
⇒ **服务端下发的 32 字节 = 下行密钥 16 + 上行密钥 16。**
（我们发 `11*16 + 22*16` 一直是对的，这也是 cB 解密始终正常的原因。）

**状态 4（真正解析帧）——`0xBEFB73` 分支**
```
0xBEFB99  call 0xBF8820         ; 取数据指针
0xBEFBBD  call 0xBEFA90         ; 处理一帧
```

**状态 6 ——`0xBEFCAB` 分支**
```
0xBEFCC5  call 0xBD4FB0         ; 只收包（解密 + 写队列），**完全不解析**
```

## 四、消息工厂与分发

### `0xBEFA90`：分发器
```
0xBEFA93  cmp dword [esi], 0     ; 已有消息对象？
0xBEFAA1  call 0xBEF9C0          ; 没有 → 工厂构造
0xBEFAB5  mov ecx,[esi]          ; 消息对象
0xBEFAB7  mov edx,[ecx]          ; vtable
0xBEFABD  mov edx,[edx+0x14]     ; 虚函数 #6
0xBEFAC1  call edx               ; 交给对象处理
```

### `0xBEF9C0`：工厂按**位长**分流（不是 32 位 ID）
```
and ecx, 0x8000007F     ; 低位必须对齐，否则丢弃
cmp eax, 0x80   → 建 0x38 字节对象，vtable = 0xE642B8
cmp eax, 0x100  → jmp 0xBE1160（另一类）
其他            → jmp 0xBEF810（通用工厂）
```
⇒ **消息类型由"帧的位长"决定**。
（早期曾扒出 44 个 32 位 ID 并据此填 payload，方向完全错误，已作废。）

### 128 位消息的处理函数 `0xBDC580`（vtable `0xE642B8` + 0x14）
它**只是 setter，不做任何校验**：
```
0xBDC591  mov edx,[ecx]      ; 数据[0..4]
0xBDC593  mov [eax+0x18],edx
0xBDC596  mov edx,[ecx+4]    ; [4..8]  → +0x1C
0xBDC59C  mov edx,[ecx+8]    ; [8..12] → +0x20
0xBDC5A2  mov ecx,[ecx+0xC]  ; [12..16]→ +0x24
0xBDC5B3  ret 4
```
⇒ **128 位消息 = 16 字节原样存成 4 个 u32**，语义由上层消费方决定。

## 五、★ 核心卡点与突破

### 卡点
- 登录时客户端处于 **状态 6**：收包、解密、写队列，**从不解析**
- 进状态 4 的唯一入口要求 `状态==1 && [socket+0x9C]!=0`，
  而**没有任何代码把状态写回 1**（该断点实测零命中）
- 读队列的虚函数 `0xBF0FC0`（vtable 项 `0xE6408C`）及其镜像 `0xBF10F0`（`0xE6410C`）
  **从头到尾没被调用过**（两个 vtable 项的硬件读断点均零命中）

### 突破：强改状态
`tools/ce_force_state.lua`：
```
0xBD50A0 命中 → EBX = ring → socket = ring - 0x4E0
→ write [socket+0x9C] = 1
→ write [socket+0x280] = 4
```

**行为对比（决定性）：**

| 操作 | 客户端行为 | 弹窗 |
|---|---|---|
| 不改（状态 6） | 收下、解密、排队、**干等 30 秒** | `A 2:0` |
| **强改状态 4** | 收下、**立即解析、1 秒内主动断开** | **`A5:13`** |

```
15:07:23  write [socket+0x280] = 4  -> true
15:07:25  peer closed after 36 bytes      ← 主动断开
15:07:25  closed (存活 4.4s)              ← 不再是 30 秒超时
```

## 七、第 37 轮纠正：`A 5:13` 是撕帧，登录读的是另一套明文环

### `A 5:13` 的调用点
文案是 `40,0,0`「服务器通信被切断了(%c %d:%d)」。
`0xBD4FB0`（状态 6 的收包函数）里：

```
mov esi, [buf]          ; 密文缓冲的第一个 u32 = 声明长度
call 0xBD36E0           ; 上限 = max(socket+0x1C8 - 0x12, 0x578)
ja  / je  → 0xBD5149    ; 长度 > 上限，或长度 == 0
0xBD5149  push 5 / push 0x0D / call 0xBF89A0
```

`push 5; push 13` 就是弹窗里的 `A 5:13`（和以前 `push 1; push 9` → `A 1:9` 同一条路径）。
同一对常数在 0xBD5554 / 0xBD5B4F 等处还有几份拷贝，是不同流类型的克隆。

### 强改状态 4 为什么必现这个错
状态 4（`0xBEFB73`）**不读解密队列**。它从密文缓冲 `socket+0x230` 直接取 `位长/8` 个原始字节
（登录这里是 16），交给 `0xBEFA90`，再用 `0xBF8850` 把这 16 字节从缓冲里吃掉，
然后状态 5 → `0xBED980` → 状态 6，**紧接着就调用 `0xBD4FB0`**。

我们下发的加密帧是 20 字节（`u32 长度=16` + 16 字节密文）。状态 4 吃掉前 16 字节后，
剩下 4 字节密文被 `0xBD4FB0` 当成「长度」。这个 u32 要么是 0，要么远大于 0x578，于是 `A 5:13`。
换 payload 改变不了这件事。16 字节整段被吃光、后面不再跟数据时，才不会走到这个长度检查。

### 登录这条连接的类
状态机 `0xBEFB40` 在 vtable `0xE6375C`，RTTI 是

`iCryptSession<iTcpStream, CamelliaCrypter>`

它的明文环（`0xBD3670` 读、`0xBD36A0` 推进）：

| 字段 | 偏移 |
|---|---|
| buf | `socket+0x4E8` |
| head | `socket+0x4EC` |
| tail | `socket+0x4F0` |

`0xBF0FC0` 属于另一个类：`iCompressSession<LZP, iCryptSession<iLoopbackSession, Camellia>>`。
登录走的是 TCP Camellia，**不会调用它**。之前对 `0xE6408C` 的读断点 0 命中是预期结果，不是「没人解析」。

### 第 38 轮：上层在读，但记到的 24 次全是空队列

`0xBD3670` 的调用者是 `0xBF9580`（返回点 `0xBF9596`），再往上是套接字事件 `0xBF9E1E`。
`avail==0` 时 `0xBF95A0` 直接返回；`avail>0` 才把指针和长度交给 `[session+0x1C4]` 的虚函数 `+0x20`，
然后 `call [vtable+0x3C]`（`0xBD36A0`）把数据吃掉。

24 次命中发生在状态 3→6 的瞬间，`head=tail=0`，断点随后被卸掉。
sweep 的帧是 2 秒后才发出的，所以这 24 行**不能**证明明文一直是空的。

### 第 39 轮：明文进了 `CGVOProtoAuth`，尾部的 `00` 把流卡死

`WRITE` 明文 `00 0B 00 00 00 C6 D7 7A 61 00…` 与 sweep 第一帧一致，状态 6。
`DELIVER` 的监听者 vtable `0xE148F4` = **`CGVOProtoAuth`**，入口 `0xBD1610`。

首字节高 4 位 = 消息类型（0..4），低 2 位 = 长度字段额外字节数。
类型 0、宽度 0：`byte1` = payload 长，总长 = 2 + payload 长，吃完返回这个总长；
字节不够则返回 0（`0xBD1A2D`），队头不动。

所以这 16 字节被拆成：
1. `00 0B` + 11 字节 → 吃掉 13
2. `00 00` → 长度 0 的空消息，吃掉 2
3. 剩下 1 个 `00` → 头不完整，返回 0，之后每次轮询都停在这 1 字节

payload 再交给 `0xA5B290`，用首部 **u16** 做分发。已见到的操作码：
`0x1146 0x298E 0x4F3F 0x60E0 0x8F36 0xA103 0xA5DA 0xDE24`。
客户端自己发出的那条明文是 `00 0E | A9 34 …`（u16 = `0x34A9`），刚好 16 字节、一条消息。

`fake_auth.py` 的默认 sweep 已改成 8 条同样形状的帧：`00 0E | 操作码 | 12 字节 0`。

### 第 40 轮：界面进了「登录中」，客户端发出账号包，然后 `A 2:0`

`ce_plain.log` 停在 `16:49:30` 的装载行，之后没有命中。
`pcall` 返回 true 只说明 Lua 没抛错，断点没有打进 `16:52` 那次登录的进程。
证据在 `fake_auth.log`，不在 CE。

`16:52:10` 握手后客户端先发 20 字节（明文仍是 `00 0E | u16 0x34A9 | …`，对应「认证中」）。
`16:52:12` 到 `16:52:26` 八条完整消息都发完。
`16:52:26` 与最后一条 `op_de24` 同一秒，客户端再发 100 字节（`u32 0x60` + 96 字节密文）。
`16:49:57`、`16:51:04` 两次也是卡在 `op_de24` 这一秒。连接随后空闲到 `16:53:11` 被服务端关掉。

上行密钥 `22*16`，计数器接着首帧：首帧 n=0，这 6 块是 n=1..6。明文：

```
00 5E | u16 0xF24B | "123\0" | "202cb962ac59075b964b07152d234b70\0"
      | "31555bd7-55f4-427f-8171-ad972b74c4c9\0" | "00:00:00:00:00:00\0"
```

类型 0、长度 94，一条消息刚好占满 96 字节。
`202cb962ac59075b964b07152d234b70` 是密码 `123` 的 MD5。
后面两段是客户端 UUID 和全零 MAC。

这条包由 `0xA5C410` 组出（`mov word [ebp], 0xF24B`），唯一调用者 `0xA560A4`。
函数入口要求 `[this+0x5E] != 0` 才发送。镜像里没有 `cmp` 这个操作码的接收分支，
`0xF24B` 只出现在三个发包点（`0xA5C499`、`0xA85AC9`、`0xAD65F9`）。

`CGVOProtoAuth` 虚函数 `+0x64`（`0x4B31A0`）是 `ret 8`。
八个操作码处理函数里解析失败时的 `call [vtable+0x64]` 什么都不做，所以空正文不会弹出 `A 2:0`。
`A 2:0` 仍是通信切断对话框：账号包发出去之后没有人回，客户端等到超时。

`0xDE24` 的处理在 `0xA5BD60`：先 `A5A1C0(1)`，通过后连读 3 个 u32（正好 12 字节）。
对象 `+0x38C` 为空时走 `0xA5BF22`，`call [vtable+0x68]`（`0xAF3E60`）。
第一个 u32 `>= 0` 就把 `[this+0x3CC]` 写成 1。

`[this+0x5C]` 到 `[this+0x7B]` 在 `0xA5A530` 被初始化成 1，所以 `[this+0x5E]` 一开始就是 1。
账号包的发送开关不是某条操作码打开的。打开「登录中」的是 `+0x3CC`：
`0x43DDD0` 看到它为 1，并且会话状态是 3 或 4，就调用 `0x439FB0(1)`。
`CGameStateStepUpdateLoginAuth`（`0x43A140`，步骤 0）随即发出 `0xF24B`，步骤改成 1。步骤 1 空转。

`0xA5DA` 正好读 1 个 u32，读完调用 `0xAF3CD0`。u32 `>= 0` 时经 `0x438C90` 广播给游戏步骤的虚函数 `+0x0C`。
`LoginAuth` 的这个函数是 `0x42DA20`：参数 `>= 0` 步骤加一，`< 0` 写成 `0x64`。
步骤变成 2 后，`0xA5CE10` 发出 `0x8288`，等待条切到「正在取得战区列表」。
上一轮盲发的 `op_a5da` 声明长度 14，读完 4 字节对不上结尾，所以没走进这条分支。

`fake_auth.py --sweep` 现在：首帧后只发 `op_de24`，上行明文以 `00 5E 4B F2` 开头就回 `op_a5da`
（u32 默认 0，块尾用 8 字节未知操作码填满）。`--login-code` 改这个 u32。`--sweep-list` 仍是旧的盲发。

17:37 两次都走到了：`op_de24` 之后客户端立刻回了 `0xF24B`，`op_a5da code=0` 之后又回了 20 字节。
用上行计数 n=7 解开是 `00 02 | u16 0x8288`，正好 4 字节明文，后面 12 字节是补块。
线上头是 `04 00 00 00`（明文长度），不是密文长度。解析器按密文长度只吃了 4 字节，
把剩余密文当成下一帧长度，随即关掉连接，所以界面直接是 `A 2:0`。
上行 u32 = 补块前的明文长度，密文按 16 对齐。下行仍按密文长度发。

17:48 的连接在帧长改对之后停在「正在取得战区列表」。登录本身已经过了：
`0x34A9` → `op_de24` → `0xF24B` → `op_a5da code=0` → 客户端发出 `0x8288`，
然后 45 秒空闲才断。`0x8288` 是 `send_worldlist_get`，对应的回复是 `0x298E`
（`recv_worldlist_get_r`，`0xA5B326`）。之前没有回这条，等待条就停在 `0x439FB0(2)`。

`0x298E` 先读 3 个 u32（结果码、预选区号、条数，条数 ≤ 32），再读 `count` 条记录。
`0xA5A380` 每条线上 309 字节：u32、0x31、0x31、0xC1、u32、u16、u32、u32。
写进内存时步长是 0x13C，中间两处填充不在线上。
载荷含操作码共 323 字节，类型 0 宽度 0 装不下，用宽度 1（`01 43 01` + 载荷，总长 326），
再补一条 10 字节的未知操作码凑成 336。下行计数从 `op_a5da` 之后的 n=2 起，占 21 块。

`0xA5B598` 把这三个 u32 和记录指针交给 `0x43E700`：
结果码是第一个 u32，必须 ≥ 0；第二个 u32 和记录开头的区号相等时，这一条被标成当前选中；
条数是第四个参数。`0x43E700` 里 `[记录+0x134]` 做除数，容量填 0 会除零。
结果码 ≥ 0 时还会调用步骤虚函数 `+0x10`，`LoginAuth` 的步骤从 3 变成 4，下一步结束。

3. `0x1146` 的三个字符串是 C 字符串（`0xA5A160` 读到第一个 0），不能按定长 0xE7 补 0。
   字段：结果码、区名、`loungesv_host`、`loungesv_port`、userid、otp。
   结果码 0 会经 `0xA4F3B0` 关掉认证连接。端口填 0 时闪白退回账密；填 30000 才会连上休息室。
4. 第二条连接是休息室。短 `0xF24B` 是 `proto_lounge_client::send_authenticate`：
   `00 0C | 用户号 1 | otp "local"`。回复是休息室自己的 `0xA5DA`（操作码同样是 `0xA5DA`，正文是两个 u32）。
   第一个 u32 ≥ 0 才离开「频道登录中」。认证服那条前缀是 `00 5E`，不要混用。
5. 等待条变成「正在取得数据」（`0x439FB0(11)`）。客户端发 `0xF86A`
   （`send_datafile_download`），回复 `0x5290`（`recv_datafile_download_r`，`0xAB09B6`）。
   字段：结果码、文件名、hash、`src_bytes`、u16 `compress`、正文字节数、正文。
   `compress` 填 0。`0x544770` 看到完成位才会发下一张；完不成就停在这张，
   `--idle 45` 到点掐连接，弹出 `L 2:0`。

12:48 实测：`autoexec_sv.cfg` 用解密包里的 `autoexec.cfg`（10222 字节）顶上之后，
客户端立刻再要 `msma/msma_weapon_set.csv`。这 76 张表是服务端数据，
`download_list.csv` 只列了路径，解密包里没有文件。
回 `00 00` 或 `#\n` 都没有再要第三张。`0xA46480` 把正文当文本读，
并且另一条路径会先丢掉前 2 字节；短于 3 字节丢掉之后是空的，这一项失败，队列停住。
缺文件现在回 `####\n`，丢掉 2 字节后仍以 `#` 开头（`0x9DC818` 把 `#` 当注释行跳过）。
这一版还没有跑过。
