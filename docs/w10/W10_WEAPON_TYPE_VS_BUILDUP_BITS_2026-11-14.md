# W10 · 客户端武器类型（C 值）与强化位表对照分析

> 日期：2026-11-14　｜　性质：**只读数据统计**，不改服务端表 / 不改看板 / 不改任何 runtime 代码
> 目的：用数据验证（证伪）「客户端强化面板可选数值项由武器类型（C 值）决定」这一推测。

**一句话结论**：C 值与 6 位强化位表**强相关但非决定**——同类型内出现 2 种以上位向量的类型占多数，且 31 种位向量里有 **17 种被 2 个以上类型共用**；位表实际是「该武器 `attributes_json` 里有没有这 6 个字段」的投影，与类型只有统计相关性。

## 一、方法与数据源

### 1.1 数据源探明（四个 `weapon_settings` 口径对比）

文件均为 **UTF-8（含 BOM）**，`#` 开头行为注释；数据行列数 149 列（`weapon_seed` 为 134 列，多/少列错位，不可与主表混用）。

| 文件 | 数据行 | C 值枚举数 | 判定 |
|---|---:|---:|---|
| `dataset/snapshot/weapon_settings_50033_成功基线_20261111.csv` | **3994** | **25**（23 实质 + `-` 79 行 + 空 3 行） | **采用**：行数最多、口径最新（11-12），且 `tooling/build_visual_weapons.py` 正式读取的就是它 |
| `dataset/weapon_full/weapon_settings.csv` | 3890 | 23 | 旧全量快照，无注释头，比基线少 104 行 |
| `dataset/official_chain/weapon_settings.csv` | 28 | 5 | 仅 101021401 官方链样本 |
| `dataset/weapon_seed/weapon_settings.csv` | 22 | 6 | 列结构不同（134 列），仅供种子用例 |

> 说明：任务书给的三个候选中 `weapon_full` 行数最多，但仓库内还有更新的 `dataset/snapshot/*_50033_成功基线_20261111.csv`（3994 行），且是可视化工具与 235 项目共用口径，故以它为全量母本；`weapon_full` 作为交叉校验（C 值分布形状一致）。

### 1.2 列位探明（何时用 0-based / 1-based 已对齐）

`weapon_settings` 每行按 `,` 切分后：

| 索引（0-based） | 含义 | 证据 |
|---:|---|---|
| 0 | item_id | 与 `item.csv` 第 1 列一一对应（3976/3994 可查到名字） |
| 2 | 图标键（8 位挂载/图标号） | `build_visual_weapons.py:266` `key = c[2].zfill(8)` |
| **21** | **武器类型枚举（C 值）** | `build_visual_weapons.py:295` `kind = c[21].strip()`；本文件即任务书所称「C 值」 |
| 109 | 重量 | `build_visual_weapons.py:305` |
| 112 | 倒地值 | `build_visual_weapons.py:281` |

类型枚举为**字符串**（`BEAM_RIFLE` / `WRESTLE` …），不是 0–21 的整数；`C21_TO_TYPE`（`tooling/build_visual_weapons.py:155-166`）共 23 项，与实测 23 个实质枚举完全吻合。

### 1.3 位表重算规则

严格照抄 `C4 服务器配置对齐/runtime_v1/server/hangar_experiment.py:479-490`：

```
col1 = 威力, col2 = 集弹性能, col4 = 装填性能, col5 = 锁定, col6 = 射程距离, col10 = 效果范围
bit = 1 if 该属性名 in weapon.attributes else 0     # 其余 14 列恒 0
```

`attributes` 在生产链路里就是 `unit_catalog.sqlite → weapon_resource.attributes_json`（`catalog_units.py:68-75` 读取，`down_points.py:14` 注释亦确认）。**已验证：6 个位控字段在 5855 行里没有任何「键存在但值为空」的情况**，所以「键在 = 位为 1」成立，不存在空串歧义。

### 1.4 两表如何关联（关键限制，先讲清楚）

`weapon_settings`（3994 把，客户端 item 表）与 `weapon_resource`（5855 行，wiki 页逐行）**没有共同主键**：

- `weapon_settings.c2`（图标键）↔ `weapon_resource.client_id`：**同域可比**，覆盖 5193/5855 = **88.7%** 的资源行；
- `item.csv` 名（多为日文 `ビーム・ライフル`）↔ `weapon_resource.weapon_name`（中文 wiki 名）：**精确名只命中 93/3994 = 2.3%**（中文名条目本身只有 485 条，命中 104 条）。

因此本报告采用两级证据：

1. **精确名子集（93 把，可 1:1 定位）**：加「去变体后缀 + 图标键校验」后命中 93 把，其中 89 把（96%）图标键也一致 ⇒ 这 93 把的「类型—位向量」对应关系**确定无疑**，用作硬证据；
2. **图标键分组（1755 组 / 覆盖 88.7% 资源行）**：把同一图标键下的武器视为一个「武器族」，只采纳**组内 C 值唯一**的组（1220 组，覆盖 2314 把 = 57.9%）做同类型统计，用作大样本旁证。

> 已知噪声：同一图标键会被不同武器族共用（文档 §13.3 已记载，如 `03010101` = SHOTGUN / BEAM_SPRAYGUN / REPAIR）。因此图标组证据一律做了「名称语义可解释性」人工核对，凡名字明显不属于同一族的组（如「散射型火箭炮 / 散射型火神炮」）不进结论。

### 1.5 复现脚本

`W10 武器类型探究/` 下 4 个只读脚本：`w10_probe.py`（关联率与初筛）、`w10_probe2.py`（图标分组反例）、`w10_probe3.py`（精确名子集）、`w10_final.py`（本报告全部数字）。全部以 `file:...?mode=ro` 只读打开 SQLite，未写任何数据库与 server 文件。

### 4.3 反例结论

- **31 种位向量中有 17 种（55%）被 ≥2 个武器类型共用**；
- **23 个类型中没有一个是「一位向量对一类型」的单射关系**（主位向量占比最高 96.8%，最低 44.2%）；
- ⇒ 「武器类型决定强化面板位表」**被证伪**。类型只是与位表**统计相关**（因为类型本身也是从参数集合归纳出来的），真正决定位的是**该武器 `attributes_json` 的字段是否存在**。

### 5.2 量化判定：是否「按类型模板批量生成」

| 指标 | 数值 | 含义 |
|---|---:|---|
| 全库 attributes 键集种类 | **287 种** | 若按类型模板生成，应 ≈ 类型数（23） |
| 最大单一键集占比 | 11.7% | 无全局模板 |
| 每类型内部键集种类 | 25–61 种（MACHINEGUN 25、HAND_THROW 30、BAZOOKA 31、HOWITZER 33、CHARGE_RIFLE 39、BEAM_RIFLE 40、WRESTLE 41、MISSILE 61） | 同一类型内部也**不是**一套键集 |
| 每类型主键集占比 | 13%–50%（MACHINEGUN 49%、WRESTLE 50%、MISSILE 13%） | 只有统计共性，无强制模板 |

**录入规则结论（一句话）**：`attributes_json` 是**逐把按 wiki 武器模板实际填写的字段集合**（缺项就不出键，扩展项如连射速度/红锁/诱导/特殊*比例 按武器个体差异出现），**不是按武器类型批量套模板**；类型与键集之间只存在「同类常见字段相似」的统计倾向。6 位位表是这个大键集在 6 个字段上的投影，因此**位表由「这把武器有没有这 6 个字段」直接决定，与 C 值无函数关系**。
