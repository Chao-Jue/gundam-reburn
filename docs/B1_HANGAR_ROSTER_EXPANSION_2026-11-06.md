# B1 机库机体扩容：从 1 台到 358 台的完整链路与派生问题合并整理

整理日期：2026-11-06。本文把五个原本分散记录的「计划外」问题合并为一条主线：
**X2 机库扩充 / X3 客户端资源审计 / X6 机体改名 / X9 未知机体占位 / X11 无图标资源过滤**。
它们不是五个独立特性，而是同一个目标（把机库从 1 台实验机扩到资源允许的上限）在不同阶段
暴露出来的后续与扩散。本文给出统一的问题视图、可复用判据、实现路径、版本边界与回滚办法。

> **本 PR 是文档 + 纯标准库工具，不改服务端逻辑、不改任何表、不携带客户端资产或存档。**
> 上游 `AGENTS.md` 禁止上传客户端、解码资产、转储、日志、账号、凭据与 `saved_*` 存档；
> 本文只记录统计数字、判据和实测结论，不含上述任何内容，也不含部署 IP 或本地绝对路径。

### X11 的两处细节（最容易复错）

- **判据自检**：269 台已命名机体 **269/269** 有 `s`+`d` 图标 ⇒ 10 位模型串口径正确；
  118 台占位机里 89 有 / 29 无。真机第 31 页 4 台红黑缩略图 `4/4` 落在 29 台内，
  同页 3 台正常缩略图都有图标。剔除后抽查 9 页 0 红黑。
- **重叠取舍**：`121011801`（ザクⅡJ型 / 渣古ⅡJ型）既是 22 台补名之一，又在 29 台无图标里。
  按「缺图标一律剔除」优先 ⇒ 机体删除，名字仍入库，实际生效 21 台。

### 关于「lastshot」

本地没有任何叫 `lastshot` 的数据源：客户端真实归档、`GundamOnline_CHINA.exe`
（含 UTF-16 宽字符）、解包参考树、235 包、并行项目资料里 `last[\s_-]?shot` /
`ラストショット` 命中均为 0。这个叫法应是并行侧对「过场动画 / 战场机制机体」的俗称，
**不要去找同名的清单**，直接用上面的图标判据界定这批机体。

## 3. 三条铁律（跨阶段共用）

1. **判「资源存在」必须查客户端真实归档，不能查解包参考树。**
   `data/chara/<AA>/<BB>.hed`（43 个）、`data/interface/icon.hed`（缩略图）、
   `data/settings.hed`（表）。参考树比实际客户端完整，会系统性高估：
   武器侧同一坑表现为 898 个唯一图标键「参考树有、真实归档没有」，反向 0 个；
   机体侧表现为「473 台可用」的错误基准和 3 台点开就崩。
2. **表两铁律**：CSV **数据行必须带尾逗号**；改表必须经 `serve` 重启（表在启动时构建并缓存）。
   少一个尾逗号的表现不是报错，而是客户端停在「正在取得数据」或弹 `[5:13]`。
3. **单帧 16366 B 硬上限**，`0x5290` 正文自带 `u16 compress`，`compress=1` 走 zlib，
   `src_bytes` 必须是**解压后**长度（填小了静默截断且客户端不检查返回值）。
   详见已提交的 PR #7。358 台四表最大帧 **13382 B / 16366 B**（余 2984 B）；
   历史对照：269 台 8976 B、387 台 14236 B。正文没有 offset / 序号 / 总长，
   **一帧 = 一整张表，多帧分片不可行**。

## 4. 判据的形式化定义

### 4.1 ID 编码与模型路径

```
msma_id = A * 1_000_000 + B * 100 + v          # A、B 各 4 位数字组（十进制丢前导 0）
目录    = chara/<A4[0:2]>/<A4[2:4]>/<B4>/
模型    = MSM_<A4>_<B4>_<v2>.dxg
```

例：`101110101` → `A=0101, B=1101, v=01` → `chara/01/01/1101/model/MSM_0101_1101_01.dxg`；
`101010101` → `A=0101, B=0101, v=01` → `chara/01/01/0101/model/MSM_0101_0101_01.dxg`
（与本项目 `docs/CURRENT_UNIT_ASSOCIATION.md` 的 `101*1e6 + 0101*100 + 01` 一致）。

★ **易错点**：不要按字符串目测拆段。我们本地一份生成器注释曾写
「`101011101` → `A=0101 B=1101`」，但按上式它实际是 `(101, 111, 1)`，
`B=1101` 对应的是 `101110101`。`tools/verify_roster_expansion.py` 把这条
作为固定回归检查，避免照抄注释导致判据整体错位。
「机型 ID / 模型 ID / 客户端号 / Wiki revision」是不同身份，不要混用。

### 4.2 缩略图键

```
10 位模型串 = "0" + 9 位 model_id（补零到 9 位）
s 图 = ./item/s/s<10位>.dds
d 图 = ./item/d/d<10位>.dds
```

`icon.hed` 实测 15885 条记录、`s10` / `d10` 各 417 个键。判「可上架」要求 s、d 成对存在。

### 4.3 名字来源（三层，别搞混）

| 来源 | 内容 | 能不能当机库名 |
|---|---|---|
| 服务端 `msma_settings.csv`（名册生成） | 机体名，随表下发 | **是，唯一生效来源** |
| 客户端 `settings.hed → ./favms_ok_list.csv` | 315 数据行，只有 7 位 `練度ID` + 日文名 | 否。是最爱机体 / 图鉴白名单，改它不影响机库显示 |
| 235 加料版 `favms_ok_list.csv` | 702 行 / 14 列，多出 `モデルID`、中文 WIKI 名等 | 只能当**补名来源**，靠 `モデルID` 列桥到 9 位 ID |

7 位 `練度ID` 与 9 位 `msma_id` 之间**没有算术推导关系**（`1111011→101100101`、
`1107011→101020101`、`1421011→103090101`），只能靠上面那张加料表桥接。
这一点决定了「客户端表里有机体 id 和名字」≠「能直接拿它给机库命名」。

补名归一化规则：中文 WIKI 名优先 → 去掉 `高达OL` 前缀与尾部 `（国）/（日）` 地区标注；
WIKI 名为空的保留日文名。22 台归一化结果与人工核对列 22/22 一致。
国服用语系：敢达 / 渣古 / 老虎 / 格鲁古古 / 龟霸 / 魔蟹 / 战蟹 / 吉刚。

## 5. 实现路径（服务端侧，供复现）

```
登录名册链：0x16AC → 0x2ACF（slot_num = 本次 0xA832 记录条数，不是仓库容量）
            → 0xA832 × N → 0xFCE6（空正文结束）
表下发：   0xF86A 请求 → 0x5290 应答（四张 msma 表）
名册：     dataset 里一份 JSON，按 mtime 热读 ⇒ 改名册不用重启；
           但改「表」必须重启（铁律 2）
补齐：     ensure_roster() 登录时按名册补实例（幂等），sync_names() 同步昵称
占位：     不写 perf 数据 ⇒ perf_of() 找不到即回退 GM 常量模板（3425/1004/1000/TIME50…）
过滤器：   剔除名单要写进独立指针文件，让占位脚本下次运行不会「复活」已删机体
```

四张表：`msma_settings` / `msma_battle_detail` / `msma_model` / `msma_weapon_set`。
358 台时 zlib9 实测：131710→12864 B、108456→13318 B、26278→1232 B、6647→422 B。

**每一步都要能回滚**：名册追加用「只追加、不重建」（避免打乱已持有存档的 `uniqid`
顺序和编队 / 强化 state）；占位脚本提供 `--apply` / `--revert` / `--rename`，
清理脚本提供 `--apply` / `--revert` / `--verify` 并先写三份备份；
开关 `MSGO_ROSTER_EXPAND=0` 只停扩容，**不会**裁掉已写进存档的实例，
所以「停实验」必须按「裁名册 → 关开关 → 重启」的顺序，否则会出现表里查不到 `msma_id`
的点开就崩条件。

## 6. 用法（本次提交的工具）

两个脚本都是纯标准库、不访问客户端、不读取本项目的 `dataset/`，可独立运行：

```bash
# 判据自测：ID 编码 / 图标键 / 尾逗号 / 帧上限 / 台数守恒 / 名字归一化 / 重叠取舍
#            + 3 项交付物静态检查（无本地绝对路径 / 无凭据 / 无部署 IP）
python tools/verify_roster_expansion.py

# 判据工具骨架：输入自己导出的归档路径清单 + 候选 ID，输出可上架 / 剔除清单
python tools/roster_archive_audit.py --selftest
python tools/roster_archive_audit.py \
    --index client_archive_index.txt \
    --candidates candidate_ids.txt \
    --out audit_report.json
```

`--index` 是一行一个资源路径的纯文本（由你自己的 HED 索引解析流程导出，
本工具不含解密逻辑，也不要求你上传任何客户端文件），例如：

```
chara/01/01/1101/model/MSM_0101_1101_01.dxg
chara/01/01/1101/model/MSM_0101_1101_01C.dds
./item/s/s0101010101.dds
./item/d/d0101010101.dds
```

输出分三类：`ok`（模型齐全 + s/d 图标成对）、`no_icon`（模型齐全但缺缩略图 ⇒ 对应 X11 剔除集）、
`miss`（模型目录查不到 ⇒ 对应 X3 的 archive-miss）。把 `--candidates` 换成你自己版本的
定义表 ID 列即可复用整套判据。

## 7. 版本边界（★ 最重要，别照搬）

本文实测全部来自 **MSGO 5.0.0.33 国服客户端 + 自建 50033 服务端**。
上游主线是 9.0.0.235，两者**数值 / 表结构 / exe 地址 / 资源编号口径都不通用**：

- 可以迁移的：**判据与顺序铁律**（查真实归档、尾逗号、单帧上限与 `compress` 语义、
  ID→目录→模型文件的编码关系、图标键命名、名字来源分层、先让位后占位之类的顺序要求）、
  **失败模式**（白屏 / `[5:13]` / 点开闪退 / 红黑缩略图各自对应什么错）。
- 不能照搬的：任何具体台数、性能数值、CSV 列号、opcode 长度、exe VA、模型目录数量。
  例：235 的 `weapon_battle_detail.csv` 是 key-first（`9500000,POWER,40`），
  50033 不是；235 的 `mechanic_ticket.csv` 是「1 格 = 1%、行键 = 券 id」，
  50033 是「g8/g7×2、`INITIAL_ODDS` 唯一来源、行键 6010xxx」。
- `compress=1` 分支只在 50033 客户端真机验证过；235 侧要先用一张小表单独验证。
- 客户端接入补丁（PR #5）写死本地测试地址 `127.0.0.1:30000`，补丁必须放在
  **与 `GundamOnline_CHINA.exe` 同级的游戏根目录**（`%~dp0` 自定位）。
  换部署要同步改四处同值；本 PR 不改动这些文件。

## 9. 失败尝试与未验证项

- **判资源用解包参考树**：判负。选出 3 台在真实归档里查不到的机体，图标空白、点开报错；
  武器侧同一坑高估 898 个唯一图标键。
- **多帧分片下发大表**：不可行。`0x5290` 正文没有 offset / 序号 / 总长，
  客户端一帧就解包 → `Load` → `erase` 队列节点 → 请求下一张表，第二帧名字查不到会静默 return。
- **纯协议改机库显示名**：判负。机库名来自服务端 `msma_settings.csv`，
  客户端 `favms_ok_list.csv` 是最爱机体白名单，改它不影响机库。
- **`lastshot` 关键字检索**：全库 0 命中，改用图标判据。
- **235 客户端**：本 PR 的 `compress=1`、机型与图标判据均未在 235 真机验证；
  排序 UI 顺序回显（`0x2C17→0x3075`）仍是半修复状态，不属本 PR 范围。
- 遗留：68 台占位机暂无名字来源；281 台「235 有数据但客户端无模型」仍不能上架；
  2 台精确变体文件缺失的风险机体仍在库里（点开可能闪退）。
